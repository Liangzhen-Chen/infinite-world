# 门禁提交流程重设方案（第 2 版，按审查 A、B 的 changes 修订）

状态：纸面方案。亮圳同意之前，不改任何脚本、钥匙、账号、权限，也不连服务器。依据：docs/审查/门禁提交流程调查.md（下称"调查"）、F:/dnd-tmp/review/门禁方案-审查A.md、-审查B.md、F:/dnd-tools/cloud/gate/ 下本机脚本。

先说清楚：第一期没有新增任何技术防线，只把"写结论"与"提交"拆成两次调用，并去掉 python 读 stdin。防代交、防自批的技术保证全部在第二期。

## 1. 问题陈述

### 1.1 被拒事件
调查第 4 节：一次 Bash 调用里先用两个 heredoc 写结论文件、紧接着运行 review-submit.sh 提交 approve，被分类器以 [Undermining Oversight] 整条拒绝，无部分执行；此前"先单独写文件、再单独运行"的提交都成功。调查的最可能结论（推测、未确认）：写结论与提交批准合在同一步，叠加"用特权钥匙写批准记录"的性质。不是 python 或 heredoc 本身所致。

### 1.2 现流程的弱点
1. 自报身份：review-put.sh 只校验 reviewer 字段符合 id 正则，不核实是谁。
2. 共享钥匙：tc_review 单一共享，无按人绑定。
3. 可代交：持有同一脚本和钥匙的协调者技术上可替"审查者"提交两轮。
4. 写结论与提交同一步：review-submit.sh 把 verdict 当参数，拼 JSON 后立刻写入批准记录。
5. 辅助弱点：implementers、哈希、r1 引用都是调用方自报。

### 1.3 python 读 stdin 的违规（项目红线），第一期范围
- review-submit.sh:12-18：`python - ... <<'PY' | ssh ...`，脚本本体经 stdin heredoc 读入。
- manifest.sh:7：`git ls-files -z | python "$M" ... --stdin-list`，清单经管道读 stdin（接收端 manifest.py:121-122）。
- stage.sh:14：与 manifest.sh:7 同类，同样 `--stdin-list`。
- stage.sh:19：`$T get ... | python -c "import json,sys;d=json.load(sys.stdin);..."`，python 从 stdin 读 JSON。
- 不在第一期：deploy.sh:15（ak()）、:66、:83 的 `python3 - ... < akedit.py`，及 akedit.py 第 1 行注释，移到第二期（它们每个动作都改 authorized_keys，无法在不动钥匙的前提下验证）。
- 不违规：deploy.sh:23、:26、:62 的 `python3 -c`、gate.sh 对 manifest.py/apply.py 的调用，都不读 stdin。
- 连带：去掉 `--stdin-list` 会打断 manifest.sh 与 stage.sh 两个调用点，所以必须按 3.1 的顺序同批改完。

## 2. 第二期目标流程

角色：审查者（只写并签自己的结论文件）；协调者（派卡、登记实施者、触发 run，不写不改结论）；门禁（服务器 gate.sh，run 时核对）。

### 2.1 步骤
1. 审查者读代码，写本地 `F:/dnd-tmp/review/verdicts/<hash>/r<轮>-<审查者>.json`（单独一次调用）。
2. 审查者本人用自己的私钥签名（单独一次调用）：`ssh-keygen -Y sign -f <审查者私钥> -n gate-review <结论文件>`，得到同目录的 `.sig`。结论文件字段：
   - schema、round（1 或 2）、hash（内容哈希）、verdict（approve 或 changes）、reviewer（id）、scope、findings；
   - cmd：本次批准针对的入口命令与参数（见 2.4）；
   - covered_excludes：哈希不覆盖的路径清单（见 2.3）；
   - nonce（随机串）、issued_at、expires_at（有效期上限 7 天）、max_runs（可被运行次数，默认 1）；
   - round1_sha256（仅 r2：r1 结论文件的 sha256；r1 填 null）。
   签名覆盖文件全部字节，所以上述任何字段都不能被事后改动。
3. 传输，两种都允许，因为门禁只信签名，不信谁传的：
   - A 路径（推荐用于 changes 结论）：审查者自传，经只能写 inbox 的受限通道，不经协调者。
   - B 路径：协调者或任何人，随内容一起，原样转送（.json 与 .sig 一并）。转送者没有批准权：改一字节验签失败；伪造则没有登记的私钥；转送者能做的只有"不转"和"重复转"，分别见 4.3 的缺失与重放处理。
   上传所用钥匙与审查者身份无关，门禁不从上传通道取身份；这就消除了原方案"上传钥匙与身份绑定"的矛盾。
4. 门禁 run（见 2.2）验签、取 id、核对全部条件后才放行。
5. 门禁的审计日志（见 4.4）记录每次决定。

### 2.2 门禁 run 时的核对（取代原 approved()）
按顺序，任一不满足即拒绝并写审计：
1. 取 run 锁（按目录加 flock），把 /work/<dir> 复制为只读运行快照，由门禁账号拥有、runner 只读。
2. 对运行快照自己重算内容哈希（不是对原目录，更不是用记录里的哈希）。作业只从该快照运行。这堵住"核对完、执行前目录被改"的 TOCTOU：被核对的字节与被执行的字节是同一份。
3. 取 inbox 中全部候选，验签：`ssh-keygen -Y find-principals` 从签名得出 id，再 `-Y verify` 对登记表 allowed_signers（namespace gate-review）验证；文件里 reviewer 字段必须等于签名得出的 id。验不过的候选丢弃并记审计，不参与否决（防拒绝服务，见 4.3）。
4. 只保留 hash 字段等于第 2 步重算哈希的候选；cmd 必须等于本次 run 要执行的入口命令与参数（见 2.4）；未过期；未被撤销；未用尽 max_runs。
5. 任一有效 changes 一票否决。
6. 需要一条 r2 approve，其 round1_sha256 等于某个存在的有效候选的 sha256，且该候选 round==1、verdict==approve、hash==r2.hash==当前哈希；两轮 reviewer 互不相同；两者都不在实施者登记中（2.5）；登记缺失则拒绝（fail closed）。
7. 通过后原子地登记一次消耗（4.2），再执行。

### 2.3 哈希覆盖范围（manifest 的实际口径）
manifest 行为 `<sha256>  <相对路径>`，按路径字节排序；文件内容 CRLF 归一为 LF（文本文件；.gitattributes 标 -text 或含 NUL 的按原字节）；符号链接哈希其链接目标；顶层 node_modules、.out、.tmp、.git 排除；本地用 `git ls-files -co`（含未跟踪、不含被忽略），服务器侧遍历全部文件，二者相等即证明服务器目录没有额外的被忽略文件。
不被哈希覆盖：可执行位等文件权限、空目录、被排除的顶层目录。要求：
- 作业的入口、依赖和读取路径必须都在覆盖范围内；排除的目录由 run 环境在快照内自行重建（如 node_modules 由锁文件安装），其来源在 covered_excludes 中写明，审查者签名时已知；
- 可执行位是否需要纳入哈希，由亮圳批准是否改 manifest（改了所有旧记录作废，且必须先过 5 节第 1 点的等价验证；一处不一致整项回退，不修补）。在此之前，作业不得依赖文件权限位，入口命令一律显式写解释器，如 `bash x.sh`。

### 2.4 命令绑定
记录绑定的是内容哈希加 cmd 字段。同一内容用不同入口或参数运行，需要另一份带该 cmd 的签名结论。run 时 gate.sh 把实际要运行的入口命令与参数规范化后与记录的 cmd 逐字比较，不等即拒绝。

### 2.5 实施者登记
- 谁写：协调者在派卡时通过 tc_dnd 的 `register-impl <dir> <ids>` 动词追加（只追加，不覆盖、不删除；同目录后续派卡取并集，旧实施者永远留在名单里）。审查者通道没有该动词的写权，登记表不可被审查者改。
- 如何防冒充：审查者 id 只由签名对应的登记公钥决定（allowed_signers 由亮圳用 tc_admin 写，协调者无权写）。实施者（执行者代理）不持有任何登记私钥，所以实施者无法以审查者 id 签名；协调者也没有被登记的 id，所以协调者无法自批。登记表只是第二道检查：防止"同一个持钥的 id 既实施又审查"。
- 不防的：协调者故意少登实施者。缓解：审计日志每次 run 记录登记内容，亮圳抽查与 PLAN 派卡记录对账；登记缺失一律拒绝。该点列入遗留风险。

### 2.6 审查者身份与私钥保管
- 一人一把钥匙：每个审查者 id 一把 ed25519 签名钥匙，公钥登记在 allowed_signers，同一把钥匙不得登记为两个 id，实施者与协调者不得持有任何审查者私钥。
- 保管者与位置（需亮圳批准选哪种）：
  - 方案一（推荐）：硬件安全钥匙（`ssh-keygen -t ed25519-sk`，签名需物理触碰）或带口令的钥匙，由亮圳本人保管、签名时本人在场操作；协调者会话读得到文件也无法签名。代价是每份结论亮圳要动手一次。
  - 方案二：独立 Windows 账号 gate-reviewer，钥匙在该账号配置目录，目录 ACL 只许该账号读，协调者所在账号无权；审查者代理必须运行在该账号会话里。代价是审查者代理的运行环境需要另配；若审查者仍与协调者同账号运行，则方案二只防误操作，不防故意，必须如实写成这个强度。
- 如实声明：同机同账号的代理，技术上无法证明彼此独立；没有方案一或二，签名只防事故与格式错误，不防协调者故意。

## 3. 分两期

### 3.1 第一期：不动钥匙，可马上做，共 2 项（只写方案，不改脚本）

协调者在第一期不提交、不转送、不改任何审查结论，仍由审查者本人用现有通道（tc_review，现有保管）提交。

**项 1：写结论与提交拆成两次独立调用（操作规范）**
- 调用一：审查者用 Write 工具写 `F:/dnd-tmp/review/verdicts/<hash>/r<轮>-<审查者>.json`，内容是现有 review-put.sh 接受的 JSON（round、hash、verdict、reviewer、implementers、round1、scope、findings）。这是唯一动作，不运行任何脚本。
- 调用二：审查者运行只读文件、不生成任何内容的提交脚本，不与调用一合并；输出不用 `| tail` 截断，全量保留。
- 协调者只触发 run 和读 stage.sh，不写、不转、不改任何结论文件。implementers 来自协调者派卡时写的本地记录文件，由审查者原样抄入；这一点第一期仍是自报，列入遗留风险。
- 只有现有真实审查才提交到真实 /work/.reviews；不为试探分类器而造假审查任务，不向真实记录灌测试记录（记录只追加不可删）。

**项 2：去掉 python 读 stdin（四处，各给替代写法）**

通用约定：临时文件一律 `mktemp`（默认权限 0600，仅属主可读写），放在 F:/dnd-tmp/ 下（避免 Git Bash 的 /tmp 路径对 Windows 原生 python 不可见；若仍用 /tmp 则传 `cygpath -w` 转换后的路径）；创建后立刻 `trap 'rm -f "$TL"' EXIT` 清理；不用 `$$` 命名。

(1) manifest.sh:7 与 manifest.py:121-122：
- manifest.py 新增 `--list-file <路径>`：读该文件，按 NUL 分割，逻辑同现 `--stdin-list`（不读 stdin）。
- manifest.sh 第 7 行改为：

  git ls-files -co --exclude-standard -z > "$TL"

（同一个 `$TL` 在循环内被覆盖复用，退出时清理；(2) 与 (3) 共用 stage.sh 里同一个临时文件。）

[ "$(printf '%s\n' "$fh" | grep -c .)" = 1 ] && [ "$fh" = "$lh" ] && [ "$lh" = "$sh" ] || { echo "REFUSED: hash mismatch"; exit 4; }

### 3.2 第二期：动钥匙或权限，等亮圳批准，共 6 项

**顺序：C -> E -> A -> B -> D -> F。B 依赖 C（登记的 id 必须由钥匙决定，否则登记无防御力）；回退顺序相反。**

**项 F：deploy.sh 的 python stdin 整改**（deploy.sh:15、:66、:83，akedit.py 第 1 行注释）：
一次 ssh 内完成，`cat` 收 stdin、python 只收文件路径：
```
as $k 'f=$(mktemp) && cat > "$f" && chmod 644 "$f"; python3 "$f" ARGS; rc=$?; rm -f "$f"; exit $rc' < "$G/akedit.py"
```
mktemp 产生不可预测文件名（O_EXCL 创建）；因 :66、:83 以 `sudo -u reviewer` 运行，需 chmod 644 让 reviewer 可读，用后立即删除；akedit.py 是公开脚本，不含秘密。ARGS 沿用现有预先加引号的参数。验证必须真的改一次 authorized_keys，所以整项在亮圳批准后、在影子账号上验证。
- 风险：写错会损坏 authorized_keys 导致锁死。
- 回退：改前备份 authorized_keys，tc_admin 恢复。

## 4. 作废、并发、审计

### 4.1 内容变化后旧审查自动失效
哈希在 run 时对快照重算，hash 字段不等的候选不参与；任何内容改动（含 CRLF 归一后的差异）都使旧记录失效。

### 4.2 撤销、有效期、单次使用
- 撤销：签名的 revoke 记录（字段 hash、可选 cmd、reason），由已登记审查者或亮圳签发，按哈希封禁；run 看到有效 revoke 即拒绝。
- 有效期：每份结论带 expires_at，上限 7 天，过期不参与。
- 单次使用：结论带 max_runs（默认 1）。run 通过后，在 /work/.consumed/<hash>-<cmd 的 sha256>/ 下用 mkdir 原子建立计数标记；已达 max_runs 则拒绝，需要再跑须新的签名结论。由审查者在签名时决定放宽，不由协调者决定。

### 4.3 并发、配对、缺失
- 配对规则：取全部有效候选；任一 changes 否决；r2 必须引用某个存在、有效、approve、同哈希的 r1 的 sha256。
- 原子写：inbox 先写临时文件再 rename，文件名为内容 sha256；run 在加锁后一次性读取候选集，之后新到的候选不影响本次 run。
- 加锁：同一目录的 run 与快照互斥；两个 run 同时使用同一批准时，靠 4.2 的原子 mkdir 计数，只有一个成功。
- 缺失/拒绝服务：未验签的 changes 不否决（防随意写入以封杀某哈希）；有效 changes 才否决。协调者"不转" changes 结论的风险：审查者的 changes 结论须同时留本地并报亮圳，门禁审计里"本地归档的结论 sha256 在服务器无对应候选"可对账发现；changes 结论优先走 A 路径自传。

### 4.4 服务器审计日志
/work/.audit/ 下只追加日志（门禁账号拥有，runner 无权；可加 append-only 属性），每次记录：时间、动作（inbox 收到 / run 决定 / revoke / register-impl）、目录、重算哈希、cmd、参与候选各自 sha256 与 id、通过或拒绝及原因、登记表内容快照。提供只读动词让协调者拉回，归档到 F:/dnd/docs/审查/。

## 5. 验证计划

原则：不绕过任何安全检查；负向测试（冒充、改写、重放）只在门禁的测试副本上做，不碰正式记录。

测试副本：把 gate.sh 及依赖脚本复制到独立目录，只把"记录根、inbox、登记表、审计、锁、consumed"这几个路径参数指向临时树，核对逻辑与正式版同一份代码、一行不跳过；测试用的审查者钥匙与 allowed_signers 是测试里新生成的，与正式钥匙无关；在云上运行（rt.sh），不写 /work/.reviews。

**第一期**
1. 哈希等价：同一棵含空格、中文文件名、CRLF 文件、-text 文件、未跟踪文件的树，用旧写法（--stdin-list）与新写法（--list-file）各算一次，必须逐字相同，并与服务器 hash 动词一致；stage.sh 对同一目录输出新旧一致。任一不一致，整批回退。
2. review-submit.sh 新形态：用不匹配的哈希调用应在本地 REFUSED 退出 4（这一步不写任何服务器内容）。第一次真正提交只在有真实审查需要时进行，每个步骤一次；不为试探造审查任务。
3. 第一期操作规范检查：同一次调用里不得同时出现"生成结论内容"与"提交"。
4. 分类器若仍拦截（包括已拆成两次调用之后），立即停下，不换写法、不拆调用试探，把被拒原文与调用内容报亮圳决定。同一步骤失败两次同样停下报因。

**第二期（在测试副本上，全部必须被门禁拒绝，只要有一条通过即不合格）**
- 冒充：未登记密钥签名；reviewer 字段与签名 id 不符；用实施者 id；同一 id 两轮；审查者在实施者登记；登记缺失。
- 改写：改一字节再验签；协调者用自己的未登记钥匙重写 r1 加 r2；r2 引用错误的 r1 sha256；r1 为 changes；hash 与当前不符；cmd 不符。
- 重放：同一份 r2 第二次 run（max_runs=1）；换哈希或换 cmd 后重放；过期记录；已撤销记录。
- 竞态：核对后改 /work/<dir>，快照执行的内容必须仍是被核对的内容；两个 run 同时用同一批准，只能成功一个；上传与 run 并发。
- 非法候选：无签名或验签失败的 changes 不得否决。
- 正向：合法的两轮、不同 id、自传（A）与转送（B）各一次，必须通过；审计日志对每条决定有记录。
- 正式上线前：备份 authorized_keys、/work/.reviews 权限清单、gate.sh；做回退演练；每项变更后重跑全部上述测试；经亮圳批准后才开始。
- 分类器若拦截任何一步，同样停下，报亮圳决定。

## 6. 安全论证

防自批：登记表加按钥匙决定的 id，使审查者不能是实施者，协调者与实施者没有登记私钥，无法以审查者身份签名；两轮互异、任一有效 changes 否决、r1 与 r2 同哈希同 cmd 都由门禁判定，不依赖提交者。
防代交：身份来自签名与登记公钥，不来自上传通道或自报；转送者（含协调者）无法生成或改动合法结论。第一期不具备这一点，只靠"协调者不碰提交"的规范。
防篡改：签名覆盖全文；hash 字段与 run 时对运行快照自算的哈希比对，且执行的是同一份快照；r2 以 sha256 绑 r1（只防事后替换 r1，不是身份绑定）。

## 7. 遗留风险
1. 第一期无技术防线，协调者代交仍只靠操作规范。
2. 私钥保管：未采用方案一（硬件触碰或亮圳口令）或方案二（独立账号且审查者运行其中）时，同机同账号的代理无法在技术上证明独立，签名只防误不防恶。
3. 实施者登记由协调者写，只能防"持钥匙的 id 兼任实施者"，防不住协调者故意少登；协调者使用未登记的第三方 id 不会通过（无登记钥匙），但需 allowed_signers 严格只由亮圳写。
4. 第一期 implementers 仍由抄入的自报文件提供。
5. 协调者可"不转" changes 结论（B 路径）；靠本地归档对账与 A 路径缓解。
6. ubuntu 账号保留 sudo（README 称为单独决策），可绕过目录权限；服务器被攻破则全部失效。
7. 哈希不覆盖可执行位、空目录、被排除的顶层目录；作业若依赖它们就是旁路（2.3 要求规避，未强制）。
8. 审查者质量与是否真的读了代码不在本方案范围；可要求 findings 附"已读文件清单"抬高伪造成本，但不能证明独立。
9. 分类器是否接受新流程，只能试后才知（5 节第 1 期第 4 点）。
10. 回退演练覆盖不到的线上差异。
