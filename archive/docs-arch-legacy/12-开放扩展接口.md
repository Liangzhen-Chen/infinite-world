# 12 开放扩展接口：第三方内容包的形状、加载、存档兼容与作者工具

用户需求原话："想象以后我开源了，有其他人想往里面加一些自己的内容，是不是不会那么费劲，可以通过统一的接口接入。"（2026-10-15，见 待用户确认.md 末尾"开放扩展"一条。）

本章回答：一个不读引擎源码的外部作者，怎样只写数据就把一个门派、一部地方法典、一座带新经济玩法的城镇接进世界；引擎怎样在加载时把错误挡在门外并说清楚怎么改；装、升级、卸载怎样不损坏存档；作者怎样用一条命令自测。

**核心主张**：第三方包与一方包（经济、法律、治理……）**是同一种东西**——第 3 章 §3.3 的玩法包形状，经同一个加载器、同一套校验、同一个注册表。"开放"不是另开一条后门，而是把第 3 章的包形状收紧成一份**有版本的公开契约**：八个核心概念、十九个效果原语（14 族）、规则四形状与四种声明式规则形状、钩子模板（附录 A §A.4）、词汇表、**开放性宪章**（附录 A §A.9：表开放、族开放、派生缺省开槽、定义可补丁、协议后续开放）、契约附表 B/C（core 派生值的 bounds、core 候选的输入，附录 A §A.16–§A.17），加上本章规定的清单、命名空间与受限表达式。契约之内的一切，作者写数据即可；契约之外（新原语、新求解器、新存储概念）作者不能做，只能向引擎提需求。修订历史见 修订记录.md；第五轮按根因分析 (a) 把"扩展点是封闭清单"改为"缺省开放、清单只是索引"。

## 12.1 目标与边界

**目标**
1. **零引擎改动接入**：新增门派、法典、城镇、物种、职业、契约、灾害、节日……只写包目录里的数据文件；不改 server-plugin、extension、L1 本体文件。
2. **说清楚的报错**：每个错误指出文件、字段（JSON 指针与行号）、违反了哪条规则或不变量、怎样改；一次报完同阶段全部错误，不是改一个报一个。
3. **装卸不坏档**：存档记录装了哪些包的哪个版本；装、升级、卸载都是事件；卸载后遗留的实体、持有、义务、账户按声明规则经转移协议处置；历史事实（已发生的事件、已判的案件）不改。
4. **冲突显式**：同一地点、同一郡的法典、同一槽位被两包覆盖时，报冲突或按用户在装载配置里写明的优先级，绝不静默合并、也不"后装的赢"。
5. **包与包相乘而不相知**：两包靠词汇表标签协作（N7 的盐税作用于 N8 的盐），不互相 import、不互为依赖。
6. **不增加静态提示**：包内容按需检索进动态尾部；无 LLM 时包的动作与模板照样出现在界面。
7. **一条命令自测**：schema、引用、不变量、推演、意图语料、卸载往返、规模预算一次跑完。

**不做**
- 不提供运行期热插拔：装卸只在载入存档时（或开局时）进行，注册完成后冻结（沿用 03 §3.2 第 5 条）。
- 不让第三方包加原语、加工具、加核心概念、加钩子模板枚举（但可写钩子的原语列表）、加实体模板、加求解器（11 §11.1 的"故意不通用化"对第三方同样成立）。
- 不提供在线包仓库与签名基础设施（发布渠道属部署决定，见 §12.12 待定事项）；本章只规定包格式与本地加载。
- **不让包改 core 的公式本身与内核语义**：货币定价公式（15 §15.3）、规范栈层序（05 §5.2.2）、传导的知情门控（05 §5.6）、阅读前置 `canRead`、协议步骤、原语校验不是扩展点。包能做的（附录 A §A.9 开放性宪章，缺省开放）：给**任何**派生挂修正项、给任何表加行（估值表、物种、配方、失真表、历法、基线、相互作用）、给任何族加词、给任何定义打受控补丁（追加前置、豁免、收窄范围）、声明钩子、在法典里写承认条目（法定货币、发行者、外地认证与婚姻、历法、单位）、声明新资源种类（含 `metal: none`）与拘禁制度。"一类新东西怎么算"是估值表或物种数据的一行，不再是公式分支；真需要新算法的写进 `pack doc` 的"接口缺口"。

## 12.2 包的形状

### 12.2.1 目录结构

第三方包与一方包同构，放在 `packs/<包id>/`（一方包）或用户的包目录 `<存档根>/packs/<包id>/`（第三方）。全部文件可选，除 `manifest.json`。

```
hantan-sect/                      包目录名 = 包 id
  manifest.json                   清单（必需）
  LICENSE                         许可全文（清单 license 字段对应）
  vocabulary.json                 词汇扩展：私有词、提议共享词、上位关系
  ontology/
    kinds.json                    新实体种类（必须挂到 01 §1.2 八类模板之一）
    holdings.json                 持有种类（01 §1.3 的全部必填字段）
    obligations.json              义务种类（01 §1.4；累计用闭式表达式）
    resources.json                资源种类（单位、商品类标签、源汇许可）
    statuses.json                 状态标记（叠加；精神 / 辅助 / 治疗类的 consent 声明，附录 A §A.15）
  entities/                       作者数据，与 world/ 同格式，经 L1 转换器变成持有与账户
    orgs.json  offices.json  people.json  items.json  buildings.json  nodes.json
  places/
    places.json  routes.json      新地点（必须挂到有法域的父节点）、路线边
    sensory.json                  感官素材（按季节 × 时段 × 天气）
  law/
    codes.json                    法典正文（罪名表、程序与程序成本、民事十类、冲突法、税表、契约效力、认可（含改币）、授权表）
    facts.json（在 ontology/）    扩展事实：对 core 种类声明带本包命名空间的可写字段（§12.2.3）
    bindings.json                 法典绑定到地点槽（§12.4.4）
    patches.json                  补丁：对既有法典条款、动作前置、持有不相容、义务条款范围的受控修正（05 §5.2.8）
  rules/
    derivations.json              派生规则（受限表达式 RX，§12.8.1）
    reactions.json                反应规则（谓词 DSL → 原语列表；声明优先级类与索引键）
    clock.json                    时钟规则（必须声明 closedForm 或 tolerance；可声明 paceable / major）
    tagging.json                  合法性标注规则（裁决第 3 步打 offense:* 候选标签，05 §5.2.3）
    modifiers.json  inferences.json  修正项、推断规则
    tables/*.json                 查表数据（速率、容量、价格基准、职位表、继承表……）
  autonomy/candidates.json        自治候选（05 §5.7.1；也可内联在动作的 satisfies 字段）
  supernatural/                   13 章：beings.json（生灵物种，六轴标签、真实与传说弱点、出处、敏感度、独有钩子）、
    rites.json  banes.json  cultures.json  rumor-channels.json（传闻通道 extend）
  lore/legends/*.json             传说条目（知情层：人们相信什么）
  actions/*.json                  动作（06 §6.4 格式；仪式带 rite 块）
  narration/
    verbs.json                    每个新动词的事件流模板（无 LLM 必需）
    dialogue/<文化>/<语域>/*.json  对话模板（06 §6.9.2）
    lore/*.md                     检索文档（进检索索引，不进静态提示）
  ui/
    groups.json                   动作分组、图标、快捷栏建议
  params.json                     安装参数（例：门派驻地挂在哪个郡）
  uninstall.json                  卸载处置规则（§12.5.4）
  migrations/
    1.0.0-to-1.1.0.json           升级迁移（数据形式）
  tests/
    probes/*.json                 包自带推演题（夹具 + 扰动 + 断言）
    intents/*.json                包自带意图语料
    fixtures/                     夹具世界片段（可选，缺省用标准夹具世界）
```

**没有 `*.mjs`**。第三方包默认是"数据包"（trust = data）：只有 JSON、Markdown 与受限表达式。允许代码的"原生包"（trust = native）只给一方包与用户本机显式放行的包，不在开放契约的保证范围内（取舍见 §12.8）。

### 12.2.2 清单 manifest.json

```json
{
  "format": 1,
  "id": "hantan",
  "name": "寒潭剑宗",
  "version": "1.0.0",
  "summary": "西陲一处寒潭边的剑修门派：驻地、五门功法、门规、掌门与弟子。",
  "authors": [{"name": "某作者", "contact": "可选"}],
  "license": "MIT",
  "contentLicense": "CC-BY-4.0",
  "homepage": "可选",

  "engine": ">=1.0.0 <2.0.0",
  "contract": "^1.0.0",
  "vocabulary": "^1.0.0",

  "trust": "data",
  "dependencies": {},
  "optionalDependencies": {},
  "suggests": ["nanling-code"],
  "conflicts": [],
  "overrides": [],

  "provides": {
    "kinds": [], "holdings": ["disciple_of"], "obligations": ["tuition"],
    "resources": [], "statuses": ["hantan:frost_qi"], "facts": [],
    "places": true, "entities": true, "law": false,
    "rules": ["derivations", "reactions", "clock", "tagging"],
    "autonomy": false, "supernatural": false, "lore": true,
    "actions": true, "narration": true, "ui": true
  },
  "slots": [
    {"slot": "place.seat", "target": "{{params.seatParent}}", "mode": "claim"}
  ],
  "params": "params.json",
  "uninstall": "uninstall.json",
  "prompt": {"staticTokens": 0},
  "budgets": {"entitiesAtInstall": 60, "clockRules": 3, "maxProposalsPerEvent": 4}
}
```

| 字段 | 含义 | 校验 |
|---|---|---|
| format | 清单格式版本 | 加载器不认识即拒绝，报"请升级引擎或改用 format N" |
| id | 包 id，即命名空间 | `[a-z][a-z0-9-]{1,31}`；不得为保留字 `core`、`world`、`engine`、`src`、`sink`、`player`；全局唯一 |
| version | 语义化版本 | 存档锁记录；升级迁移按它找迁移文件 |
| license / contentLicense | 代码与内容许可（SPDX 标识） | 必填；加载器只展示不判定；缺失即错误 |
| engine | 引擎版本范围 | 不满足即拒绝 |
| contract | 开放契约版本（八概念、原语、规则四形状、钩子模板、开放性宪章、扩展点 schema 的版本） | 主版本不同即拒绝；次版本更高报"需要新引擎" |
| vocabulary | L1 词汇表版本范围 | 主版本变更时引擎随附 `sameAs` 映射，加载器自动改名并提示 |
| trust | data / native | 第三方缺省 data；native 需用户在装载配置里逐包放行 |
| tier | content / rules | 包档（§12.8.6）：content 包不声明任何规则形状，自测只跑内容类检查；声明了规则即 rules |
| dependencies | 硬依赖 `{id: 范围}` | 缺失或版本不符即拒绝；被依赖的包不能先卸 |
| optionalDependencies | 软依赖 | 缺失时引用该包的内容按 `when` 守卫跳过，不报错 |
| suggests | 推荐同装 | 只提示 |
| conflicts | 声明互斥的包 | 同装即拒绝 |
| overrides | 本包有意覆盖的包（必须同时在 dependencies 里） | 让槽位冲突变成显式分层（§12.4.4） |
| provides | 声明本包会注册什么。**键集唯一定义**：`kinds`、`holdings`、`obligations`、`resources`、`statuses`、`facts`（扩展事实）各为 id 列表；`places`、`entities`、`law`、`autonomy`、`supernatural`、`lore`、`actions`、`narration`、`ui` 各为布尔；`rules` 为子集列表，取值 `derivations` / `reactions` / `clock` / `tagging` / `modifiers` / `inferences` / `tables`。03 §3.3 的示例按此书写 | 与实际文件比对，多出或缺少都报错（防止"顺手"注册） |
| slots | 本包要占用或覆盖的槽位 | §12.4.4 |
| params | 安装参数 schema | §12.2.5 |
| prompt.staticTokens | 静态提示增量 | 必须为 0（08 §8.3） |
| budgets | 包自报的资源上限 | 超出由加载器与运行期守卫拦截（§12.8.3） |

### 12.2.3 能声明什么：扩展点

扩展点由**开放性宪章**决定（附录 A §A.9）：凡是表、族、派生、定义、协议后续，**缺省开放**；下表只是 core 预置文件与 schema 的索引，任何声明 `extensible`（缺省）的表、族、派生、定义自动成为扩展点，不必列入本表。每个文件有 schema、合并语义与静态检查。**合并语义只有四种**（补丁文件按 extend 合并，作用方式见附录 A §A.9 第 4 条）：

- **add**：只能新增本命名空间的 id；与已有 id 重名即错误。
- **edge**：新增一条至少一端是本包实体的关系（持有、路线、初始关系基线、地点父子）；不能改另一端的任何事实。
- **slot**：占用或覆盖一个声明为"可覆盖"的槽位（地点的法典、驻地锚点、聚落的治理组织……）；冲突按 §12.4.4 处理。
- **extend**：向开放族追加成员（词汇族、对话模板、动词模板、检索文档）；不能删改已有成员。

| 扩展点 | 文件 | 合并 | 必须声明 | 加载期静态检查 |
|---|---|---|---|---|
| 实体种类 | ontology/kinds.json | add | 所属模板（agent/collective/thing/population/place/office/instrument/interim 之一）、可写事实白名单与范围 | 模板存在；事实字段不在黑名单（I10） |
| 实体（作者数据） | entities/*.json | add | 与 world/ 同格式；经 L1 转换器变成持有与账户 | 引用完整；派生字段不出现；初始账户 ≤ 合理性表（§12.8.3） |
| 地点 | places/places.json、routes.json | add + edge | 父节点、坐标、地形、路线边（方位、距离、通行方式、季节封闭规则、可选 `passage` 条件——开放 RX，可组合 core 的 `passage:*` 条件词与 `window(id)`，01 §1.5） | I9：父链能解析法域；坐标不与他包驻地相撞（§12.4.4）；`passage` 的 RX 通过 P7 |
| 持有种类 | ontology/holdings.json | add | 01 §1.3 全部字段（条目键 `holdingKind`）：holderKinds、subjectKinds、exclusive、sum、grantedBy、handover（gone / vacated / defected 三项必填；在途 / 失能 / 受限不是列）、onSubjectGone、`hooks`（其余协议后续 `{on, when, do}`，附录 A §A.4）、derives（authority、称呼、额度、schedule、服务、conduction 任一项；**不含 pins**）、visibility；可选 incompatibleWith、`pins`（独立字段）、`contest`、`patchable` | I5：钩子模板只取附录 A §A.4 的八个值（gone 不得为 stay）、标的侧四个；钩子的原语列表经 P8 幅度校验 |
| 义务种类 | ontology/obligations.json | add | 条目键 `obligationKind`；日程（`anchor: day | month | …` 按历法锚到期，累计闭式按条款 `per: day | anchor`，口径见附录 A §A.15）、清偿原语、不足、违约（读 `grace()`）、`onDebtorGone`/`onCreditorGone`（附录 A §A.4，**没有 handover 键**）、可选 `hooks`、条款范围（利率区间、期限上限 `maxDays`）、可选开放债权人、可选 `exclusive{on, among, policy}`（01 §1.4：同标的互斥，按上位词匹配）、`patchable` | I7：违约规则必须读债务人状态；累计必须闭式，输入为 `days` 或 `anchorsBetween` 的锚计数（I14）；`among` 的词在词汇表（I18） |
| **扩展事实** | ontology/facts.json | add | 对 core 种类（person / creature / org / building / item / settlement…）声明带本包命名空间的可写事实字段：`{kind, field: "<包id>:<名>", type, range, default, writableBy: [本包规则 / 动作], uninstall: dormant / fallback / drop}`；修正项、候选、谓词经 `fact(x, '<包id>:<名>')` 读取 | 字段名带本包前缀；不在派生黑名单（I10）；只有本包与 core 的 fact.set 原语可写（他包只读）；卸载按声明处置 |
| 资源种类 | ontology/resources.json | add | 单位、商品类标签（`goods:*`）、货币事实 `money`（含 `metal: none` 与 `backedBy`，15 §15.3）、保质与损耗（`lots: true` 时声明保质曲线、批次合并键，01 §1.6）、可用源汇 | 源汇只能用 01 §1.6 的源汇族；`src:mint` / `src:issue` 的使用者由法典认可条目 `issuers` 决定，包只能在自己的法典里声明；`src:craft` 必须指向配方 |
| **配方** | rules/tables/recipes.json | add | `{id, inputs, tools, workplace, skill, laborMinutes, outputs（resource、qty RX、quality RX、lot 元数据）, byproducts, lossRate}`（01 §1.6）；被制作动作与工坊生产时钟规则引用 | 产出资源在词汇表；产出量 RX 只读投入与技能；制造守恒对可审计（I1）；产出为 `goods:coin` 的配方在 P8 标 `mintLike`，供罪名谓词识别 |
| **失真表** | rules/distortion.json | extend | `{id, when: RX（讲者性格立场、通道、源类型、沟通度 canCommunicate）, op: replace_detail / omit_subject / scale_quantity / drop_clause / bias_toward, p: RX}`（05 §5.4） | op 在枚举内；`p` 经槽 `social:distortion`；不得读真相以外的随机 |
| 状态标记 | ontology/statuses.json | add | 叠加规则、持续、强度、是否精神 / 辅助 / 治疗类（读同意） | 精神、辅助、治疗类必须声明 `consent: {scope, onRefusal: contest / abort}`（附录 A §A.15；缺省 contest），不得声明"拒绝施加" |

**兜底标签实体的反应**：用户 2026-10-15 的"尊重玩家想象力"原则要求任何创意都能留下"带标签的实体"作持久痕迹。包可以对这类实体的标签声明反应规则（例如寒潭剑宗对 `mark:frost`、`mark:sword_carving` 的反应：弟子注意到崖壁剑痕 → 立场与传闻），这是让第三方内容也回应玩家即兴行为的标准入口，不需要任何专门接口。

### 12.2.4 不能做什么

| 禁止 | 由什么保证 | 被拦下时的报错 |
|---|---|---|
| 直接写状态 | 包没有写入口；数据包无代码；规则只返回原语提案（I3） | —（结构上不可能） |
| import 内核以外模块 | 数据包无代码；原生包的 import 图测试只允许 `@wildfield/pack-api`（L0/L1 只读视图与提案 API）（I19） | E-IMPORT |
| 改其他包或 core 的数据 | 合并语义只有 add/edge/slot/extend；对他人 id 的任何"同 id 声明"按重名报错；影响他人定义只能经受控补丁（追加前置、豁免、收窄、修正项，附录 A §A.9 第 4 条），补丁不改数据只改选中结果 | E-ID-DUP / E-EDGE-FOREIGN / E-PATCH |
| 新增效果原语、工具、核心概念、钩子模板枚举、实体模板、求解器 | schema 枚举封闭（其余族、表、派生、定义缺省开放，附录 A §A.9） | E-SCHEMA（"可选值为……"） |
| 增加静态提示 | staticTokens ≠ 0 即拒绝 | E-BUDGET-STATIC |
| 私造同义词 | 词汇冲突检查 | E-VOCAB-SYN |
| 在运行期注册规则 | 注册表冻结 | —（结构上不可能） |
| 凭空造钱物 | 初始存量只能经 `src:genesis`（作者数据转换）且受合理性表约束；运行期只能用已有源汇族 | E-INV-I1 |
| 幅度比 core 上限更大 | 动作与功法的数值不得超过 core 上限表对应阶段的值（可更严，不可更宽）；物品与装备按模板声明的物品阶 `stage` 对表，K2 倍率同受约束，包不能声明超过 core 最高阶的 stage（06 §6.7） | E-INV-I20 |
| 删改他人动作的既有前置或 outcomes；拒绝他人提案 | 合法性标注只能打标签；补丁只能**追加**前置并须带世界内原因（目标 `patchable` 可拒绝） | E-SCHEMA / E-PATCH |
| 使用随机数 | RX 无随机函数；只能用内核 `roll(键)`，键自动含包 id、对象、日期 | E-RX |
| 访问文件、网络、时钟 | RX 无此类函数；原生包运行在无文件/网络权限的隔离环境 | E-RX / E-NATIVE |

## 12.3 命名空间、id 与引用

### 12.3.1 两种 id

- **定义 id**：包里声明的种类、模板、规则、动作、词汇、法典、表——"世界里可以有什么"。
- **实例 id**：世界里有永久编号的实体——"世界里有什么"（01 §1.2，永不复用）。

**规范形式**：`<命名空间>:<本地 id>`。

- core（world/ 数据与 L1 本体）的命名空间是 `core`，书写时可省略：`npc_hw_linsui` ≡ `core:npc_hw_linsui`。现有全部 id 不改。
- 一方包注册进 L1 词汇表的种类与动词（loan、holds_office、offense:breach……）属于 core 词汇，不带前缀；一方包的私有内容带自己的命名空间。
- 第三方包的一切定义与实例都带命名空间：`hantan:skill_frost_01`、`hantan:org_sect`、`hantan:npc_master`。
- 本地 id 沿用现有前缀约定（npc_/loc_/bld_/item_/org_/office_/node_/skill_/law_……），前缀决定实体种类的初判，命名空间决定归属。
- 包内书写时可省略本包前缀：在 hantan 包内写 `skill_frost_01`，加载器按"本包 → core"顺序解析；**不会**去别的包里找。

**实例 id 的代次**：卸载后再装同一个包，作者数据里的同一个人会得到新实例 id `hantan:npc_master~2`（代次后缀），因为旧 id 已成墓碑（§12.5.4），永不复用。定义 id 不加代次：重装后休眠的功法熟练度可以恢复（§12.5.4）。

### 12.3.2 引用其他包的内容

| 情形 | 写法 | 要求 |
|---|---|---|
| 引用 core | `npc_hw_linsui` 或 `core:npc_hw_linsui` | 无 |
| 引用硬依赖包 | `luquan:item_salt_warrant` | 该包在 dependencies 里，版本范围满足 |
| 引用软依赖包 | 同上，但所在条目带 `"when": "installed(luquan)"` | 包在 optionalDependencies 里；未装时整条跳过并记 info |
| 想作用于"任何包的某类东西" | **不引用 id，用词汇标签**：`commodity: goods:salt`、`offense:smuggling`、`kind: org/sect` | 标签在 core 或共享词汇里 |
| 未声明依赖就引用别包 id | — | E-REF-UNDECLARED："hantan 引用了 qingfeng:org_sect，但 qingfeng 不在 dependencies/optionalDependencies 里；若只想作用于所有门派，请改用标签 org/sect" |

第三条是协作的主路：**包之间靠词汇相乘，不靠 id 相知**（03 §3.2 第 2、3 条）。只有"故意基于另一个包做的扩展包"（例如"寒潭剑宗·外门"）才写硬依赖。

### 12.3.3 词汇表扩展与冲突

词汇表（03 §3.2 第 3 条）是包之间唯一的契约。开放后分三区：

| 区 | 谁写 | 形式 | 用途 |
|---|---|---|---|
| core 词汇 | L1 数据（含一方包注册的） | 无前缀：`offense:smuggling`、`goods:salt`、`harm:injury`、`org/sect` | 跨包协作的公共语言 |
| 共享扩展 | 任一包"提议"，加载后进入公共区 | 无前缀，但必须挂在已有族下：`goods:brine`（上位 goods）、`contract:redeemable_sale`（上位 contract） | core 没有、但多个包都需要的词 |
| 私有词 | 包自己 | 带前缀：`hantan:frost_qi`、`hantan:sect_rule_breach` | 只本包使用；别的包只能通过上位词感知 |

**词条格式**：

```json
{
  "term": "offense:salt_smuggling",
  "scope": "shared",
  "broader": "offense:smuggling",
  "label": "私盐",
  "aliases": ["贩私盐", "无引运盐"],
  "definition": "未持有效盐引运输或出售盐类商品",
  "distinctFrom": []
}
```

**规则**：
1. **上位词必填**（私有词也要）。法典、反应规则、价格投影按"本词 → 上位词 → 更上位"回退匹配：南岭法典没有 `offense:salt_smuggling` 条目，就按 `offense:smuggling` 判；没有任何法典认识的私有词，至少有一个 core 上位词可被反应。这保证第三方新词不会"落地无声"。
2. **同义词禁止——只对词汇条目**：`vocabulary.json` 里的词条（动词、标签、商品类、罪名、需求、状态族、`org/*` 种类标签等"用来匹配规则的词"）的 label 或 alias 与已有词的 label/alias 完全相同 → E-VOCAB-SYN（"'私盐' 已是 core:offense:smuggling 的别名；请直接用该词，或给出不同的 label 并在 distinctFrom 里写明区别"）；字面高度相近（二元切词 Jaccard ≥ 0.6）→ 警告，需在 `distinctFrom` 里列出并说明区别才放行。**定义的显示名不受此限**：技能、法术、功法、境界、物品模板、动作、组织、人物这些"有 id 的定义"可以同名（`hantan:skill_frost_01` 与 `qingfeng:skill_frost_01` 都叫"映雪"，`xiuxian:realm_jindan` 与 `tianlu:realm_jindan` 都叫"金丹"），界面显示带包名消歧，LLM 路由遇同名返回候选（06 §6.10.4）；动作的 `llm.synonyms` 重叠只报 W-SYNONYM。这是现状"两套元素词表、七份态度账"病根的闸门，同时不把内容作者的命名权收走。
3. **共享词的冲突**：两包提议同一个共享词——定义一致（上位词、label、definition 归一后哈希相同）则合并为一个词，声明者列表记两包；不一致 → E-VOCAB-CONFLICT，两包不能同装，除非其一改用私有词。不存在"谁先加载谁的定义"。
4. **不能改已有词**：不能给 core 词加 alias、改上位、改定义；需要时向引擎提词汇表修订（次版本号递增）。
5. **词汇表版本**：core 词汇表有语义化版本。加词 = 次版本；改名/合并/删除 = 主版本，随附 `sameAs` 映射，加载器把旧词自动改写并提示作者更新。存档事件里的旧词由同一映射在归约时解析（与 10 §10.7 的事件版本适配同理）。

## 12.4 加载

### 12.4.1 校验流水线

加载器（L4 的"存档读写与迁移"旁，新增 `pack-loader`，只调用 L1 注册表的公开入口）按阶段执行。**同一阶段收集全部错误后再停**；后一阶段依赖前一阶段的结果，前一阶段有错误就不进入后一阶段（避免连锁误报）。

| 阶段 | 做什么 | 典型错误码 |
|---|---|---|
| P0 发现 | 读装载配置（`packs.profile.json`：装哪些包、哪些放行 native、槽位裁决、安装参数），读各包 manifest | E-MANIFEST |
| P1 版本 | engine / contract / vocabulary 范围比对 | E-VERSION |
| P2 依赖 | 解析依赖图，版本求解（取满足全部范围的最高已有版本），检测缺失、循环、conflicts | E-DEP-MISSING / E-DEP-CYCLE / E-DEP-CONFLICT |
| P3 schema | 每个文件按扩展点 JSON Schema 校验；provides 与实际文件一致 | E-SCHEMA / E-PROVIDES |
| P4 命名 | 限定全部 id；本包内重名、与已加载内容重名、保留前缀 | E-ID-DUP / E-ID-RESERVED |
| P5 词汇 | 合并词汇：上位词存在、同义词、共享词冲突、私有词前缀 | E-VOCAB-* |
| P6 引用 | 全部引用解析到 core、本包或已声明依赖；软依赖守卫；参数代入后再解析 | E-REF-* |
| P7 表达式 | RX 编译：名字与类型、调用的函数在白名单、最坏步数 ≤ 预算、无随机 | E-RX-* |
| P8 静态不变量与内容纪律 | I5 钩子声明完整（handover 三项必填 + 标的侧，`do` 取模板或经幅度校验的原语列表）；I7 违约读债务人状态；I9 新地点可解析法域；I10 黑名单（按记录类别）；I14 时钟规则有 closedForm/tolerance；I18 词汇封闭；I20 每个原语幅度有上限来源且不宽于 core 上限表；I1 初始存量只从 `src:genesis` 且在合理性表内，`src:*` 只在声明了该源的规则中引用且有每日预算；I19 原生包 import 图；I24 规范补丁在目标 `patchable` 内；I25 自治候选与推断规则的 RX 只读主观视图；神祇不作 vital / commands / seals 标的；**E-SOURCE**：生灵、神职、传说、仪式条目的 `sources` 非空；**E-SENSITIVE**：名称与别名命中排除名单（`orthodox_worship` 档）或仪式名命中真实宗教仪式即拒载，`sensitivity.reviewed=false` 的条目不得进入发布包（13 §13.1）；**E-DEITY-CAP**：`ancient_attested` 名称出现在非 `kind:"historical"` 的神灵条目之外即拒载，现实古神条目须带 `interactionCap ∈ {talk, gift}` 与 `sources`（13 §13.1、§13.1A） | E-INV-I1 … E-INV-I32、E-SOURCE、E-SENSITIVE、E-DEITY-CAP、E-PATCH |
| P9 可玩性 | 每个新动词有事件流模板；每个新请求种类有对话答复模板；每个动作有叙述模板且槽位一致；每个动作至少一个可见性入口（对象菜单/此处可做/快捷） | E-PLAY-* |
| P10 冲突与重复 | 槽位冲突、持有约束冲突（两包让不同持有人 `controls` 同一 core 地点 → 互斥；`owns` 份额之和 > 1.0 → 份额，§12.5 第 5 条）、空间冲突（驻地坐标距离 < 阈）、动作同义词冲突；**生灵与神职的重复检查**（13 §13.9）：与同原型族、同地区已有条目的机制签名相似度、特征距离、无独有钩子 → E-CONFLICT-DUPLICATE（附"并入 X 作为别名"建议）；活动实体配额与神祇上限 → E-QUOTA（列出可合并或移往他省的候选，只针对无差异的堆叠） | E-CONFLICT-* / E-QUOTA / W-SYNONYM |
| P11 预算 | staticTokens = 0；每个动作的 LLM 可见文本 ≤ 60 token；每篇检索文档分块 ≤ 300 token；装载实体数、时钟规则数 ≤ budgets 与全局上限；**每事件最坏谓词求值数 ≤ 预算**（07 §7.5 成本模型：无守卫的反应与罪名条目限额） | E-BUDGET-* |
| P12 存档对照 | 与存档 `packs.lock` 比对：新装、升级（需迁移文件）、缺失（需卸载确认）、内容哈希不符 | E-SAVE-* |
| P13 注册与冻结 | 按加载顺序向 L1 注册；生成合并后的动作目录、检索索引、事件模板表；冻结 | —（前面已拦） |

P0–P11 不需要存档，作者工具（§12.7）在作者本机跑的就是这一段；P12–P13 在玩家载入存档时跑。

### 12.4.2 报错格式

每条诊断同时有机器可读的 JSON 与给人看的文本；界面与作者工具都用同一结构。

```json
{
  "code": "E-INV-I9",
  "severity": "error",
  "stage": "P8",
  "pack": "hantan@1.0.0",
  "file": "places/places.json",
  "pointer": "/0/parent",
  "line": 7,
  "rule": "I9 法域可解析：每个地点能沿包含树解析出法域",
  "message": "地点 hantan:loc_seat 的父节点 core:loc_hantan_valley 不存在，法域无法解析",
  "fix": [
    "把 parent 改成已存在的地点；`pack find place 寒潭` 列出候选",
    "或改为安装参数 {{params.seatParent}}，让玩家在安装时选择所在郡"
  ],
  "related": []
}
```

文本形态：

```
✗ E-INV-I9  hantan@1.0.0  places/places.json:7  /0/parent
  违反：I9 法域可解析
  地点 hantan:loc_seat 的父节点 core:loc_hantan_valley 不存在，法域无法解析
  修法：① 改成已存在的地点（pack find place 寒潭）② 或用安装参数 {{params.seatParent}}
```

**写诊断的规矩**：
- 必有 file + pointer（JSON 指针）+ 行号；跨文件的错误在 related 里列出另一处。
- 必有 rule：违反的是哪条不变量（I1–I32，附录 A §A.12）、哪个扩展点 schema 的哪个字段、哪条内容纪律（E-SOURCE / E-SENSITIVE / E-QUOTA）、还是哪条加载规则；用编号和一句话。
- 必有 fix：至少一条可直接照做的修法；能自动修的（加前缀、改名）给出 `pack fix` 可执行的补丁。
- 枚举类错误列出全部合法值（"handover.gone 可选：vacate / succeed / estate / close / revert / retain_disputed（stay 与 suspend 不可用于 gone）"）。
- 拼写近似给建议（"未知动词 'exel'，你是不是想写 'expel'"）。
- 严重度三级：error 拒绝加载；warning 加载但在装载报告里列出（`--strict` 视为 error）；info 只记录（软依赖跳过、上位词回退）。
- 玩家在载入存档时看到的是简化版："寒潭剑宗 1.0.0 未能加载：驻地所在的地点不存在。此包未启用，存档其余部分正常。查看详情"——不让一个坏包拖垮整局（§12.8.4）。

### 12.4.3 加载顺序与依赖解析

1. **core 最先**：L1 本体 + world/ 数据 + 一方包（一方包之间按其依赖图）。
2. **第三方包按依赖拓扑序**；同层无依赖关系的包按包 id 字典序。**加载顺序不受文件系统顺序、装载配置里的书写顺序影响**——顺序必须是确定的，回放才一致。
3. 由于合并语义只有 add/edge/slot/extend，**顺序不改变结果**：add 与 extend 可交换；edge 只触及本包一端；slot 的裁决只看声明与配置，不看谁先加载。顺序只影响注册时引用能否解析（依赖先于依赖者）。
4. 版本求解：每个包只装一个版本；求不出满足全部范围的版本即 E-DEP-UNSAT，列出相互冲突的范围与要求它们的包。
5. 依赖循环即错误（包之间的"互相需要"应该改为共享词汇）。

### 12.4.4 槽位、冲突与优先级

**槽位**是 core 或包显式声明为"可被覆盖或占用"的一个值，每个槽位同一时刻只有一个赢家。初始槽位目录（L1 数据，可随契约次版本扩充）：

| 槽位 | 挂在哪 | 含义 | 模式 |
|---|---|---|---|
| place.lawCode | 地点 | 该地点子树适用的地方法典 = 规范栈"次级属地层"中地点子树类条目的单一赢家（05 §5.2.2）；只覆盖主权法典中未 `reserved` 的条款，未写的部分 inherit | override |
| place.layout | 地点 | 该地点的分区布局（缺省由确定性布局规则生成） | override |
| place.seat | 地点 | 某组织在此设驻地（独占一块地） | claim |
| settlement.administrator | 聚落 | 治理组织（administers 的持有人） | override（**仅开局装**或该聚落当前无存活 `administers` 持有时可占；中途注入对已有治理组织的聚落按 J3 拒绝——夺取要走世界内过程） |
| place.sensory | 地点 | 感官素材整体替换（追加用 extend，不占槽） | override |
| org.charter | 包自己的组织 | 允许依赖包改章程 | override（仅 overrides 声明的依赖包） |
| place.culture | 地点 | 该地点子树的文化圈归属（13 §13.2；缺省继承父节点） | override |

**冲突判定与裁决**（按顺序）：

1. 只有一个包声明某槽位 → 该包赢。
2. 多个包声明同一槽位：
   - 若其中包 B 在清单 `overrides` 里列了包 A（且 A 在 B 的 dependencies 里）→ B 赢。这是"有意分层"：B 是基于 A 的修订包。
   - 否则查装载配置 `packs.profile.json` 的 `resolve`：`{"place.lawCode@core:county_xichui_longqu": "nanling-code"}`，有则按配置。
   - 都没有 → **E-CONFLICT-SLOT，两包都不注册该槽位上的内容**，并报：
     ```
     ✗ E-CONFLICT-SLOT  place.lawCode @ core:county_xichui_longqu
       nanling-code@1.0.0（law/bindings.json:3）与 lingnan-custom@0.4.0（law/bindings.json:5）都为该郡绑定法典
       违反：槽位单一赢家；不静默合并
       修法：① 在 packs.profile.json 的 resolve 里写明用哪一部 ② 卸掉其一 ③ 请其中一个包的作者把另一包列为依赖并在 overrides 中声明
     ```
3. **层级不是冲突**：一包给郡绑定法典、另一包给该郡下某镇绑定法典，按"最近绑定"派生（更具体的赢）；装载报告记 info，说明哪些地点由谁的法典管。
4. **claim 模式的空间冲突**：两包驻地占同一 place.seat，或新地点坐标距离 < 阈值 → E-CONFLICT-SEAT。包可在 params 里声明 `"seat": {"relocate": "nearest-free-in-county"}`，冲突时加载器按确定性规则（同郡内按距离与 id 排序的第一个空闲候选）迁移，并在装载报告里写"寒潭剑宗驻地因与 X 冲突迁至 Y"；未声明可迁移则拒绝。
5. **持有约束冲突**：两包都让各自的组织 `controls` 同一 core 地点 → 违反 I8 **互斥**（`controls` 是 exclusive 持有）→ E-CONFLICT-EXCLUSIVE；两包都让各自的组织 `owns` 同一 core 地点或建筑 → `owns` 不互斥（共有即多条份额边，01 §1.3），冲突是 I8 的**份额总和**：两包各声明份额 1.0 → 总和 > 1.0 → E-CONFLICT-SHARE（裁决同第 2 条；两包份额之和 ≤ 1.0 时合法共有，不是冲突）。
6. **动作同义词冲突**：两包的动作共享同一同义词 → 警告；运行期路由（06 §6.8）遇到同分时返回候选而不猜。
7. **同一判定的唯一赢家**（附录 A §A.9 `decides`）：两包的反应规则、动作、推断规则或表行声明了同一 `decides` 判定 id（两家的"出千识破"、两张诊断表对同一症状的行）→ 按第 2 条裁决（overrides → `resolve` → E-CONFLICT-DECIDES，两包该项都不注册并报出位置与修法）；表声明了 `key` 字段时主键重复同样报冲突而不并集。未声明 `decides` 的同类规则各自生效，这是缺省——只有作者自认"这是一个只能有一个答案的判定"时才声明。

**绝不做**：字段级合并两部法典、"后加载覆盖先加载"、按包体积或安装时间排优先级。

### 12.4.5 两包协作：词汇相乘

协作的标准做法，不需要任何一方知道另一方存在：

| A 包提供 | B 包使用 | 连接点 |
|---|---|---|
| 资源种类带商品类标签 `commodity: goods:salt` | 法典税表按 `goods:salt` 征税 | 税的反应规则（治理包，core）读交易事件的商品类标签与交易地法典 |
| 动作打 `offense:salt_smuggling`（上位 `offense:smuggling`） | 法典罪名表的 `offense:smuggling` 条目声明 `matches: offense:smuggling`（core 缺省法典数据缺省如此） | 该条目的谓词因 `matches` 对下位标签为真（05 §5.2.3）；没有该族的政体用补丁 `append(clause)` 追加条目 |
| 组织种类 `org/sect` | 另一门派包的外交反应"对所有 org/sect" | 反应规则的参与者谓词按种类标签 |
| 事件 `harm:injury` | 医疗包 | 03 §3.2 第 2 条 |
| 兜底标签实体 `mark:*` | 任何包的反应 | §12.2.3 |

N7 × N8 的完整链见 §12.10.3。**唯一需要协调的是词汇**：如果 core 没有某个商品类或罪名，两个作者各自提议共享词时要用同一个词——为此 core 词汇表要预置足够宽的族（goods:*、offense:*、contract:*、org/*、mark:*），作者工具 `pack vocab search 盐` 先查再造。

## 12.5 存档兼容

### 12.5.1 存档里记什么

- **`packs.lock`**（存档根，随快照写）：`[{id, version, contentHash, trust, params, installedAt(事件编号), generation}]` + 词汇表版本 + 槽位裁决结果。
- **包仓**：`<存档根>/packs/.store/<id>@<version>/`：存档实际使用过的每个版本的只读副本（按 contentHash 去重）。理由：回放从最近快照开始，快照之后的事件需要当时版本的规则；升级时强制打快照（§12.5.3），所以只需保留"最新快照之后用到的版本"，旧的可清理。
- **来源事实**：包产生的每个实例实体带不可变事实 `origin: {pack, version, generation}`；每个持有、义务、账户由其创建事件的规则 id（`hantan:recruit`）可追溯；事件的起因链本来就有。
- **墓碑**：卸载后的实例保留墓碑记录 `{id, kind, name, origin, removedAt, removedBy: 事件编号}`，供历史渲染（"曾任寒潭剑宗掌门"）。

### 12.5.2 安装：开局装与向已有存档注入

- **开局装**：与 world/ 一样经作者数据转换器物化，起因为开局事件。
- **中途装（向已存在的世界注入）**：一个父事件 `pack.install{pack, version, contentHash, params, framing}` + 子事件（create 实体、holding.open、初始账户 transfer、知情种子）。整批是**一个事务**：任何一步失败或末尾断言失败，整体回滚，存档不变。

**时机**（只有一个）：载入存档流程中、玩家在装载界面确认之后、第一个回合之前，即 §12.5.5 所说的**纪元边界**。顺序：读快照 → 把各地区按自己的层级补算到当前时刻（07 §7.3 第 4 条）→ 写 `pack.install` 事件 → 重建注册表并冻结 → 开始回合。不允许在回合中、推进中、离屏中注入；规则与动作不能产生 `pack.install`。安装事件的时刻 = 当前世界时间，**不回填历史**：事件日志时间单调（I13），包不能往过去插事件。

**一致性规则**（P12 之外，注入时对**当前状态**而非原始 world/ 数据再检一遍）：

| # | 规则 | 违反时 |
|---|---|---|
| J1 锚点存活 | 包地点的父节点、包实体引用的 core 实体在当前状态中存在且未消失（未成墓碑、未 gone） | E-INJECT-ANCHOR：列出已消失的锚点；可改安装参数重选 |
| J2 占用以当前为准 | 驻地槽、互斥持有、空间冲突按当前持有判断：core 地点此刻被首领 `controls`、被玩家 `owns`、已有建筑占同一坐标，都算占用 | E-INJECT-OCCUPIED；声明了 relocate 的按确定性规则迁移 |
| J3 不夺活持有 | 注入只能占**空**槽位或建立新边；不得替换当前存活的持有（例：不能让包组织直接 `administers` 一个已有治理组织的聚落——`settlement.administrator` 槽在中途注入时只对无存活 administers 的聚落开放，§12.4.4）。需要夺取的，包应提供动作，由世界内过程完成 | E-INJECT-LIVEHOLDING |
| J4 规范从现在起生效 | 法典绑定等规范槽位从安装时刻起生效；之前发生的行为按当时的法典（罪刑以行为时法为准，§12.5.4） | — |
| J5 按层级物化 | 目标地区在智能层/规则层 → 全部实体当场物化；在统计层 → 只物化纲要：地点、组织、职位、被职位与义务钉住的人物（07 §7.2 的 pinned），其余人物为名册种子，首次到达时按种子物化 | — |
| J6 守恒 | 落在包**自有地点**的人与物：初始存量从 `src:genesis` 流入，受合理性表约束。落在**已有聚落**的人（例：包往白石镇加一位剑馆教头）：若该聚落有统计层聚合账户，从聚合人口与聚合财富中**借出**（07 §7.3 第 5 条），总量不变；若该聚落已全量物化、没有聚合可借，从 `src:genesis` 流入并标 `immigrant`（作为新迁入者，下一条决定叙述）。**累计上限**：同一包 id 在同一存档的 `src:genesis` 累计注入量按资源记在 packs.lock 历史段，上限 = 合理性表上限 × 1；卸载时转入 `sink:pack_removed` 的 core 等价量按资源记为"已回收"，重装（generation ≥ 2）的注入只能在 `上限 − 累计 + 已回收` 的余额内进行，不足部分从聚合借出或不注入（人物以更少的随身财富登场）。反复装卸不能扩张世界货币 | E-INJECT-BUDGET（超合理性表或超累计余额） |
| J7 年龄与日期相对化 | 作者数据中的 `age`、"三年前入门"之类相对量按当前世界日期换算成出生日期等不可变事实；`foundedYear` 等写成事实，不生成事件 | — |
| J8 知情不伪造 | 不生成任何"过去的见证"。按包声明的 `knownBy`，安装事件为相应人群生成 authored 知情种子，来源记为本次 `pack.install` 事件（与开局作者数据同类，I12 认可的第三种来源） | — |
| J9 叙述框定 | `framing` 二选一：`always-there`（"本来就在"）或 `newcomers`（"新近迁来/新近建成"）。规则：若包的任一地点位于玩家**已亲历过**的地点子树内（玩家知情集合里有该子树的在场事件），强制 `newcomers`——发一条公开事件 `settled_in`，见证由在场派生，进入传闻；否则缺省 `always-there`。这样不会出现"我在这郡住了三年，从没见过这座剑宗"的矛盾 | — |
| J10 立场只给基线 | 与已有实体的初始关系只作为立场基线（05 §5.6 的基线项），不生成回溯的 impress 事件 | — |
| J11 末尾断言 | I1–I32 全量断言（含 I9 新地点法域、I8 互斥、I15 账户唯一） | 整体回滚 |

- 开局装可视为"在第 0 个纪元边界注入"，同一套规则全部自然满足。

### 12.5.3 升级

- 包新版本附 `migrations/<旧>-to-<新>.json`（可链式）。迁移是数据：

```json
{
  "from": "1.0.0", "to": "1.1.0",
  "rename": {"hantan:skill_frost_03": "hantan:skill_frost_step"},
  "transform": [
    {"select": "entities(kind=hantan:disciple_rank)", "field": "rank", "rx": "rank + 1"}
  ],
  "remove": [{"id": "hantan:status_old_qi", "uninstall": "dormant"}],
  "vocabulary": {"sameAs": {"hantan:cold_qi": "hantan:frost_qi"}}
}
```

- 执行：先打快照 → 父事件 `pack.upgrade{pack, from, to}` → 每项迁移为子事件（改名 = 改定义引用的事件；transform = fact.set；remove = 按卸载规则处置那几项）→ 断言 I1–I32 → 失败整体回滚，存档保持旧版本可玩。
- 没有迁移文件而定义有删除或改名 → E-SAVE-NOMIGRATION，列出存档中引用了被删定义的实体数，建议作者补迁移或玩家选择"按卸载规则处置这些项"。
- **已发生的事件不改**：改名只影响此后的读取；旧事件里的旧 id 由 rename 映射在渲染时解析。

### 12.5.4 卸载

卸载是一次以 `pack.uninstall{pack, version}` 为父事件的批处理，所有子事件起因指向它；**一律走转移协议（第 4 章），reason = "包卸载"（`pack_removed`）**。步骤：

```
0 预演      pack uninstall --dry-run：列出受影响的实例、持有、义务、账户、玩家相关项与处置结果；玩家确认
1 依赖检查  有已装的包硬依赖本包 → 拒绝，列出依赖者；软依赖者的相关条目此后按 when 守卫跳过
2 槽位释放  本包赢得的槽位回到次优（下一个声明者按 §12.4.4 重新裁决，或回到 core 缺省）
3 实体退场  本包每个实例按 uninstall.json 的 entities 策略（附录 A §A.9：gone / keep / convert_entity）：
              gone（缺省）：组织/聚落 → gone → liquidation（清算实体，04 §4.2 第 2 步）；
                           人物与生物 → gone（reason=pack_removed）——注意这不是"死亡"：不产生尸体、不进 sink:death、
                           不触发 harm/哀悼；财产进遗产、按 04 的继承与清偿走（继承人可能是 core 人物）；
                           地点 → 其内 core 实体按 moved 迁到父节点；地点本身成墓碑；
                           物品个体、建筑、资源点 → gone；被 core 实体 owns 的按 uninstall.json 处置（折现/转换/作废）
              keep：实体种类是 core 种类（org/sect、building、office、place…）的实例保留为 core 的孤立实体：
                    origin 改记 {pack, version, keptAt}，章程、法典、持有、账户、位置照旧，此后由 core 规则管
                    （修仙包卸掉后门派仍在，只是功法休眠、境界事实按 facts 策略处置）
              convert_entity{to, facts}：按映射改为 core 种类或模板（城隍庙 → core 寺观建筑；阴差职位 → core 道士认证职位；
                    镖局 → core 商号），事实按 facts 表折算、其余 drop；持有与账户不动
              包定义的实体种类（非 core 种类）只能 gone 或 convert_entity，不能 keep
3′ 改指      core 持有指向本包实体的（certified → 包职位、registered → 包登记机关、devotee_of → 包教团、member_of → 包组织）：
              按 uninstall.json 的 holdings.retarget 改指到声明的 core 实体（镖师认证 → core 武者认证，阴差 → core 道士，
              派生此后读 core 被动表），或按 snapshot 留在墓碑上并由退役表 tables 区承载被动表（§12.5.5），
              或 close（缺省；记"门派已散"）
4 遗留物    core 实体名下指向本包实体的其他持有：按交接类关闭或转移（member_of → close，记"门派已散"）
            义务：一端是本包实体 → 由清算实体承接（I7），清偿顺序照适用法；无可清偿 → bad_debt
            本包定义的资源种类的账户：按 uninstall.json 转换为 core 资源（经 sink:pack_removed / src:pack_converted
              一对显式源汇，I1 可审计）或转入 sink:pack_removed
            本包定义的持有种类、义务种类的存活实例：按 uninstall.json 关闭（reason=pack_removed）或转换为 core 种类
            core 实体身上引用本包定义的慢变事实（功法熟练度、状态）：按 uninstall.json（dormant / fallback / drop）
5 断言      I1–I32 全部重新断言；任何一项失败整体回滚，存档保持已装状态，诊断写明是哪一项、哪个实体
6 写锁      packs.lock 移除该包并记纪元边界；实体墓碑与退役词条（§12.5.5）写入；打快照；重建注册表并冻结
```

**uninstall.json**（每项有缺省值，作者可改得更宽厚，不能改得更苛刻于"作废"）：

```json
{
  "facts": {
    "skill": {"policy": "dormant"},
    "hantan:skill_frost_01": {"policy": "fallback", "to": "core:skill_warrior_combat_02", "ratio": 0.5}
  },
  "statuses": {"policy": "drop"},
  "resources": {"luquan:item_lake_salt": {"policy": "convert", "to": "core:item_salt", "ratio": 1}},
  "instruments": {"luquan:salt_warrant": {"policy": "redeem", "payer": "issuer", "value": "terms.faceValue * remainingQty / qty"}},
  "holdings": {"hantan:disciple_of": {"policy": "close"},
               "retarget": {"core:certified@hantan:office_sword_master": "core:office_warrior_cert"}},
  "obligations": {"hantan:tuition": {"policy": "cancel"},
                  "hantan:escort_insured": {"policy": "convert", "to": "core:escort"}},
  "entities": {"hantan:org_sect": {"policy": "keep"},
               "hantan:bld_shrine": {"policy": "convert_entity", "to": "core:building/temple", "facts": {"hantan:godName": null}},
               "kind:hantan/ghost_bailiff": {"policy": "gone"}},
  "playerNotice": "寒潭剑宗已从世界中散去。"
}
```

| 策略 | 含义 | 缺省用于 |
|---|---|---|
| dormant | 事实保留在存档但休眠：不参与派生、界面不显示、不可用；重装同一包（任一兼容版本）时恢复 | 技能熟练度、功法、配方掌握 |
| fallback | 折算成 core 定义（例：功法熟练度 × 0.5 计入 core 剑术） | 作者声明时 |
| drop | 删除事实（记子事件） | 状态标记、临时效果 |
| convert | 资源按比例转成 core 资源（一对显式源汇转移） | 声明了 core 等价物的资源 |
| redeem | 契据/凭证折现：由发行方（已进清算）按清偿顺序支付；不足部分 bad_debt | 盐引、汇票、股份 |
| close / cancel | 持有关闭、义务取消，reason=pack_removed | 包定义的持有与义务种类 |
| convert（义务） | 包义务种类的存活实例改为 core 义务种类（条款快照保留，加 `convertedFrom`；在途镖货转普通护送）；**各法域对转换后义务的态度**由其 `recognition{what: obligationKind, selector: convertedFrom}` 条目决定（赌债在王国转为借贷有效、在林地 void）——策略不按法域分支 | 声明了 core 等价物的义务种类 |
| void | 作废，不补偿 | 只有作者显式声明才用 |
| gone / keep / convert_entity（实体） | 见上文第 3 步 | 组织、建筑、职位、地点、人物 |
| retarget / snapshot / close（core 持有指向包实体） | 见上文第 3′ 步 | certified、registered、devotee_of、member_of |

**历史事实不改**：
- 事件日志一字不改。旧事件引用的已卸载实体渲染为墓碑名称加"（已不存在）"；引用的已卸载定义（动词、标签）渲染为词汇条目的 label 快照（词汇在卸载时把用过的私有词 label 留进墓碑表）。
- 已判案件（判决事件、执行事件、已完成的转移）不改。
- **未结案件**（N7 卸载①）：案件阶段的适用法本来就是每阶段由派生取得（05 §5.2）。卸载后槽位回落到原法典，下一阶段起按原法典审。规则是**罪刑以行为时法为准，程序从新**：
  - 行为发生时依当时法典本不构成罪名、因而未立案的事——不追溯立案（立案反应规则只在事件发生时触发一次，I4）。
  - 已立案、原法典也有对应罪名（含上位回退）——继续审，刑罚取行为时法与新适用法中较轻者。
  - 已立案、原法典没有对应罪名——撤案，事件 `case_dismissed{reason: 法典变更}`。
- **合同效力**以签约时为准：条款快照（01 §1.4）记录签约时的适用法典 id 与效力判定；南岭法典下签订、被判"无效"的活契，卸载后仍无效；反之亦然。
- 墓碑永不删除；实例 id 永不复用（重装得到 `~2` 代次）。

**卸载失败时**：任何断言失败 → 整体回滚 → 存档保持已装状态 → 诊断指出具体实体与不变量。玩家仍可"禁用不卸载"（§12.8.4 的隔离模式）。

### 12.5.5 纪元、退役词条与卸载后的回放

**问题**（独立审查 run-002 design-review 第 1 条）：03 §3.2 第 5 条"注册完成后冻结"+ I18"词汇封闭（只来自 L1 词汇表）"——包卸载后，事件日志里仍有 `hantan:sect_join` 这类动词、`hantan:disciple_of` 这类持有种类；若注册表里已没有它们，从快照回放到这些事件时校验必然失败。

**解法：三件事合用**

1. **事件自描述**。事件本来就携带已解析的原语列表（01 §1.7、I16）：归约历史事件只"应用记录下的原语"，从不重跑规则、不调用包代码或表达式。所以回放需要的不是包的**规则**，只是被引用**定义**的最小信息：持有种类的互斥/份额约束与模板、资源种类的单位、义务种类的字段形状、动词与标签的 label 与事件流模板。每个事件头另记 `epoch`（所属纪元编号）。
2. **纪元**。注册表只在纪元边界变化：开局（纪元 0）、以及存档里的每个 `pack.install / pack.upgrade / pack.uninstall` 事件（还有 world_upgrade）。两个边界之间注册表冻结。纪元 k 的注册表 = core + 纪元 k 时现役的包 + 截至纪元 k 的全部退役条目，由 `packs.lock` 的历史段（每个边界事件记 `{epoch, registryHash, packs}`）唯一确定。
3. **退役条目（词汇墓碑）**。卸载或升级删除定义时，定义**不删除**，而是转入存档的**退役表** `core/registry.retired.json`：每条记 `{id, 区(动词/标签/持有种类/义务种类/资源种类/状态/法典/动作/tables), 定义快照(回放与渲染所需的最小字段), label, 事件流模板快照, retiredAt: 边界事件编号, sameAs?}`。法典的退役快照包含全文（已判案件的上诉、历史查询要用）；**`tables` 区**存被动派生表、名额表、继任表、职位表的快照，使留在墓碑上的 certified / holds_office 的派生（职业加成、名额）在卸载后仍可计算——04 §4.3 "历史认证保留、派生仍有效"由此成立；选 `retarget` 的持有不需要它。退役条目随存档走，不依赖包仓或作者。

**规则**
- **写**：新提案、新注册的规则与动作只能引用**现役**条目；引用退役条目 → 拒绝（E-RETIRED："'拜入山门' 所属的寒潭剑宗已卸载"）。
- **读与重放**：事件日志中的任一词条按"现役 → 退役 → sameAs 映射"解析；三者都不中 = 存档损坏错误（不是包错误）。
- **全量重放**（从创世快照）：按事件头的 `epoch` 依次切换注册表；纪元内的定义优先从包仓 `.store` 取完整版本，取不到时用退役快照——两者对回放是等价的，因为回放不需要规则。
- **常规载入**不需要全量重放：卸载、升级批处理结束后强制写快照（§12.5.3、§12.5.4），之后的载入从这份快照开始，快照里已没有退役定义的存活实例。
- **渲染历史**：编年史、人物面板、传闻、已判案件显示退役条目的 label 与模板快照，加"（已不存在）"之类标注；知情集合里关于已卸载实体的记忆照常存在（村民仍记得寒潭剑宗）。
- **案件与法典**：case 记两个引用——`lawAtOffense`（行为时法，可以是退役法典，用于罪刑比较与已判案件的上诉审查）与适用程序法（每阶段按当前槽位派生）；退役法典的全文在退役表里，所以"已判不变、未结按原法典"两条都可计算（§12.5.4）。
- **测试**：卸载往返测试加一项——装包 → 推演 → 卸载 → 从创世快照全量重放，最终状态与增量结果逐字节一致；用退役词汇的新提案被拒绝。

### 12.5.6 缺包载档

存档锁里有、本机却没有的包：
- 包仓 `.store` 里有该版本 → 直接从包仓加载（存档自带所需版本）。
- 包仓也没有 → 不载入，提示"本存档使用了 hantan@1.0.0，请安装该包，或选择'按卸载规则移除'"；**不静默跳过**，因为那会让存档里的实体失去规则而破坏不变量。

## 12.6 叙述与提示

### 12.6.1 不进静态提示
- `prompt.staticTokens` 必须为 0（08 §8.3）。包的任何文本（动作描述、同义词、法典正文、lore）都不进静态区；工具定义不因包增加（06 §6.10.1 的 ≤ 16 工具）。

### 12.6.2 按需检索进场景卡
- 包内容进三个现有索引，与 core 内容同一检索代码（retrieval.mjs 的 BM25）：
  - **动作目录索引**（world_actions、场景卡【可做之事】）：动作名、同义词、示例、一句话描述（≤ 60 token）。
  - **目录与知识索引**（world_catalog、world_search）：`narration/lore/*.md` 分块（≤ 300 token/块）、组织公开信息、法典摘要。
  - **事件与模板表**：动词模板、对话模板。
- 场景卡（08 §8.2，≤ 2,500 token）**只按在场、知情、相关度选材**，不给包任何额外配额或加权；寒潭剑宗的弟子出现在卡上，是因为他在场，不是因为装了包。
- 知情边界不变（I12）：法典条文、门规这类"公开知识"由包标注 `visibility: public | members | none`；`members` 的门规只对 member_of 持有人进入知情集合。
- 预算守卫：P11 静态检查单条长度；运行期场景卡、可做之事的总预算不变，超出按相关度截断（08 §8.7）。

### 12.6.3 无 LLM 时
- 包的动作经同一动作目录投影出现在对象菜单、此处可做、对话面板（06 §6.9.1）：对掌门点"对 TA 可做"即看到"拜入山门""请教功法"；在驻地点"此处可做"即看到"观剑痕""挂单借宿"。
- 每个新动词必须有事件流模板（`narration/verbs.json`），每个新请求种类必须有对话答复模板（至少通用文化的四种答复：同意/有条件/拒绝/拖延），P9 检查——否则无 LLM 模式会出现没有文字的事件，违反 06 §6.2 第 1 条。
- 包可以为特定文化与语域提供对话模板；缺失时按 06 §6.9.2 的回退链（文化 → 通用）。
- 构造器兜底照常可用：玩家对包实体的即兴意图走通用原语，包的反应规则照常反应。

## 12.7 作者工具

### 12.7.1 命令

全部命令只读引擎的公开契约与标准夹具世界，不要求作者读源码。

| 命令 | 作用 |
|---|---|
| `pack new <id> --template minimal|sect|law|town|species|beings|blank` | 生成骨架（含 manifest、空扩展点文件、一个推演题与五条意图样例）；`minimal` 是**最小可用路径**：一个人物 + 一组对话模板 + 一条传说，不声明任何规则（B 专项④ 第 7 条） |
| `pack check <dir>` | 跑 P0–P11 静态流水线，输出诊断 |
| `pack test <dir>` | **一条命令跑完自测**（见下） |
| `pack fix <dir>` | 应用可自动修的诊断补丁（加命名空间前缀、改近似拼写、补缺省模板） |
| `pack find place|kind|verb|tag|action <关键词>` | 查 core 与已装包里的 id 与词汇（先查再造） |
| `pack vocab search <词>` | 查词与上位族，防同义 |
| `pack doc <dir>` | 生成包说明页：声明了什么、用了哪些共享词、动作清单、卸载处置表 |
| `pack uninstall --dry-run` | 对存档做卸载预演 |
| `pack pack <dir>` | 打包为 `<id>-<version>.zip`，写入 contentHash |

`pack test <dir> [--with <其他包>...] [--strict] [--tier T0|T2]` 依次执行：

1. **静态**：P0–P11（同 `pack check`）。
2. **夹具装载**：标准夹具世界（tests/probes 用的同一套）+ 本包（+ --with 的包）走 P12–P13，开局装与中途装各一次。
3. **不变量**：I1–I32 的性质测试，事件流生成器从**本包的动作与时钟规则**加 core 的随机抽样（02 §2.2 的同一生成器）；I14 对本包每条时钟规则做"逐日 N 天 vs 一次 N 天"等价测试。
4. **推演**：`tests/probes/*.json`——夹具 + 扰动 + 断言（断言写成 RX，对视图求值），与 tests/probes 同格式。
5. **意图语料**：`tests/intents/*.json`，T0 桩翻译器测路由、裁剪、档位、连锁（06 §6.11）；`--tier T2` 才调真实模型（可选，花钱）。
6. **卸载往返**：装 → 跑推演脚本 → 卸载 → I1–I32 + 存档导出导入逐字节一致 + 墓碑可渲染 → 重装 → 休眠事实恢复。
7. **冲突**：与参考包集合（随引擎分发的 N6/N7/N8 示例包与全部一方包）同装，报告冲突。
8. **规模**：scale 场景下加载本包，日推进与场景卡耗时增量 ≤ 5%（07 §7.5 预算的包份额）。

输出：通过/失败汇总 + 失败项诊断（同 §12.4.2 格式）+ `test-report.json`（供审核流水线与发布页引用）。

### 12.7.2 审核流水线（可选）

沿用内容流水线的分层：
- **L1（必过，确定性）**= `pack test`。不过不许发布到任何官方列表。
- **L2（可选，真实模型事实审核）**：名称、描述、lore、对话模板与世界纲要、文化、已有事实是否矛盾。作者自带模型密钥或由维护者跑；费用自理。

## 12.8 安全与信任边界

### 12.8.1 规则用什么写：受限表达式（RX），不用 JS

**建议**：第三方包的规则一律用声明式数据 + 受限表达式 RX；JS 只给一方包与用户本机显式放行的原生包。

**RX 是什么**：前 11 章里已经大量使用的那种表达式（`principal*rate*days/360`、`actor.account(coin) >= amount`、`present && adult && !impaired`、反应规则的 JSON 谓词 DSL）的正式化。

| 方面 | 规定 |
|---|---|
| 语法 | 字面量、名字（actor/target/槽位/event/holder/subject/params/tables）、成员访问、算术、比较、布尔、`?:`、`??`、箭头 lambda（仅作 filter/map/some/every/sum/count 的参数）、模板字符串（只在叙述中） |
| 数据访问 | 只经 L1/L3 只读视图：`view(x).field`、`account(e, res)`、`holdings(e, kind)`、`members(org)`、`present(a,b)`、`jurisdiction(place)`、`code(place).clause`、`standing(a,b)`、`price(place, res)`、`tables.<id>[...]`、`has(event, tag)`；字段必须在视图 schema 中（静态类型检查） |
| 函数库 | 白名单：数学（min/max/clamp/round/floor/abs/log/exp）、时间（days/season/month）、集合（filter/map/some/every/count/sum，作用于有界集合）、`roll(key)`（内核确定性骰）、`npcDecision(...)`（05 §5.7）、`rank(...)`、`succession(...)` 等由 L1 提供的领域函数 |
| 禁止 | 赋值、循环、递归、自定义函数、字符串拼接成代码、动态属性名、随机、时钟、I/O、对视图之外的任何访问 |
| 全函数 | 必终止；每次求值最坏步数在编译期估算 ≤ 预算（缺省 2,000 节点；集合遍历按上限计）；运行期超预算 = 求值失败（§12.8.4） |
| 确定 | 同输入同输出；`roll` 键 = 战役种子 + 包 id + 规则 id + 对象 + 日期 |
| 可解释 | 求值器可返回逐项值（给"为什么拒绝我拜师"的解释与调试） |

**取舍**：

| 方案 | 表达力 | 安全 | 回放确定性 | 静态检查与好报错 | 作者门槛 | 结论 |
|---|---|---|---|---|---|---|
| 数据 + RX | 中：查表、算式、谓词、有界聚合；没有自定义算法 | 高：没有写入口、没有 I/O、必终止 | 有保证 | 编译期类型检查、步数估算、指出字段 | 低：写 JSON 与算式 | **第三方缺省** |
| 沙箱内 JS（QuickJS/wasm 隔离、无宿主 API） | 高 | 中高：需维护沙箱、桥接 API、时间与内存上限 | 需额外约束（禁 Date/Math.random，冻结内建） | 只能运行期发现错误 | 中 | 不在 S8 前做；若 RX 表达力被证明不够，作为契约次版本加入 |
| 进程内原生 JS（.mjs，3.3 现状形状） | 全 | **低**：Node 进程内无法可靠隔离；import 限制可被 eval/动态 import/原型污染绕过 | 靠自觉 | 靠测试 | 高：要读引擎 API | 仅一方包与用户显式放行（trust=native） |

理由：(1) 开源后最常见的包是"内容包"（门派、法典、城镇、物种、职业），前 11 章与第 9 章走查已证明这类新增"全是数据"；(2) 第 11 章故意保留的专用求解器（战斗交锋、寻路、计票、决斗、天气）对包开放的是**参数**而不是算法，包写战斗数值而不写战斗算法；(3) 回放确定性与"不坏档"是硬要求，进程内 JS 给不了保证；(4) RX 让加载器能在作者本机就指出"第 12 行的 `holder.stagee` 不是视图字段"，这是"不费劲"的关键。代价是表达力：真需要新算法的包（新的求解器）必须向引擎提需求，这是故意的——新算法应进 core 并被所有包共享，而不是藏在某个包里。

**原生包（trust=native）的约束**：只能 import `@wildfield/pack-api`（只读视图 + 提案构造器，I19 import 图测试覆盖）；在独立 worker 中运行、无文件与网络权限；导出的函数只能是派生函数与参数计算器，返回值仍是值或原语提案；每次调用有时间上限。即便如此，装载界面明确标"原生代码：可能影响存档安全"，需玩家逐包放行；S8 验收与开放契约的保证都不覆盖原生包。

### 12.8.2 包伤不了存档：结构性保证

1. **没有写入口**：一切经提案 → 内核事务 → 不变量校验 → 事件（I3、I16）。错误的包最多产生被拒绝的提案。
2. **事务原子**：一个提案或一个卸载批处理失败即整体回滚（01 §1.8）。
3. **加载期拦截**：P3–P11 挡住结构性错误；运行期只剩"规则逻辑对但数值荒谬"一类，由 I20 上限与合理性表兜住幅度。
4. **事件只追加**：包永远不能改写历史；卸载、升级也是追加事件。
5. **存档自带版本**：包仓保存用过的版本，回放不依赖作者是否还在维护。

### 12.8.3 资源与平衡预算

- **装载预算**：实体数、地点数、时钟规则数、反应规则数（清单 budgets 自报，加载器另有全局上限）；超出即 E-BUDGET。
- **合理性表**（L1 数据）：初始公库、储量、人物财富、功法与装备数值按"组织种类 × 规模"、"聚落等级"、"阶段"给出上限；超出为 error（数值类上限，I20）或 warning（财富类，需在清单里写 `"justify": "……"`）。防止一个包带进十亿铜钱把全世界物价打穿。
- **反应扇出**：每条反应规则对每个起因事件最多产生 `maxProposalsPerEvent` 个提案；反应链深度有全局上限（防两包反应规则互相触发成环；幂等键 I4 已防同一起因重复）；**包声明的反应规则无论优先级类一律计深度**（包的 settlement / legal 类上限另设，缺省 16），只有 core 的协议子步与合法性标注豁免（14 §14.2）。
- **性能份额**：`pack test` 第 8 步；运行期按规则统计耗时，进调试面板。

### 12.8.4 运行期隔离与熔断

- RX 求值失败（超步数、视图返回空值未处理）、原生函数超时、某规则的提案在 24 小时游戏时间内被连续拒绝超过阈值 → 该规则**熔断**：事件 `rule_suspended{rule, reason}`，此后不再触发；游戏继续；装载报告与调试面板提示作者与玩家。熔断不改变任何已归约状态。
- 整包隔离模式（"禁用不卸载"）：包的动作从目录隐藏、反应与时钟规则暂停，实体保留；**义务照常到期、罚息、违约（I29、04 §4.1）**，隔离不是失能；若玩家希望隔离期间免除该包义务的催收，引擎在纪元边界写一条显式的宽限规范条目事件（`grace`，来源 = 引擎，可审计）；可随时恢复。用于"这个包有问题，但我不想丢存档里的东西"。

### 12.8.5 本章定义的不变量（I21–I23）

B 专项⑤指出第 12 章没有以 I21–I23 为题的定义段，补在这里（02 §2.1 的表行与此一致）：

- **I21 包隔离**：包内容只经加载器在纪元边界进入注册表；每个包实例带可追溯的 `origin`（包、版本、代次）；包没有写入口——数据包无代码，原生包只经 pack-api 返回提案。保证：加载器 P0–P13、I3、I19。测试：伪造 origin 的包被拒；运行期无任何包模块持有状态引用。
- **I22 可卸载**：`pack.uninstall` 批处理完成后 I1–I32 全部成立，存档导出导入逐字节一致，历史事件一字不改，墓碑与退役条目可渲染。保证：卸载批处理 = 转移协议的批量调用（basis pack_removed）+ 退役表 + 末尾断言整体回滚。测试：`pack test` 第 6 步装 → 推演 → 卸 → 全量重放一致。
- **I23 表达式全函数且确定**：每个 RX 表达式在编译期有最坏步数估算 ≤ 预算、必终止、同输入同输出、数值为定点数、无 I/O 与随机（`roll` 的键由内核给出）。保证：RX 编译器 P7 + 运行期超预算即熔断。测试：随机表达式模糊测试；跨平台求值哈希一致（标杆 B13.2）。

### 12.8.6 包档（B 专项④ 第 7 条）

`manifest.tier: content | rules`。**content 包**只声明实体、地点、传说、对话与叙述模板、词条（不声明任何规则形状、持有或义务种类）；`pack test` 对它跳过规则类检查（I14 等价、I27 修正项、聚合变体），只跑 schema、引用、词汇、出处与敏感度、可玩性、注入断言与卸载往返，报错用内容作者能懂的措辞。声明了任何规则形状的包自动为 rules 档。

**rules 档的作者门槛**（R5 专项④）。rules 档作者只需理解五件事，其余由缺省与模板承担：①**修正项**（挂到任一派生值，core 的 bounds 见附录 A §A.16，写 `when` / `value`）；②**规范条目**（罪名谓词、税表、豁免）；③**反应规则**（事件 → 原语）；④**时钟规则**（周期 → 原语）；⑤**扩展事实**（在 core 实体上记自己的状态）。不必理解的：closedForm / tolerance（只含 transfer 与数值 fact.set 的时钟规则可写 `"equivalence": "auto"`，引擎按闭式自动推导并在 `pack test` 验证；做不到时诊断给出"请改写为 closedForm 或声明 tolerance"）、聚合变体（`aggregate: "auto"`）、退役与纪元（全由引擎处理，作者只写 uninstall.json 的策略）、RX 库的全部函数（`pack new --template modifier|law|reaction|clock|facts` 生成带注释的骨架，每个模板只用到 ≤ 6 个库函数）。`pack doc` 为 rules 档作者生成"你的包影响了哪些 core 派生值、读了哪些扩展事实、还想影响但没有槽的派生"三张表。

## 12.10 走查：N6、N7、N8

### 12.10.1 N6 寒潭剑宗

**建模**：门派 = org（种类 `org/sect`，collective 模板）+ 章程数据；驻地 = 新地点（父 = 安装参数选定的郡，法域随父链派生）+ 三栋建筑；掌门、长老 = office 实体（holds_office）；弟子 = person + member_of + `hantan:disciple_of`；五门功法 = skill 定义（core 同格式，带 `combatAction` 参数）；门规 = 章程中的成员层规范条目（05 §5.2.6；谓词 → 私有标签 `hantan:sect_rule_breach`，内部制裁）；与已有门派的关系 = edge（初始关系基线一行一端是本包组织）。

**装上以后**
- ① 驻地出现在指定郡、弟子按日程活动：地点经 P8 的 I9 检查；弟子是 world/people 同格式的作者数据，经 L1 转换器变成 resides/member_of/employed_by 等持有；日程由 05 §5.8 派生（基准作息 + 门派职务片段），无需包写日程代码。
- ② 拜师、学功法、战斗数值变化：`join_sect` 动作（同意走 npcDecision）→ member_of + disciple_of；`learn_art` = learn 原语（来源 = 师承持有，前置由 RX 派生）；战斗求解器读技能定义的 combatAction 参数，熟练度进入战斗视图——功法数值受 core 阶段上限表约束（I20），所以第三方门派不能造出"无敌剑法"。
- ③ 与已有门派的初始关系与变化：初始关系是立场投影的"基线"项（05 §5.6），变化来自 impress 事件（弟子被打、切磋胜负、结盟），沿 member_of 传导（K4）——与 core 门派完全同一机制。
- ④ 离屏自行招收与更换首领：招收 = 时钟规则（智能/规则层走 NPC 自治 + 同一动作；统计层闭式计数，声明容差，I14 等价测试自动纳入）；更换首领 = core npcLife 死亡/年迈退位 → 转移协议 → holds_office vacate → 继任规则 `duel`（04 §4.6）→ 候选人约斗（core 决斗动作）。包没写一行"继任代码"。

**卸掉或与他包同装**
- ① 卸载：org_sect → gone → liquidation（公库按清偿顺序，剩余按法域规定归公）；玩家 member_of 与 disciple_of 关闭（reason=pack_removed），人物面板据关闭的持有派生显示"寒潭剑宗（门派已散）"；已学功法按 uninstall.json：缺省 dormant（存档保留、不可用、重装恢复），本示例包对映雪声明 fallback → core 剑术熟练度 ×0.5；门内弟子（包的 person）按 pack_removed 退场，其财产走遗产、继承人可能是 core 人物；I1–I32 重断言；存档不报错（墓碑渲染历史）。
- ② 与另一包争用驻地：两包都对同一 place.seat claim，或驻地坐标距离 < 阈 → E-CONFLICT-SEAT；本示例包声明 `relocate: nearest-free-in-county`，加载器确定性地迁到同郡下一个空闲候选并写入装载报告；对方未声明可迁移时，按 §12.4.4 第 2 条要求玩家在 profile 里裁决。
- ③ 同名功法：`hantan:skill_frost_01` 与 `qingfeng:skill_frost_01` 是不同定义 id，名称都叫"映雪"也无妨（同义词阻断只对词汇条目，不对定义的显示名，§12.3.3 第 2 条）；界面显示"映雪（寒潭剑宗）"；LLM 路由遇到同名时返回候选（06 §6.10.4 歧义不猜）；两者的 llm 同义词重叠只产生 W-SYNONYM 警告。

**新增**：全是数据。用到的扩展点：地点、实体、持有种类、状态、动作、时钟、反应、叙述、界面、卸载处置、安装参数。

### 12.10.2 N7 南岭郡法典

**建模**：法典 = `law/codes.json` 一部完整法典（罪名表、程序、民事十类、冲突法、税表、契约效力、豁免）；绑定 = `law/bindings.json` 占用槽位 `place.lawCode@<南岭郡>`。若世界里没有叫"南岭"的郡，包要么带一个新郡（地点扩展点，挂在某省下、该省由某政体 governs，I9），要么用安装参数让玩家选一个已有郡绑定——示例包两种都提供，缺省为参数绑定。

```json
{
  "id": "code_nanling",
  "polity": "inherit",
  "extends": "inherit",
  "offenses": {
    "offense:homicide": {"penalty": "death_or_exile", "exempt": [{"when": "has(event, 'duel:consented') && event.location in scope", "reason": "私斗经双方立约，不究"}]},
    "offense:assault":  {"exempt": [{"when": "has(event, 'duel:consented')", "reason": "同上"}]},
    "offense:smuggling": {"penalty": {"fine": "value * 3", "confiscate": true}}
  },
  "contracts": {"void": ["contract:redeemable_sale"], "voidReason": "禁活契：典卖须绝卖"},
  "tax": [{"base": "trade", "commodity": "goods:salt", "rateBps": 3000, "recipient": "treasury"},
          {"base": "toll", "node": "{{params.checkpoint}}", "flat": {"resource": "core:coin_kingdom_copper", "qty": 2}, "recipient": "controller",
           "exemption": {"per": "person", "window": 30, "qty": 1, "counter": "countEvents({actor: actor, verb: 'move', crossesNode: node}, 30)"}}],
  "civil": "inherit"
}
```

`"inherit"` 表示该部分沿用政体缺省法典（法典完整性校验视为齐全）；只覆盖的部分写出来。

**装上以后**
- ① 境内罪名与刑罚按新法典：法域派生 = 地点向上找最近的 lawCode 绑定（槽位）→ 南岭法典；无绑定才用政体缺省法典。立案反应规则（法律包，core）读事件的规范栈（05 §5.2.2），南岭法典作为次级属地层条目进入栈——零改动。
- ② 盐税提高、盐价上涨、私盐增多：税反应规则按交易事件的商品类标签 `goods:salt` 与交易地法典税表征税；价格投影的"法域政策"项（15 §15.2）读同一税表 → 南岭盐价上升；自治包的机会评估读**主观视图中**两法域间同一商品类的价差（经 `market_report` 的转述得知，05 §5.4）→ 他相信的价差足够大时，风险偏好高的 NPC 选择运私盐动作（带 `offense:smuggling` 标签）→ 私盐案件增多。这一条要求自治包的机会评估包含跨法域价差项（core 数据，见 §12.11）。
- ③ 决斗不追究：core 决斗动作打 `duel:consented` 标签；南岭法典的罪名表对 homicide/assault 声明豁免 → 立案规则不立案。决斗仍产生 harm 事件，立场、哀悼、复仇等反应照常（法律不追究 ≠ 世界不反应）。
- 禁活契：义务创建时，条款快照记录签约地法典与效力判定；`contract:redeemable_sale` 在南岭签订 → 效力"无效"（派生后冻结进快照）→ 违约时不产生可立案的 breach，法院动作对其拒绝受理并给世界内原因；不打罪名（法典没把它定为罪）。

**卸掉或与他包同装**
- ① 卸载：槽位释放 → 南岭郡回到政体缺省法典；已判案件不变（判决与执行是事件）；未结案件按"罪刑以行为时法为准、程序从新"处理（§12.5.4）：决斗致死在南岭本不立案，卸载后也不追溯；已立的私盐案继续按原法典审，刑罚取较轻者；南岭特有罪名的案件撤案。已签的活契保持签约时的"无效"判定。
- ② 两部法典同覆盖一郡：两包对同一 `place.lawCode` 槽位声明 → E-CONFLICT-SLOT，两包在该郡的绑定都不生效，直到玩家在 profile 里裁决或一包把另一包列为依赖并声明 overrides；永不字段级合并。一部管郡、一部管郡下某镇 → 层级，不冲突，按最近绑定。

**新增**：全是数据。需要 core 预置的词汇：`duel:consented`、`contract:redeemable_sale`（若 core 没有，N7 以共享词提议，上位 `contract`）、`goods:salt`。

### 12.10.3 N8 卤泉镇（盐井、盐商行会、盐引）

**建模**：卤泉镇 = settlement（地点 + 实体，行政等级"镇"）挂在安装参数选定的郡下；盐井 = node 实体，账户（卤水储量，资源种类 `luquan:brine`，商品类 `goods:brine`）；产盐 = 经营持有下的生产动作/规则：transfer(卤水, 盐井 → 灶户) → **配方 `luquan:boil_salt`**（`rules/tables/recipes.json`：投入卤水 + 燃料，产出 core `item_salt`（商品类 `goods:salt`）从 `src:craft` 流入灶户账户，同事务消耗投入——制造守恒对，01 §1.6，`create` 只造物品个体）；盐商行会 = org（`org/guild`）+ 章程（继任 charter_vote）；盐课司 = office（由镇治理组织设职）；盐引 = instrument 实体（种类 `luquan:salt_warrant`，条款：面值、可运数量、有效期、发行职位），玩家/商人 `owns` 盐引；无引运盐 = 合法性标注规则。

```json
{
  "id": "salt_without_warrant",
  "on": "proposal",
  "when": "op == 'move' && cargo(entity).some(c => commodity(c.resource) == 'goods:salt' && c.qty > 0) && warrantCover(actor, 'goods:salt', now) < cargoQty(entity, 'goods:salt')",
  "tag": "offense:salt_smuggling",
  "scope": "jurisdiction(from).recognizes('luquan:salt_warrant')"
}
```

`warrantCover` 是包里的派生规则（RX：本人 owns 的有效盐引可运数量之和）；`scope` 让盐引制度只在承认它的法域生效（包声明"卤泉所在政体承认"，可由法典扩展）。

**装上以后**
- ① 周边郡盐价随卤泉产量变化：盐产出就是 core `item_salt` 的账户增加；市场投影（15 §15.2）的"到岸成本"项沿可通行路线找最近有存量的供给地——卤泉镇的盐账户自动进入周边郡的价格公式。产量降（储量下降、灶户停工）→ 价格升。零改动。
- ② 无引运盐违法：合法性标注在裁决第 3 步给 move 提案打 `offense:salt_smuggling`（上位 `offense:smuggling`）；承认盐引的政体法典的 `offense:smuggling` 条目因 `matches: offense:smuggling`（core 缺省）对该下位标签为真 → 嫌疑记录 → 可立案（05 §5.2.3）；对不承认盐引的政体，标注的 `scope` 为假，不命中。
- ③ 盐井储量随开采减少：盐井只有一个卤水账户，开采是从它转出（I1）；再生按包的时钟规则（极慢，闭式），归零即无产出。盗采同样从这个账户扣（E04 同理）。
- ④ 官员、行会首领任免更替：盐课司是镇治理组织下的 office，任免走 core 治理包动作，继任按职位规则；行会首领按章程 charter_vote（04 §4.6）；首领死亡走转移协议。俸禄是 salary 义务，金额由职级 × 聚落等级派生。

**卸掉或与他包同装**
- ① 卸载：盐课司、行会 → liquidation；玩家的盐引按 uninstall.json `redeem`：由发行方（盐课司所属治理组织的清算）按"面值 × 剩余可运量比例"在清偿顺序中支付，不足部分记 bad_debt——折现且守恒；行会股份（share 持有）按清算净资产分配（04 §4.3 share：清算按份额分）；玩家手里的盐本来就是 core `item_salt`，**什么都不用做**；`luquan:brine` 账户按 convert 声明（无 core 等价物 → 转入 sink:pack_removed）；镇内 core 人物（若有在此居住的）按 moved 迁到父节点。存档不报错，墓碑渲染"卤泉镇（已不存在）"。
- ② 与 N7 同装：N7 的税表写 `commodity: goods:salt`，N8 的盐就是 `goods:salt`；N8 的私盐标签上位是 `offense:smuggling`，N7 的罪名表有 `offense:smuggling`。两包互不出现在对方的 dependencies 里，也不引用对方的任何 id；协作发生在 core 的税反应规则、立案反应规则与市场投影里。`pack test luquan --with nanling-code` 的推演断言：卤泉盐运入南岭交易时按 30% 征税；无引运盐在南岭立案并按 N7 的 smuggling 刑罚判；卤泉若就在南岭郡内，则 N7 法典直接管辖卤泉镇（槽位层级：郡级绑定覆盖子树，卤泉不另绑法典时）。

**新增**：全是数据。需要 core 预置：`goods:salt`、`goods:brine`（或由 N8 提议共享）、`offense:smuggling`、`org/guild`、合法性标注扩展点与 `warrantCover` 这类派生能用的 RX 集合函数。

### 12.10.4 走查结论

三道第三方题的全部预期都由"八个概念 + 转移协议 + 投影 + 动作层 + 本章的命名空间、槽位、词汇上位回退、卸载处置"算出，**没有一处需要包写代码，也没有一处需要改引擎**——前提是 §12.9 的预留在各阶段做到，尤其是：RX 编译器（A3）、槽位与法典绑定、商品类标签、卸载批处理与墓碑、词汇表的上位词与共享区。run-005、run-006、run-007 的规则档包（镖局、阴司、修仙；鬼市、监狱、结社；风水、师徒、生态）逐轮暴露的缺口——改 core 派生输入、实体转换、非金属货币、给 core 动作加前置、普通物种、地价——到第五轮由开放性宪章（附录 A §A.9）一次封口：任何派生可修正、任何表可加行、任何定义可追加前置、任何物种同一 schema、任何可定价物进估值表；逐包走查不再写在本章，S8 盲测用这九个包作对象（§12.9）。

## 12.12 风险与待定

**风险**
1. **RX 表达力**：一方包的现有派生函数有多少能改写为 RX，S3 评估前不确定。对策：不能改写的进 L1 库函数（引擎提供、所有包共享）；库函数清单随契约次版本扩充。
2. **词汇治理**：开源后共享词会被不同作者用不同理解提议。对策：上位词必填 + 同义检查 + 定义哈希；core 预置足够宽的族；共享词表随引擎版本定期收编（把常用共享词升为 core 词）。
3. **卸载的长尾**：包实体与 core 实体交织越深（婚姻、继承、案件），卸载批处理越复杂。对策：完全复用转移协议；卸载往返列入 `pack test` 必过项；失败整体回滚 + 隔离模式兜底。
4. **平衡**：合法的数值组合仍可能失衡（便宜的功法 + 高收益动作）。对策：上限表与合理性表、"不能比注册动作更划算"（06 §6.7）对包动作同样适用、推演合理率不降的验收。
5. **作者体验**：契约若频繁变动，第三方包会大量失效。对策：契约语义化版本；主版本变更随附自动迁移（sameAs、rename）；`pack fix` 自动修。
6. **开放性宪章的平衡**：每个派生缺省开槽、每张表缺省可加行、每个定义可追加前置后，多包叠加可能把世界推到荒谬值（人人千岁、十年不雨、处处要拜师三年）。对策：缺省 bounds `mul ∈ [0.5, 2]`、每槽 bounds 与数量预算（§12.8.3）、max/min 阶段天然不叠加、`exclusiveGroup`、前置补丁只能追加且带世界内原因、平衡仿真报告（标杆 B17.8）"槽叠加极值"对全部派生抽样；`pack test --with` 对参考包集合报告每个槽的叠加结果与每个 core 动作被追加的前置数。
7. **扩展事实的膨胀**：每个包在 person 上加十个字段，存档与视图都会变重。对策：扩展事实计入包的装载预算（§12.8.3），卸载按声明清理，视图按需读取。

**待用户决定**（玩法/内容/部署类）
- 开源许可（引擎代码与包格式文档的许可，以及示例包的许可）。
- 是否设官方包列表及其上架门槛（建议：L1 必过，L2/L4 可选显示徽记）。
- 第三方原生代码包是否完全不开放（本章建议：缺省不开放，仅本机显式放行，不进官方列表）。
