## 结论：必须改

两条必须改；第二条里"账本 reason 与事件 verb 的取源"同源，一并写明。改完再送分档复核。

### 必须改 1（代码）：事件条不随调用方事务回滚——幽灵事件

- 卷文原句：
  - R24-1.1 :395「事件由写下它的那笔事务写，不由别处事后推出……成功后恰有一条以本事务原语为 `primitives` 的事件」。
  - R24-1.2 :396「事件写在状态改动之后、同一事务之内」。
  - 卷二 :509「**整笔拒绝**：当前事务整笔回滚，撤销本事务的全部写入，不只丢掉被拒的那一次写入。只丢一笔、其余照提交，会留下半套结果」。
  - 卷二 :512「请求条目先单独提交入 `doc_log`（卷二十七 R27-7.3），在回滚范围之外，回滚的是处理事务，不是条目那一笔」——**只有请求条目**在回滚范围之外；事件条不在这个例外里。R27-7.3 :670 同：只有玩家指令与推进请求条目先单独提交。
  - R27-4.1 :497 存档摘要对逻辑文档计算，逻辑文档五部分含事件日志（`doc_log`）；A9-2.2 :683「任一原语被拒时，事务前后存档摘要相同」。
  - R24-1.5 :399 复演「重新产生的事件流（含各事务事件的原语列表）须与日志逐字节相同」。
  - 卷二十 :523「本刻 t 已执行的各项一律作废」、:525「心跳推进记下的事件序号区间截掉作废段」。
- 文件:行：`server-plugin/kernel/events.mjs:500`–`:502` 直接 `appendLogEntry(book, full)`；`server-plugin/kernel/save.mjs:427`–`:431` 直接 `book.entries.push`；`server-plugin/kernel/transaction.mjs:30`–`:41` 的 `rollback` 只按 `tx.undo` 恢复 state；`:116`–`:119` 提交时只把 `tx.undo` 接到刻日志；`:47`–`:71` 的刻日志也只覆盖 state。事件日志簿在 state 之外，两处回滚都不碰它。
- 行为：执行器在适配器全部通过后写事件；此后 `runTransaction` 仍会跑 `holdWhileRecompute`（`transaction.mjs:110`），它抛错即整笔回滚、state 复原，但事件留下。别的路径同样可达：调用方在 `execute` 返回后再写别的、随后失败；或推进中整刻作废（`rollbackTickJournal`，`transaction.mjs:66`–`:71`），本刻已提交事务的事件留在 `doc_log`。后果：存档摘要改变（A9-2.2）、复演事件流与日志不一致（R24-1.5、R27-7.2 的 E-REPLAY-DIVERGE）、卷二十 :525 要求的"事件序号区间截掉作废段"不成立。回报"部分与挂卡"第 2 条已自述此事、挂 5-7／块 6；按本卡分派重点，这一条判必须改，不能挂后。
- 改法（卷文所需，不新增设计）：把事件追加纳入本事务的回滚范围——提交才落、回滚即无。现有两类可行落地（择一，皆不新开特例）：
  1. 内核内（`events.mjs` 与 `transaction.mjs` 同组）让 `emit` 向当前事务登记一条日志撤销项（记下 `book.entries.length`），`rollback` 时截回该长度；事务在刻日志开着时提交，同一条撤销项也接到 `tickJournal.undo`，整刻作废时同样截掉。
  2. 事务内把待写事件放进 state 的待办（照 `pendingPost.*` 的既有写法，卷二 :1010「提交后项必须由待办记录驱动……随该事务同一次提交落盘，事务被拒即没有记录」），提交后落日志、回滚即丢弃。
  两条都满足"事件条随事务提交才落"；R24-1.6"写下后不改"不冲突：回滚撤销的是尚未提交的追加，不是已写下的事件。
- 测试缺口：`tests/kernel/events.test.mjs:286`–`:293` 只测"适配器不存在即整笔拒收"（事件尚未写）；没有测"事件已写、调用方事务随后回滚"与"整刻作废"两类。改法落实时按卷文补：事务成功→恰一条且提交后仍在；调用方回滚→日志条数回到事务前；刻日志作废→本刻事件全不在。

### 必须改 2（代码）：执行器事务事件的 `verb`／`actor`／`payload`／`visibility` 与 id 主体是按 `cause` 现造的占位

- 卷文原句：
  - 表 A :134 `verb`「已登记动词……onUnknown error……最小字段；卷九 `emit` 原语必填」；:139 `cause`「规则或指令代号……已登记的动作代号、钩子或反应规则的登记代号」——两栏不同命名空间。
  - 表 A :135 `actor`；:142 `visibility`「卷九 `emit` 原语必填」；:143 `payload`「形状由动词行 `payloadShape` 给……onUnknown error」。

  - §2.9 :437 提交段事件：规则或指令代号=动作代号、主体 id=行动者 id（同刻已有提交时取上一条事件 id）、位次 `pos.commit`；:439 推进钩子/反应规则经执行器的事件：主体 id=触发它的事件 id 或钩子的主体 id、位次由登记卷给固定代号。
  - R9-2.10 :668 `emit` 适配器用该事件的 `verb`、`visibility`、`actor`、`targets`、`payload.place` 调一次 `perceiveEvent`——这些字段必须来自真实事务上下文。
  - R24-1.6 :400「事件记录是事实，写下后任何字段不改」；R24-1.9 :403「事件记录、载荷、起因都只有代号、id 与数」。
  - 卷十八 :222 持有变化/常住变化「`actor` 取所在事务那条事务事件的 `actor`……故取值唯一」——事务事件 `actor` 置 null 会把空行动者传进协议事件。
  - 李白 11-18 22:10 总原则「写者没上线的一律"明确拒收+进PLAN挂到具体卡"，不造桩、不放空、不静默跳过」；五.2「块5建分派与契约校验，这三个遇到即整笔拒收……块5验收如实记"部分、三适配器 not_run"」；丙1「只照卷文推导，不造数据」。
- 文件:行：`server-plugin/primitives-runtime.mjs:264`–`:277` 的 `emit(...)` 调用：`verb: cause`、`actor: null`、`targets: []`、`witnesses: []`、`visibility: 'private'`、`payload: {}`，id 段 `{ rule: cause, subject: cause, position: 'pos.commit' }`；`server-plugin/kernel/events.mjs:328`–`:353` 照单收下并冻结。
- 行为：
  1. 真实动作的 `cause` 是动作代号（§2.9 :437「动作代号」），不是 `verb` 族条目。`events.mjs:332` 的 `verbRow` 在整批写入已完成后抛 E-EVT-VERB，调用方事务整笔回滚——每个真实动作都会在末步被拒。
  2. 若 `cause` 恰好是已登记动词（现有测试正是这样：`tests/kernel/events.test.mjs:60` 与 `tests/kernel/primitives-runtime.test.mjs:33` 把 `cause` 改成 `verb_test_exec`），事件的 `verb` 就是规则/指令代号，而不是动作行 emit 原语给的成交动词——事件记的"做了什么"是编的，且与 §2.9 规则段（动作代号）同值只是巧合。
  3. `actor=null`：表 A :135 类型可空、onUnknown 为 gap，结构上放行；但提交段事件的行动者是已知的（§2.9 :437 主体 id 取行动者 id）。把已知行动者写成 null 是占位，且 R24-1.6 写下后不能改；卷十八 :222 的协议事件会把 null 当行动者传走。
  4. `payload={}`、`visibility:'private'` 不是调用方给的值；动词行 `payloadShape` 非空的动词（现四行里 `verb_entity_terminated` 的 `id` 非空）会因此报 E-EVT-SHAPE 或记下不真的事实。
  5. 事件 id 的 `subject` 传 `cause`、`position` 固定 `pos.commit`：§2.9 :437 要求主体是行动者 id（或上一条提交事件 id）；:439 钩子/反应事件的主体是触发事件 id 或钩子主体 id、位次是登记固定代号。后果：两个不同行动者同一分钟执行同一动作（同一 `cause`）→ 五样全同 → `events.mjs:501` 报 E-SEED-COLLISION，第二笔整笔回滚；R9-3.8 要求"同一行动者同一分钟内的第二次提交……id 不同"。
- 改法（按卷文，不造数据）：
  - 事件 `verb`、`visibility` 取本批 `primitives` 里的 `emit` 原语（表 A :134／:142；卷九 :643）；`cause` 仍作事件 `cause` 与 id 的规则段（§2.9 :437）。
  - `actor`、`targets`、`payload`、事件 id 的 `subject`／`position` 由发起事务的上下文给（提交段取行动者与动作行；钩子/反应取其触发事件 id 或钩子主体 id 与登记位次，§2.9 :437／:439）。
  - 块 5 这些字段拿不到：按李白 22:10 五.2／总原则，`emit` 适配器未上线就**整笔拒收**（现 `E-ACT-WRITER-NOT-READY` 已在写者未上线时生效），**不写**这个事件；回报把"恰一条事件"这半边如实记"部分、待 emit 适配器／提交段接线"，不写成已完成。不要用 `cause`／`null`／`{}` 顶替后继续写事件。
  - 事件 id 的取法同样照 §2.9 分类给值；在提交段上下文未接前不写事件，也就不会撞号。
- 附（同源，一并处理）：`transfer` 适配器把 `cause` 当账本 `reason`（`primitives-runtime.mjs:235`）。卷六 :286 写 `reason: verb 代号`；K5-48（`docs/迁移体检/块5.md:68`）已把"是否已登记 verb"转真检查（`server-plugin/kernel/ledger.mjs:549`）——真实动作代号作 `cause` 会在账本入口就 E-EVT-VERB。账本 reason 也应取本笔真实事件动词（emit 原语给的 `verb`），不得拿规则/指令代号充数；若本笔没有 emit、拿不到 verb，按上条整笔拒收。此处属同一条占位链，不另立新规则。
