## 阻断

B1. N17（m2-preconditions）归类 (1) 无证据，且新增的自采入库会让原推导公式不成立
- 位置：背景包 §5 阻断 B；tests/m2-preconditions.test.mjs N17；household-subsistence.mjs:660-676（supplyHousehold 取柴入阿言行囊）。
- 理由：差额 3 的"家户烧柴"只是推测，没有探针。基线与候选都败，所以不能当作"预期影响"关闭。而且本批新增了日用自给：窗口内阿言若取柴，库存减少量 = 行动扣料 + 家户烧柴 − 自采入库。背景包提议的推导式（天数×日克数 + 初欠 − 末欠）没有自采入库项，在候选上会再错一次。
- 修法：先在云上探针取证（阿言户窗口内燃料类消耗、自采入库、行动记录 spent.materials 三项分别记）。断言要写成"行动扣料 + 家户用度 − 自采入库 = 库存减少"，三项都要有真实来源（账本里 bag 账户的入账来源 forest:/site: 与 sink:consume|item_wood|fuel 要能对上），不许改成 ≥ 或删。若账本拆不出持有人，按背景包说的补"每户用度消耗日志"原语（只记在 state.family.upkeep 行，不动账本顶层）。

B2. 性能：upkeep 导致"全户每日都跑完整日用自给规划"，没有探针数据（目标 4）
- 位置：household-subsistence.mjs:282-284（提前返回条件加了 `&&!wants.length`），:31-40 readUpkeepWants，:139-144 candidateStockKey。
- 理由：以前只有缺粮/缺水的户才走后面的整套时段/成员机会成本计算。现在凡户内持有柴（盐）不足一个交易周期的户（含欠量），每天都会过这条路径，规模是 O(户) 每日，不是 O(缺粮户)。另外 candidateStockKey 对 upkeep 每次调用都对每个候选调用 upkeepLive(context=null)，林木来源每次做 forestView（含 `forestSites(engine).find` 的 O(林地数) 默认参数 + projectForest 的 logisticStock 投影），journey 的备忘命中前就要付这笔，即实际是 O(户×来源×林地)。背景包 §7.5 自己承认没跑探针。
- 修法：给出同一世界、同一天数下 prepareHouseholdSubsistence 用时的前后对比（探针即可）。若恶化明显：(a) 把 wants 为空的早退保持；(b) upkeep 的 stockKey 用来源账本的版本戳/updatedAt+reserve（只读记录，不做投影）；(c) forestView 传入已查到的 site，避免重复 find。

## 非阻断

N1. household-subsistence.mjs:410,434 atHome=`slot.location===home`：若作息里"在家"写成家所在建筑内的子地点（房间/内室），会被判成不在家而整天没有取柴时段。请在一个真实世界样本上统计 off 判为 true 的时段占比；如有房间层级，应按"同一聚落点/同一落脚点"原语判，而不是字符串相等。
N2. household-subsistence.mjs:31-40 held 把户内所有持有人的该类货都算作覆盖，包括店主货架上待售的货；而 household-budget.reserveUpkeep 把商品（merchandise）排除在自留之外。口径不一致：持货架柴的店主户永不自采。建议 held 复用同一个"非商品"口径。
N3. sites.mjs:462-466 siteTake 对林木来源的据点资源，当 harvestForest 取不足会 throw 预设失败（'林木存量不足'）。日末结算（supplyHousehold）里这是未捕获的异常，会让整个推进失败。当前靠 upkeepSources 去重保证林木支撑的据点资源走 forest 行，但 forest 行的排除条件（place.owner/place.site.owner/requiresConsent）与 commonsResources 的（requiresConsent + ownerOf(resource)）不是同一函数，边界上可能一边排除另一边保留，导致走 site 行且 forestBacked。建议两处共用一个"公共来源"判定，并在 supplyHousehold 里对 quantity 不足保持降级而不是依赖抛错（或加一条该边界的测试）。
N4. market.mjs:198-200,218 去掉 retained 里的 upkeep 后，非短缺户持有的柴不再计入需求（原来计入）。这对粮食和非 upkeep 物品确实不变（row.upkeep 只在 reserveUpkeep 里累加），但对柴盐是价格方向的改变：需求只剩 upkeepDemand 的短缺量。目标说明是"自给越多柴价越高"的反常，方向合理；但缺一条市场侧测试证明（同户同货只算一次、粮食需求不变）。建议补测，而不是只靠 s5 的行为测试。
N5. distribution.mjs:110-113 cash() 每次笔交易都重新 wakingView，去掉了日首快照。语义修正合理，但每个出卖人每笔都重算，背景包没有列入影响与性能评估；`let view=null` 已成死变量。请清理并给出耗时。
N6. npc-labor.mjs:690-715 spent.materials 取 npcCraft 的 spent.materials，而 npc-autonomy.mjs:189 附近失败时 returnMaterials 会退还一部分料；spent.materials 是退还前的 clone。若行程中有失败批次，"spent 记真实扣量"不成立，N17 类断言会再差一截。请确认并在 spent 中扣掉退还量，或加说明。
N7. transition.mjs:133-135,153-155 featureAnchorOwner 每次在 全部地点×features 上线性查找（工位那条先例同样如此）；账户审计时 O(账户×特征)。建议用与 workstation 共用的一次性索引。无特判，锚点规则本身（环境要素账户锚在持有它的地点）没问题。
N8. tests/s5-law-subsistence.test.mjs:32 与 s5-law-water-source.test.mjs:23 的夹具给 A 塞了 1000 柴，目的是让既有水/粮分配测试不受新增柴需求干扰。可以接受，但这使"柴需求与粮/水争同一工时"没有任何测试覆盖。建议补一条：同时缺粮、水、柴时，分配顺序与工时上限成立（水、粮优先，柴只用在家时段，不超出 WORK_WINDOWS 末端）。
N9. tests/ledger-stock.test.mjs:76-86 新增测试只调用既有 transfer/auditLedger，不碰本批任何生产代码，对本批改动没有保护作用，更像为 N17 论证造的例子。保留可以，但不应作为 N17 的证据；建议改为覆盖 bookedBy / books.booked 判定（见 N10）。
N10. stock.mjs:119 `books?.booked===true` 与新 bookedBy：全仓 grep `booked` 只有 BOOKED 常量与 bookedBy 带该字段，其余是 status 字符串、变量名，没有被误跳过的写入；money.mjs 自有 BOOKED 不经此判定。逻辑成立。缺一条单测：bookedBy 的写入不产生 drift、不重复记账（以及 {booked:false} 不被跳过）。
N11. tests/settlement-trade.test.mjs:101-106 新分支：只认 booked===true 且 writer/purpose 精确匹配且 delta>0，核心断言未放宽。可接受；注意它是按 writer 名白名单写的，今后任何新的合法家户入库都要再加一支，建议改为按"books.booked 且带 writer 标注"的通用口径并仍要求正向 delta 与账本来源可查（对照 forest:/site: 账户减少量），而不是写死 household-subsistence。
