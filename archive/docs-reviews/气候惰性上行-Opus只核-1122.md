## 2. placeView / placeFootprint 按需求值

- **过（值）。** placeFootprint（:285–:308）的四个惰性属性都闭包了调用当时的 plan、rows、seed、terrainOf，求出的值和改前在调用时立即求的一样；对象冻结后访问器照常工作。placeView 的 dims 用 defineProperty 按原来排好的键序插入，键序不变。基值 placeDimBase 仍在调用时读，所以 dim() 抛错（含 E-MOD-RX 的分流）的时机不变。
- **过（缺口）。** 这条路径没有缺口登记：dim() 和高度场都是纯读，不写 state、不往 engine 记任何东西（dimensions.mjs 里没有 gap 登记的写法）。所以不存在缺口登记时机变了的问题。
- **过，附说明（错误码时机）。** 高度场里还会抛错的只有三类：rules.grid 配错（heightCtrlK 不是正整数时除零，reliefOctaves 超出定点分辨率时 grid.mjs:168 抛 E-DET-DOMAIN），以及水体 downstream 成环（water-bed.mjs:90，生成期已由 gen/water.mjs:102 拒收）。在能通过加载、rules.grid 取值正常的世界里，这些都到不了。配错的情况下，报错从"调用 placeView/placeFootprint 时"挪到了"读 elevationM/zRange 时"，错误码不变。生产代码里 placeView 没有别的调用者（server-plugin 里只有 place.mjs 自己用），生产唯一的读者 placeClimateInput 一定会读单元的 elevationM，所以同一个配错照样在同一次调用里抛出。改前 placeClimateInput 还会因为单元以上的祖先（世界根）的出口或高度场报错；那些报错跟卷二十 :335 定义的输入无关，改后不再抛，我判合理。heightCtrlK 那一类由下面"必须改 1"一并堵上。若主会话按卡文第 2 条字面从严，改法是在加载期校验 rules.grid 的 heightCtrlK 和 reliefOctaves，让运行期根本到不了这些报错。这会多出一项加载校验，是否要做由主会话定。

## 3. grid.mjs controlSurfaceAt

- **过（缓存）。** WeakMap 的键是控制点数组对象本身。生产上的两个来源都不会改数组内容：footprint.mjs:505–:516 controlPointsOf 建好后存进 plan.controlPoints，之后不再改；grid-base.mjs:85–:101 nearControlPoints 每次 filter 出一个新数组（每次都是新键，只是不命中，结果不受影响）。计划重划会产生新数组，旧缓存随 GC 回收。没有跨数组、跨加载的状态。风险只在于以后有人原地改写同一个数组（push、改 elevM）时缓存会过期，见建议 1。
- **过（平局次序）。** :218 的 before 是严格小于。:226 插入时只越过严格大于自己的元素，所以等键的元素保持输入次序，和 Array.prototype.sort 的稳定排序一致。:224 表满时，候选不严格小于末位就丢掉，等于稳定排序里排在后面的那个被截掉。和旧的"全排序后取前 k"等价。
- **过（测试覆盖平局）。** 随机比对把控制点放在 7×7 的格点上，查询点放在 25 米格点上，距离平方并列很多，并列时按 id 排序（id 互不相同）。K 从 1 到 5，第 K 名和第 K+1 名等距的情况会大量出现。同 id 并列没有覆盖，生产上 id 来自 plan.cells 的键，是唯一的，不需要覆盖。
- **必须改 1：grid.mjs:224 在 heightCtrlK 不是正整数时与旧写法结果不同；写者自查第 3 条"k<=0 的旧行为保留"不准确。** 旧写法是 `slice(0, k)`：k 为负数时得到"去掉末尾 |k| 个"，照常能算出值；k 为 NaN 时得到空集，接着除零。新写法：k<=0 一律空集，接着除零；k 为 NaN 时 `>=`、`>` 比较都为假，于是全部控制点都入选，照常算出值。k 为小数（如 2.5）两边一致。heightCtrlK 没有任何加载期校验（server-plugin 里没有，grid.json:34 只有值），属卡头二.3"特殊值不能绕过"。改法照现有口径（place.mjs:458、:726 对 landSearchRadiusCells 的写法）：在 controlSurfaceAt 入口拒收不是正安全整数的 heightCtrlK，报 E-RULES-UNREGISTERED。grid-control-select 补一条 0、−1、NaN、2.5 被拒收的用例。这样逐位不变的承诺在合法域里成立，非法域明确拒收。改完照规矩再核一次（Sonnet 一轮即可）。

## 4. 不另造里块缓存

- **过。** footprint.mjs:633–:655 regionHeights 按 `${worldSeed}|${id}` 缓存在 plan.heights 上（footprint.mjs:406 建计划时新建）。计划本身缓存在 place.mjs:165 的模块级 WeakMap 里，键是表对象，命中还要求 rules、vocab 是同一个对象、sig（当日有效输入版本加偏离行）相同（:174–:178）。输入一变就重划计划，plan.heights 随之丢弃；重新加载会得到新的表对象，WeakMap 不会命中旧的。没有跨加载的全局状态。卷五 :499 原文是"可按里块缓存"（可以，不是必须）。气候读路径只需要整行的平均值，现有的按行缓存已经满足复用与失效要求。写者的说法成立。

## 5. 剩余开销与卷文读法

- **卷文读法（过）。** 卷二十 :336 `env.climateTempC` 写的是"单元 annualMeanTempC + gradient ×（地点 surfaceRefElevationM − 单元所在地点 elevationM）"，:363 写"单元所在地点海拔处的年均温"。卷五 :107 定义 elevationM 为"区域足迹取足迹内各区格代表地表高（区格中心的 h）的平均"，:499 规则 13 重申区域足迹"一律在区格粒度上算……一个郡的派生量是区格数量级（10⁶ 上下），可按里块缓存"，并明写读者含"卷二十的海拔修正"。卷二十和卷五都没有给单元另设海拔字段，也没有让单元读 anchorElevationM（卷五 :103 写明那是"高度场在本行处的控制海拔"，是生成输入）。所以"单元节点足迹平均地表高"是卷文唯一的读法，实现没有读错。要更快（比如改读 anchorElevationM，或单元行自己声明海拔）就得改卷二十 :336 或卷五 :107，属于 **建议，须裁定**，见建议 3。
- **挡不挡块 6。** 不挡正确性和功能验收。读数是对的，每次加载只付一次（按计划缓存），之后同一世界、同一输入不再重算。量级也在卷文预期之内：卷二十七 :692 给"派生一个里块（100 区格）的区格层"的暂定预算是 10 ms，垄渠郡约 1.0×10⁶ 区格，约 1 万个里块，合计约 100 秒。写者实测每区格 0.11 ms，约合每里块 11 ms，和预算持平。但从可玩性看，每次开档第一次读温度要卡一到两分钟（写者独占估 1.8 分钟，并行占机实测 68 秒），这一点很明显。块 6 的试玩验收要不要设首读时延门槛，由主会话或李白定。不改卷文的出路有两条：开档时在后台预热；或者按卷五 :499、卷二十七把派生缓存进存档或分片（要看卷二十七存档分片口径是否允许派生缓存落盘）。见建议 3。

## 建议（不挡合入）

1. grid.mjs:191 的注释写了"控制点数组构造后不再改"，但 controlSurfaceAt 是导出的纯函数，调用者可能原地改数组。可以在 footprint.mjs controlPointsOf 里对 out 做 Object.freeze（元素也冻结），让"不再改"由语言保证，缓存就不会过期。只是加固，不影响现有读数。
2. placeFootprint 的 JSDoc（place.mjs:260）已写明哪些属性是读到才求。可以再补半句"高度场的规则表配错时，在读这些属性时才报错"，给以后 kernelApi 的调用者看。
3. 首读开销要不要再降，须裁定。选项一：卷二十 :336 改单元海拔的读法（比如读单元行的 anchorElevationM）。这要改卷文，而且会改变读数（控制海拔不等于足迹平均地表高）。选项二：不改卷文，开档时预热，或按卷五 :499、卷二十七让里块派生缓存落盘。写者回报里提到的"格点噪声按里块共用"约省两成，可以作为技术自定项。
4. 不是本卡引入的问题，顺带记下：place.mjs:1373 用自身的 elevationM 充当卷二十 :336 的 surfaceRefElevationM（后者在 _unbuilt-derived.json 里登记为未建）。区域足迹两者定义相同（卷五 :107 与 :113），但建筑、房间、体积足迹不同：elevationM 是 zMin × 层高，surfaceRefElevationM 是所占各列地表高的平均，室内地点的气温海拔修正会因此偏差。建议另开卡或记进 docs/问题.md，本卡不动。
