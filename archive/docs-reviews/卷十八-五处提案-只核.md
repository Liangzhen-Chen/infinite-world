# 卷十八 五处提案 只核

- 被核：`审查/卷十八-五处提案.md`
- 依据：`收尾待办.md` :384–388（李白 11-14 卷十八五处裁定）；背景 `审查/配合项落地-卷十八-优先-只核.md`
- 只核者：claude-opus-5-5 中档。只读，没有改任何卷正文或脚本；本文件是唯一写入。

## 结论：不通过

第一处的 R18-1.12 两句改法确实解决了原只核真问题 4，四个派生量也都是数值维度、句柄走规则表键，不读文字。但第一处的占手数公式会让多手器械谁都拿不起来，“没有 `weaponClass` 不能手持”又把盾和投射器排除在外。第三处名义上按类，实际分类与所说的判据对不上，效果等于点名斗殴、成婚两个动词，违反裁定。第五处的推荐项与“优先复用、不新造”相反。

## 真问题

1. **第一处，多手器械拿不起来（1-A 甲乙两案都有）。** 写新边时求值集合只加“这一条新边”。第一个人去握 `hands` 为 8 的撞槌时 `wielders`=1，占手数 ⌈8÷1⌉=8，大于可用肢端 2，拒写。以后每个人都是“第一个人”，所以永远握不起来，R13-15.2（卷十三 :1107）“多人合握”无法实现。乙案“独握时 `grip` 等于 `hands`”也是同一个结果。要先补上“合握怎样起手”（例如同一事务里成批写边、对整批求值，或者人数不足时允许握而不可用），再谈甲乙。
2. **第一处，盾和投射器挂不上手持边。** `weaponClass` 的适用范围是 `byClass:comp_weapon`（卷十三 :223），盾是 `comp_guard`（:224、:242“盾、可招架的兵器”），投射器是 `comp_launcher`，两者都不必有 `weaponClass`。提案把“盾必须带武器类别”说成“数据要求、不另立规则”，实际上是要求所有手持物都挂 `comp_weapon`。这与 R13-5.2“一手兵器一手盾都是两条手持边”、R13-10.6“持投射器的、持格挡物的”（:903）相冲突，等于改了规则。占几只手应当覆盖整类可握之物，不能只读武器类别。
3. **第三处实际是点名，不是按类。**
   - 乙类判据是“恒在一个卷九动作的同一事务里发出，载荷的 `EventId` 指向那个动作”。但成婚是在婚约合同**履行时**写入的，`consentAct` 记的是婚约**订立**事件（R18-2.3，卷十八 :646），不是同一事务里的动作。按提案自己的判据，成婚不属于乙类。
   - 反过来，离异“是一个动作”（R18-2.4 :647），授予荣誉“是组织首领或职位的动作”（R18-7.6 :921），除名“是首领的动作”（R18-3.1 :699）。三者都在动作事务里发出，提案却因为载荷里没有 `EventId` 字段而划进丙类。
   - 结论：判据实际看的是“载荷有没有某个字段”，不是提案所说的发出点。分类结果只有斗殴、成婚为真，其余全假，效果等于逐个点名。另外，甲乙丙三类不是已登记的分类（:183 只登记了发出系统），是提案新立的。应当按已登记的发出点统一判：在卷九动作事务里当场落定的为一类，固定刻、派生、别的写入发出的为一类，再把各行重新归类。
4. **第五处推荐项违反“不新造”。** 乙案要新登命名 struct `struct:subjectRef`，还要在卷十八新立一个封闭枚举（`on` 的两个值）。甲案只用已有的 `EntityId`、`EventId`。裁定原文是“类型优先复用卷二已登记身份键类型，不新造”，所以推荐项应当是甲。若坚持乙，必须证明甲行不通，提案没有给出这个证明。卷二 §1.5（:182）也确实没有现成的“实体或事件”联合类型可以复用，`refs` 不行（事件 id 没有前缀）。此外，卷十八的封闭枚举是“代码内封闭枚举，值不带前缀”（:142），提案写“带前缀代号”，与本卷口径不一致。
5. **牵连清单缺两项。**
   - 卷十八 §2.4 的 rx 可读变量表（:240）。§4.1.1 :411 规定 `holdWhile` 的“变量名与取数归登记该行的卷”，而手持行登记在卷十八，`holder.handsHeld` 等四个变量要进这张表并写明绑定入口。清单里没有这一行。
   - 卷九 R9-13.9（:1052）。新谎言的 id 要到说谎动作落定才产生，可是决定卡在落定**前**就要带“登记的谎言 id”。提案写“不改”，但没有说清这个先后顺序怎样成立。

## 逐处核

### 一、`holdWhile`

- **是否只读数值维度与固定代号：是。**
  - `graspLimbs`、`handsHeld`、`wieldHands`、`wielders` 都是 derived integer count。
  - 能力句柄取规则表键 `rules.combat.roles.graspCapability`（`ref vocab capability`）。
  - 表达式里没有文字，也没有种类代号。
  - 卷四 P-5 (c) 禁的是 `bodyView().dims` 里由 `rules.capacity` 点到的那几项能力值，`graspLimbs` 不读它们，不触禁。
- **R18-1.12 两句改法：解决了原真问题 4。**
  - “写入后求值”堵住了放过超限。
  - “按建立先后逐条放回”避免了整人关边。
  - 例子已验算：可用肢端 1，手上一把双手兵器、一面盾。不论先拿哪件，结果都是双手兵器关闭、盾留下。
- **是否超出五处：没有。** “未知按假”和两句 R18-1.12 都属于 `holdWhile` 本身。
- **问题：** 真问题 1、2。另有小项：
  - `handsHeld`、`wielders` 被定义成“按求值集合计”，值随调用场合变化，不再是状态的函数。这不像一个登记维度。建议维度按现状定义，假设状态由 R18-1.12 按 §2.4 的绑定方式给出。
  - `eff(p)` 不在 `bodyView().parts` 里。`parts` 只含质量与材料（卷四 :335）。`eff(p)` 要由 `dims.partIntegrity`、祖先链和 `rules.body.integrity.lostBelow` 算出（B-3，:452）。
  - “`eff(p)` 只在事务里变”这一句成立：完好度只取状态实例当前档的修正（B-2 :451），换档由写者在事务里发事件（卷二十一 :1333）。

### 二、`functional` 两行取真

- **先例引用准确。**
  - 取真五行：:499、:505–507、:514 逐行核对无误。
  - 取假成员类：:497、:509–511 无误。
  - R13-10.2 三种兵出自合同：卷十三 :899 无误。
  - 监护失能由 `functional` 加候补顺序处理：:1378 无误。
  - A13-14.2“能行动”：:1091 无误。
  - 说明：“经营＝亲自使用”“受雇＝凭契约提供劳务”是提案自己的概括，卷十八没有这样的原文定义。
- **小项：** “持续行动”判据的反例不止提案坦白的看管、操控两行，还有 `hk_mentor_of`（师徒，`grants: schedule`，`functional` 取假，:516、:584）。如果把这条判据写进 §4.1.1 含义栏，就会和现有数据行相矛盾，而且超出五处。建议删去这一可选项，两行只凭同类先例取真。两格的结论本身没有问题。

### 三、`perceivable`/`senses`

- 见真问题 3。判据和归类自相矛盾，效果是点名，违反裁定。
- 先例核对：
  - 卷二十三 :201 押注赢、押注输取 `perceivable` 真、`senses` {视}，与提案所述一致。
  - 卷二十四 :991 告示事件取 `perceivable` 真，一致。
  - 表 B :169–170 一致。
- `sense` 族已登记，前缀 `sense_`（卷五 :165）。提案只写“视听两通道”、没写代号可以接受，但落正文时要写出代号。

### 四、立嗣定为收养

- **先例：** 全书没有“收养发事件”的先例。收养只出现在 :632、:677（“按制度行收养”）、:699、:972、Q12。提案只类比了分家、监护变更“kin 发事件、边由写者写”的写法。
- **小项：** 亲子记录由内核关系写者写（:320），kin 怎样进入那一笔事务，提案没有交代。R18-1.10、R18-1.11 的先例是由写边者自己发事件。
- **是否须选：不必。** 立嗣从 v1 起就在 :183 名单里，R18-8.4“收养后重新求值”需要一个事件来触发，删除这一行会留下缺口。现有条文已经决定了甲。

### 五、`lieId`、`subjectRef`

- **`lieId` 复用 `EventId`：合规。** 卷二十四表 A（:133）、卷十八 `consentAct`（:189、:411 后的公共键）已把 `EventId` 当类型用。`EventId` 不在卷二 §2.8 的品牌清单里，是旧缺口，提案已如实说明。
- **建议：** 写明“一次说谎动作只登记一条谎言”这一不变量。R9-13.9 规定每张决定卡带一条，所以这一不变量成立，但要写出来。
- **`subjectRef`：** 见真问题 4。
