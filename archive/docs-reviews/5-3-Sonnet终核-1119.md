### 必须改 1：缔结类种类（concluded）的转移与改份额新增持有人，没有任何入口能带"本笔同意"，实际永远拒收
- 现状：`server-plugin/kernel/holdings.mjs:605–610` 转移时先剔除旧边的 `consentAct/origin`，再 `checkConsent(row, terms)`（:410 只认 `terms.consentAct`）。但 `transferHolding` 的 input 只有 `{id|三元, newHolder, cause}`（:580–:590 文档与 :593–:599 读取），没有任何字段能把本笔事务的同意事件编号交进 `terms`；`rescaleHolding` 新增持有人同理（:657–:660，input 只有 `shares`、`cause`，primitives-runtime.mjs:253/:263 的适配器也不传）。
- 后果：词表里 `hk_owns`、`hk_share` 均为 `concluded: true` 且 `transferable: true`（_vocab.json 263/264 行）。所有权转移（卷十八 R18-1.5 的"带同意条款动作"本应成立的最典型一路）与份额新增持有人，在运行期没有一条能成功的路径——"不复制旧同意"改成了"永远拒"。这不是 R18-1.5 的原意（卷文要求"本笔事务自己的同意"，不是"禁止"）。
- 证据：holdings.test.mjs 的正向转移用例（:288 起）用的是非缔结的测试种类 `hk_test_move`；缔结类只有拒收用例（:316、:265），没有一个"带本笔同意后通过"的正向用例。开边 `openHolding` 因为 input 带 `terms` 能走通同意，转移与改份额是漏的。
- 要求：转移与改份额的入口接受本笔同意（例如 input 带与开边同形的 `terms.consentAct`，进承接边/新增边的 terms），仍不复制旧边的 `origin/consentAct`；补两个正向用例（缔结类转移带同意通过、改份额新增持有人带同意通过），期望值手算。按卷九 §4.2.1 的 holding 原语入参核对 primitives-runtime 适配器是否需同步（卷文未列该字段时，写"卷文推不出"报主会话，不自补）。

### 必须改 2：engine 未交入时提交前重算静默跳过（绕过口子）
- 现状：`recompute` 在 `engineRef` 为 null 时直接 `return`（holdings.mjs:759–760）；`touchedFrom/kindRowFromState` 也在无 engine 时返回 null（:751–:755）。d34e1c2a 删掉了四个写者入口里的 `engineRef = engine`，改成只靠 `installHoldingEngine`，而装配文件尚未建（注释写"挂 5-7"）。
- 后果：任何代码路径调用了四个写者（它们自己拿着 engine 参数）但没人调过 `installHoldingEngine`，holdWhile 重算与新边求值就整段不执行，不报错——正是卡头第二节第 3 条"不留绕过口子、不静默跳过"。此前入口里赋值至少保证写者调用后必有 engine。测试靠 `fresh()` 每例手动装，没有任何用例证明"未装即拒"。
- 要求：写者入口（四个）在 `engineRef` 为空时整笔拒收（如 E-ACT-WRITER-NOT-READY，同 admission 未接线一类处置，不静默），并补一个"未装 engine 时开边拒收、状态不变"的用例。入口里可以比对传入 engine 与已装 engine 不一致也拒，但不是必须。

## 1. 缔结类转移/改份额的本笔同意：改对
- `issuedConsent`（holdings.mjs）只取 `input.terms.consentAct` 一个键。值须为代号或 null，否则拒 E-HK-PROTOCOL。terms 不是对象也拒。其余入参 terms 一概不取，所以不会借此带入 origin 等字段。
- `transferHolding` 先剥掉旧边的 consentAct/origin，再写入本笔 consentAct，随后 `checkConsent` 照常把关。`rescaleHolding` 新增边同理，base 剥掉旧 origin/consentAct，再经 `prepareTerms` 走完整字段核对。
- 用例：新增两个正向用例（转移、改份额）。断言新边 terms 是字面量，consentAct 为 'act_new_consent'，且没有 origin。原拒收用例（旧边 seeded/consentAct 不被继承，拒 E-REL-CONSENT）保留并通过。
- 非缔结种类：consentAct 写 null，与既有 terms 形态一致（hk_wielding 用例）。没有为缔结类单开分支，全程读 `row` 字段。
- 适配器处置：卷九 §4.2.1 :630/:635/:636 原语契约确实没有 consentAct 字段。执行者只在内核写者入口接受，不自补适配器，并报"等李白裁定"。这合卡头第二节第 1 条（卷文推不出即停下，不自补）。同时没有留下绕过口子，因为适配器不传时仍然拒 E-REL-CONSENT。该处置可接受。
- 遗留（不拦封）：适配器层暂时传不进 consentAct，缔结类转移/改份额经原语只能被拒，要等李白裁定后补契约。这是已报的待裁项，不是缺陷。

## 2. needEngine 与提交前重算：改对
- 四入口（open/close/transfer/rescale）在 needTx 之后即调 `needEngine()`。engine 空时抛 E-ACT-WRITER-NOT-READY，且在任何写之前，状态不变。用例断言状态 JSON 与事件簿均不变。入口收到的 engine 参数不充数，只认 installHoldingEngine 交入的。
- `recompute` 无 engine 时：`writesHolding` 检查本笔 written 路径。第一段是 holdings，或任一段等于现役边的 holder/subject id，即拒。其余事务照常提交。
- 误拒与漏拒：
  - 漏拒：保守取全部现役边两端，是 holdWhile 可能挂的边的超集。持有边本身（holdings 路径）也拒。engine 缺失时本事务里新开的边只能来自四入口，它们已先拒。无漏。
  - 误拒：只有本笔路径含任一现役持有端 id 的事务才会拒，范围比"全部拒"窄，且是宁多勿漏的取舍。无 engine 时读不到种类行，没有更精确的办法，这是保守取舍，注释已写明。未碰持有端的用例（npc_b）照常提交。
- 属性：`written` 条目非数组时 continue 略过。这些条目由事务本身记录，形态由内核保证，不构成绕过。
