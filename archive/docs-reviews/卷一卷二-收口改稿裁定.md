## 结构裁定（两卷都按此写，卷二为定义方，卷一只引用）
1. **两进程模型**
   - 服务端进程（Node）：kernel、规则层、inputEdge、gate、aiGate、outputGate。
   - 客户端进程（浏览器扩展）：host、display。
   - 信任边界在两进程之间的 HTTP 通道。
   - outputGate 把 `Screened<Text>` 序列化为“已筛信封” `{screenId, text, digest}`，并作为登记过的出口发出。
   - 客户端只能通过 host 的登记入口接收信封，由客户端版 textcore 校验 screenId 和 digest 后，还原为客户端的 `Screened<Text>`，再交给 display 写 DOM。DOM 出口归客户端 display 组。
   - 玩家打的字从客户端以 RawText 发往服务端 inputEdge 的登记入口。
   - 两进程各有一张 import 矩阵和一张全局白名单。
2. **宿主能力不经全局访问**
   - 客户端只有 host/bootstrap 这一个文件可以直接访问 window、document 和 SillyTavern 上下文。它把需要的能力打包成能力对象，以参数形式交给 display。其余模块凡是经属性访问宿主全局（window.x、getContext 等）的，一律违例。
   - 服务端可用的 node:* 内置模块和 npm 包，按组列入 import 矩阵的白名单。JSON import 只允许出现在登记过的加载器里。
   - tools/ 是离线组，有自己的白名单，运行时任何组不得 import 它。
3. **定时器**
   - 墙钟定时器只许 host（客户端）和 kernel/scheduler（服务端，用于 AI 超时、心跳）使用，并且要经能力对象注入。
   - 世界时间一律由卷二十的时钟推进，不得读墙钟。
4. **摘要算法**：Sealed 的 digest 用 sha256，只在服务端计算，来源是 node:crypto，仅 textcore 服务端版可用。客户端只做核对，用 SubtleCrypto，也仅 textcore 客户端版可用。
5. **起名流程**
   - 规则层不写入任何东西，只发出“命名意图”事件 `{targetId, slotCode}`。
   - 实际写入由 aiGate 完成：筛查之后，凭 kernel 签发的凭证写入。
   - 生成名在 state 中只存 nameParts 代号，计入哈希。玩家起的名存 displayNames，不计入哈希。
   - 世界状态不得随语言包而变。
6. **实体终止协议**（死亡、消亡、毁坏的通用收尾流程）由卷二定义为通用原语；各领域卷只登记触发终止的条件。
7. **凭证与哈希口径**：一律以卷二第十二版 §2.9 为准，卷一相应条款（含 V-13）照此改写，改不通的就删除或重写。
