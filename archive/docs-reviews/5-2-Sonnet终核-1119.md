### 必须改 1：整刻作废按"追加前条数"截日志，会连带抹掉刻内穿插的请求条目
- 位置：`server-plugin/kernel/transaction.mjs` registerLogUndo（约 :37）与 rollback 的 logUndo 循环（约 :56–:60）；对照 `submitProposal`（同文件约 :187）。
- 卷文：卷二 §2.6 :512 "只有请求条目在回滚范围之外"；卷二十七 R27-7.3 :668（被拒请求按编号留在输入序列里）；卷二十 §4.1.3 :523／:525。代码自己的注释（刻日志一节）也写"被拒请求的条目记在日志簿上……不受影响"。
- 问题：`logUndo` 只存 `{book, length}`。`submitProposal` 先 `appendLogEntry` 请求条目、再开事务，事务提交后留在刻日志里。同一刻里，前一笔事务 emit 后（记 length=5），后一个请求条目落在 index 6，再有第二笔事务 emit（记 length=7）。`rollbackTickJournal` 倒序截到 7、再截到 5，index 6 的请求条目被一并删掉。
- 单笔事务回滚不受影响：请求条目在事务开始前已落，事务内不会穿插。出错面只在刻级作废，而刻级作废正是 5-2 新加的。
- 现有"整刻作废"测试（events.test.mjs :302）只放了两笔 emit、中间没有请求条目，没覆盖。
- 改法（落在原语层，不加设计）：`logUndo` 存本事务追加的条目对象引用，不存长度。回滚时按引用从 `book.entries` 里 `lastIndexOf` 删去，只删自己追加的，不动别人的。再补一条测试：刻内先 emit、再 `submitProposal` 一个请求、再 emit，整刻作废后只剩请求条目。

## 逐点
1. registerLogUndo / rollback / rollbackTickJournal（server-plugin/kernel/transaction.mjs:38-63、:91-96）
   - logUndo 存 `{book, entry}`，entry 是 emit 追加后从 `book.entries[idx]` 取出的条目对象本身。
   - `appendLogEntry` 在 save.mjs:430 把条目 clone 后 push，返回下标。emit 取 `book.entries[下标]`，这就是日志簿里的实际对象，引用有效。
   - rollback 倒序遍历 logUndo，用 `lastIndexOf(entry)` 加 `splice` 只删自己的条目。请求条目是另一个 clone 出来的对象，不会被误删。
   - 单笔回滚和整刻作废走同一个 `rollback()`：rollbackTickJournal 把 tickJournal 当 tx 交给 rollback，事务提交时 transaction.mjs:145 把 tx.logUndo 并入刻日志。
   - 同一对象不会两次进 entries：appendLogEntry 每次 clone，emit 另有按 id 的撞号检查。冻结发生在登记引用之后，不影响 `lastIndexOf`，因为比的是引用。
   - 回滚后条目下标会前移，但按引用查找不依赖下标。tickEnd 的 sealedCount 只在整刻处理完后用，回滚发生在这之前，不受影响。
2. 新测试（tests/kernel/events.test.mjs:319-345）
   - 流程是刻内 emit、submitProposal 请求、再 emit，然后 rollbackTickJournal，断言只剩原请求条目（同一引用）且 request 编号仍为 42。
   - 这是行为断言，期望值来自测试里自造的前提，不依赖仓库偶然数字。
