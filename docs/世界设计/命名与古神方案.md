## 0. 一句话与四条口径

产品负责人定的四条，本稿一条条落地：

1. **十二位原创神保留，名字改口语**，一看就知道管什么；不用生僻字和硬凑的两字雅词。中式圈与西式圈各有叫法，同一位神在不同圈可以有不同称呼（§2）。
2. **每个文化圈另加 2–4 位现实中存在过、有史料的古神**，只存在于宗教与朝拜系统，对玩家最多对话与赐物（`interactionCap ∈ {talk, gift}`）；不能显现、召请、契约、驱使，更不能有式神、图腾神、化身。城隍、土地等职位神不是现实信仰对象，仍可完整互动（§3）。
3. **地名、人名、店名、族称统一改口语**，规则写进文化记录数据，生成代码只读数据（§4）。
4. **中式与西式一眼可辨**，各圈用各自的音系与构词（§4.3 用可测的字集判别来保证"一眼可辨"）。

另外三件事一并交代：重字清单（§5）、红线改写（§6）、存档兼容（§7）；波及面（§8）与实现卡和排期（§9）；需要人拍板的点（§10）。

**三条先说在前面的发现**：

- **现有红线与第 2 条冲突**。13 §13.1（docs/架构设计/13-超自然与文化圈.md:13）明写"不区分历史神话 / 在世宗教——古希腊、北欧、埃及、凯尔特、斯拉夫、古代美洲等今天也有信仰者"，且是"用户最终规则（三次修正后）"。第 2 条等于推翻这一句，必须由人明确批准，§6 给出改写全文。
- **选古神要小心"今天仍有信仰者"**。凡古宗教，几乎都有现代复兴团体。本稿把名单分成"主名单"（没有连续传承的在世教团）和"备选"（有较活跃的现代复兴），主名单不含后者，由人最终拍板（§3.2、§10）。
- **命名现在是"代码里写死 + 从散文里用正则抠"**：remote-generation.mjs 有一整套写死的字库与按文化 id 的分支，甚至靠 `name.startsWith('锉')` 判断物种（§4.1）。所以第 3 条不是改几个名字，是把命名搬进数据，这正是 12 册 §3.3/M3 要做而尚未做的事。

### 1.3 神灵互动现状（古神规则要挂的地方）

- 神是 lore 目录条目（`category:'deity'`），不是 state 里的 agent。`devotee_of` 的 subjectKinds 是 `collective`（教团），不是神本身（world/ontology/holdings.json:594–）。现有所有动作的目标槽（`slot kind:"entity" entity:"person"`）都指向人、生灵，没有一个能点到神。所以**第 2 条的硬上限现在没有可违反的入口**；它是给未来 04 册（神作不在场 agent、香火账户、托梦神谕、aspects）落地时设的闸，要在那之前先立好。
- 04 §3.2 设计里的 `forbidden: {vitalTarget, commandsTarget, sealsTarget}` 已经有"神不能被杀、被驱、被封"这条，但它只管原创神；古神要加的是另一条更窄的线（只许对话与赐物）。

## 2. 十二神对照表

### 2.1 命名规则（数据，不是特判）

- **中式叫法**：`{职司}{公 | 爷 | 婆 | 娘娘}`。职司取两三个字、日常说得出口的词（田、保人、井水、护林、寻迹、救船、守夜、分水、匠头、河界、回家、念亡）。
- **西式叫法**：`{职司}之{主 | 母 | 父}`。
- 两个叫法都写进 `deities.json` 每条的新字段：
  ```json
  "name": "守夜爷",
  "names": {"zh": "守夜爷", "west": "长夜之母"},
  "namesByCulture": {"culture_north": "west", "culture_forge": "west"}
  ```
  `name` 是缺省显示名（中式），`names.west` 是西式叫法，`namesByCulture` 只在需要例外时写。显示规则：看**观察者所属文化的 `naming.style`**（zh / west）取 `names[style]`；找不到取 `name`。这是一条按字段读的规则，不是按神写的分支。
- 性别只是称呼口味，没有机制含义。
- 草原、林冠两圈没有第三种叫法，先按西式叫法读（`naming.style` 取 west）；是否要为它们另造本圈叫法见 §10。

## 3. 现实古神与互动硬上限

### 3.1 选择原则

- 必须是现实中真实存在过、有史料可考的古代神灵：有铭文、文献、祭坛、祭祀简牍或考古实物，并记出处（沿用 13 §13.1 第 1 条"有出处才收"的形状，`sources:[{work,section}]`）。
- 优先选**没有连续传承在世教团**的古宗教（美索不达米亚、伊特鲁里亚、赫梯-安纳托利亚、战国楚地、罗马时期高卢-日耳曼地方祭祀）；有较活跃现代复兴团体的（埃及、日耳曼北欧）放进备选，由人拍板。
- 不选：现行宗教的正统崇拜对象（佛、道三清、上帝、真主等），沿用 `orthodox_worship` 排除档，另外 03 §9 已排除的"奥丁、托尔、宙斯"仍排除。
- 不选"天"这种非人格化上位（04 §2.4 已定草原的天不作神实体，所以不选斯基泰的天父帕帕尤斯）。
- 不选与职位神重叠的（不选"司命"：民间灶神又称司命，会与 `office_hearth_god` 混淆；不选河伯：河伯已是 `office_river_lord`）。

### 3.3 数据规则（按类，不按单个神）

`deities.json` 每条加字段（新字段，原有字段全保留）：

```json
{
  "id": "deity_anc_telipinu",
  "name": "特利皮努",
  "category": "deity",
  "kind": "historical",
  "realWorldFigure": true,
  "interactionCap": "gift",
  "tradition": "赫梯（安纳托利亚）",
  "sources": [{"work": "《特利皮努神话》", "section": "CTH 324"}],
  "livingRevivalNote": "无已知连续传承教团；人审核栏",
  "culture": "culture_river",
  "sphere": "sphere:marches",
  "domains": ["丰产", "生殖（谷物、牲畜）"],
  "worship": {"shrineKinds": ["open_air_altar"], "offerings": ["goods:milk", "goods:fat"]},
  "gifts": [{"item": "item_xxx", "pool": "acct:deity_anc_telipinu:gift", "cooldownDays": 30}]
}
```

- `kind`：枚举 `original`（十二神）、`historical`（现实古神）。职位神不进 deities.json，进 divine-offices.json（04 §5.1），自带 `kind:"divine_office"`。
- `realWorldFigure`：布尔；**为 true 当且仅当 `kind:"historical"`**。城隍、土地、灶神等永远没有这个字段。
- `interactionCap`：枚举 `{talk, gift}`；`realWorldFigure:true` 时必填，否则不允许出现。含义：
  - `talk`：神可以开口——托梦、神谕、祈祷的应答、被询问时回答（04 §10 的 tell 通道）。只产出文字与已有的事实标记，不产生"在场"。
  - `gift`：`talk` 加上赐物——从该神的赐物池账户转出一件物品给玩家（账户与守恒规则同 04 §4 的 `src:offering_realm` 做法，池子有限，有冷却）。赐物只给物品，不给状态加成、不给能力。
  - 现有的"信徒向神供奉、布施、朝圣、入教"是**玩家对神职场所的行为**（faith_give、faith_rite、faith_pilgrim、faith_convert），任何古神都允许，不算互动，不受上限管。
- 现实古神**不得带**：`miracle`、`aspects`、`offices`、`church.organization` 中任何处分权、`forbidden` 以外的任何实体化字段；**不得是十二神的"面"**（04 §3.2 `aspects` 只能引用 `kind:"original"`）；**不得有生灵模板**。
- 古神可以有：圣所、神龛（地点实体）、祭司职业与教团的**供奉职能**、节日、信徒（`devotee_of`）、传说与知情层说法。

### 3.4 动作入口与拦截（用 grep 找出的现有入口）

**原则**：不是每个入口各写一条"古神不行"，而是**动词分类 + 一张数据表 + 一个闸门函数**。

1. 数据表（放 world/rules/tables/domain-rules.json）：
   ```json

     "classes": ["worship", "talk", "gift", "manifest", "invoke", "contract", "command", "familiar", "totem", "avatar", "possess"],
   ```

   表里没列的类，对古神一律拒绝（默认拒绝）。
2. 每个动词、持有种类、法术效果种类、原语在登记时声明 `deityClass`；未声明的，对 `realWorldFigure` 目标按默认拒绝。声明写在数据里（actions/*.json、ontology/holdings.json、spells.json 的 effectSpec、ontology/verbs.json）。

### 3.5 城隍、土地为什么不受这个上限

- 区分字段：**`kind`**。城隍、土地、灶神位、山神、河伯、井主属于职位（04 §5.1 divine-offices.json，`kind:"divine_office"`），是**职位**，持有人是亡者或精灵（可更替、受贿、错判）；它们没有 `realWorldFigure`，也永远不会有。
- 上限只看 `realWorldFigure:true` 的神灵条目；职位的互动由现有职位规则（任命、考试、受贿、罢免）管。
- 这与 13 §13.1 第 4 条一致："泛称的地方神职与自然精灵照收，不描绘某一位具体受供奉的神"。古神恰好相反：他们是具体的、有名有姓的受供奉之神，所以才加硬上限。两者靠 `kind`（`divine_office` 对比 `historical`）分，不靠名字表。
- 防漏洞：加载期校验"职位模板 `id/name` 不得与 `historical` 条目的名称或别名相同"，避免有人把古神写成"某某土地"绕过上限。

### 6.3 改动理由

现实古神只放在信仰系统里、互动有硬上限，这样既保留历史文化的厚度（有出处的古神、祭祀、铭文，让每个文化圈有真实的宗教底色，而不是一律架空），又避免把真实信仰对象写成可以召请、契约、驱使的游戏工具。具体做法三条：① 只收无连续传承的古宗教；② 上限写成数据按类拦截，默认拒绝，不留"某位神可以例外"的口子；③ 职位神与古神靠 `kind` 区分，城隍土地继续完整互动，不被误伤。

**这是对原"最终规则"的明确反转**，13 §13.1:13 当年写"不区分历史神话 / 在世宗教"是用户的意思，现在由产品负责人新的四条改变它。改写要在此处留痕。

## 7. 存档兼容

### 7.1 先说结论

- **只改显示名，保留 `deity_*` 等全部内部 id**。
- 存档**不写神的显示名**：神名在运行时从当前世界快照按 id 取（faith.mjs:120 `e.byId.get(t.deity)`、faith-state.mjs:34 `god`、faith-catalog.mjs:13）。存档里存的是 `deity` id 与 `church`（教会名）、`taboo`（戒律文字）。
- **教会名与戒律文字被逐字比较**：magic-ritual.mjs:81 `f.church!==deity.church.name || f.taboo!==deity.taboo` 不等就抛"须核对真实信众、教派与戒律"；faith.mjs:120 把它们写进信仰事实。所以 NM-1 **不动 `church.name` 与 `taboo`，只改 `name` 及 prose 里的叫法**。若以后要口语化教会名，须同时改这条比较为按 deity id 比（另卡）。
- 存档**钉住世界快照**：`document.worldHash`（server-plugin/archived-reducer.mjs:8–19；consistency-service.mjs:73 `store.worldRegistry.get(state.document.worldHash)`），内容寻址存放（backups/*/worlds/<hash>.json、dist/world/<hash>.json）。所以：

| 存档状态 | 显示 |
|---|---|
| 未升级的旧存档 | 继续读钉住的旧快照，**显示旧名**；存档文件一字不动，重放结果同版确定 |
| 新开的存档 | 读新快照，显示新名 |
| 旧存档升级到新快照 | 走现有世界升级路径（archived-reducer.mjs:8–19 的 `schema_migration` → world-upgrade.mjs:36 `planWorldUpgrade`）：神灵、地点、区域是 lore 目录，直接换成新快照里同 id 的名字；居民 NPC 的 `name` 字段由 world-upgrade.mjs:47–59 按 id 逐字段比较，"存档当前值等于旧目录值"则打补丁改成新名，否则（玩过程中被改动）记入 conflicts 保留原值 |

这就是"不改 id、不动原存档文件"前提下的做法：显示名由 id 查表取，升级是追加事件而非改文件。

### 7.2 不会自动更新的名字（据实说明）

- 游戏过程中**生成并写进存档**的名字：`state.created`、`state.family.people`（entity-view.mjs:302–306 注明"NPC actor.name 是初始化副本，目录才是命名权威；created/family 叠加层除外"）、`state.remote` 远郡档案、事件摘要与编年文字、玩家自己写的笔记。这些在存档里是文字或叠加层，升级后仍是旧名。
- 按"不做旧存档兼容"的既定口径（规则只一版），接受这个；不加显示层改名表、不加版本标记。若产品负责人要求"升级后连这些也换"，那是另一件事（显示层按 id 反查），见 §10。
- 卡里要核对：升级一个旧存档，`world-upgrade` 的 conflicts 列表是否因改名产生大量冲突；若有，说明改名触达了玩家改过的字段。

### 7.3 改名对按名查找的影响

- faith-catalog.mjs:20 `t.id===id||t.name===id`、locations 按 `l.name===id` 查：玩家或模型若用旧名，查不到。因此新世界里**不保留旧名作别名**（避免旧名在检索与一致性审查里出现，造成"双重命名"），一律用新名；一致性审查对未登记专名已会报 `naming` 类问题（consistency-review.mjs:242、248）。
