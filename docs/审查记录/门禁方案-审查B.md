# 门禁提交流程重设方案 审查 B（第 2 位独立审查，监督有效性角度）

被审：F:/dnd/docs/门禁提交流程重设方案.md，140 行，sha256 94154841…c2acc3 核对一致。只读，未读审查 A，未运行任何东西。

总结论：changes。2 个阻断，6 个需改。核心问题：方案的防代交靠"身份绑定"，但绑定对象（上传所用的钥匙）与方案要求的上传者（协调者）不是同一个人，第二期做完也堵不住；第一期则实质没有新增任何技术约束。

## 1. 四个攻击推演

### 1.1 实施者冒充审查者
- 第一期：不通过（没堵住）。review-put 只校验 id 正则；reviewer 与 implementers 都是调用方自报（方案 1.2 已承认，第 120 行也承认）。实施者新取一个 id 即可。第一期只有操作规范。
- 第二期（项 B+C）：项 B 单独没有防御力。实施者登记只拦"登记过的 id"，而 id 本身可自造，B 只有在 C（id 由钥匙决定）之后才有意义。必须明写 B 依赖 C，不得把 B 单独上线当作"堵洞"。
- 判定：**需改**。第 106 行"自报的洞被堵上"的说法只在 B+C 同时上线后成立，应改写。

### 1.2 协调者改审查结论
- 方案的论证（第 53 行）"改一字节，r2 的 round1_sha256 就失败"只覆盖改 r1 的情形。协调者若同时改 r1 与 r2（r2 的 round1_sha256 重算），或直接整份重写两个文件，文件里没有任何只有审查者才能生成的东西，门禁无从分辨。第 53 行括号里"（第二期有签名时）签名"——但第 2 节文件字段并没有签名字段，第 5 步的两种方案绑定的是上传通道（钥匙指纹）或令牌，不是文件。
- 更要紧的是第一期项 3（第 77 行）：由发布脚本（协调者运行）把新格式"转成旧 JSON"，implementers 也"由协调者派卡登记文件提供"。这等于协调者运行的脚本拼 JSON、用特权钥匙写批准记录，且 implementers 由协调者给——正是 1.2 第 4、5 点的弱点原样保留，还多了一个由协调者控制的 implementers。
- 判定：**阻断（第 53–55、77 行）**。改法见 2。

### 1.3 同一个代理当两轮审查者
- 门禁只能检查两个 id 不同。第一期 id 自报，同一代理写 r1-A、r2-B 即过。第二期若按人一钥，前提是两把钥匙由不同主体持有；而当前所有代理在同一台机器、同一用户下运行（钥匙在 F:/dnd-tools 一带，协调者会话可读），"一人一钥"在文件系统层面并不分离：协调者读得到全部审查者钥匙，等于仍能代交。方案第 121 行只提"发放必须在协调者之外"，没有提"保管也必须在协调者可读范围之外"。
- 判定：**需改**。补充：审查者钥匙/令牌的保管须在协调者会话不可读的位置（独立系统用户或由亮圳手工持有、运行时一次性提供）；否则第二期的身份绑定只是名义上的。并如实写入遗留风险："同机同用户代理无法在技术上证明独立"。
- 可加的弱约束（不需新钥匙）：r1 与 r2 的 scope/findings 各自必须列出审查者读过的文件及逐文件 sha256（"已读清单"），门禁核对其与内容清单一致，r2 清单不得整份拷自 r1 的哈希顺序以外的内容……此条只能抬高伪造成本，不能证明独立，只作补充。

### 1.4 审查内容与上云内容不一致
- 方案的核心机制成立：run 时对 /work/<dir> 重算内容哈希，只认 hash 字段相等的记录。通过。
- 但有四个缺口，判定**需改**：
  1. 时间窗：核对哈希与执行作业之间 /work/<dir> 可能被改（TOCTOU）。须在同一锁内核对后从只读快照执行，或核对后立即 chattr/权限锁定并在执行前再核一次。
  2. 哈希覆盖范围：manifest 的排除规则（.git、被忽略文件、未跟踪文件取舍、--normalize 的 CRLF 归一）决定了"哪些改动不影响哈希"。方案没有声明"作业只会读取/执行哈希覆盖的文件"。被排除的文件若能被作业加载，就是旁路。须在方案里写明：作业入口、依赖和读取路径必须全在哈希覆盖范围内，排除项在审查记录里列出。
  3. 命令未绑定：记录绑定的是内容哈希，不是"运行什么"。同一内容可用不同入口、参数运行。须把入口命令（及参数）纳入哈希输入或纳入记录并在 run 时核对。
  4. 哈希改算法（项 1 改 manifest.sh）本身会使所有旧批准记录作废或错配，方案第 5 节第 1 点已要求逐字一致，通过；建议加一条"改后任一不一致则整项回退，不修补"。

## 2. "协调者负责上传"是否再次被判代交

- 风险高，不应作为设计前提。被拒事件的特征是"同一代理现编评语并当场自批"。第一期的发布脚本由协调者调用、使用特权钥匙、写入批准记录、且包含"转换并填 implementers"的拼装，仍具备"特权钥匙写批准记录"的性质；而分类器把审查者与协调者看成同一会话的概率不低（子代理结果回到协调者上下文）。分开两次调用并不改变"协调者写批准"。这一点方案第 135 行自己也承认"试后才知"。
- 更稳的做法（按推荐顺序）：
  1. **审查者本人上传，协调者不碰上传。**审查者两次独立调用：先 Write 结论文件，再运行一个只读文件、不生成任何内容的提交脚本（这正是调查里"先单独写、再单独运行"多次成功的模式）。协调者只触发 run。第一期即可采用，不需新钥匙；权限上审查者与协调者共享 tc_review 的问题仍在，但至少"代交"这个动作不再由协调者执行，规范与实际行为一致。
  2. **文件自带审查者签名，门禁验签。**审查者用自己的 ssh 签名钥匙（ssh-keygen -Y sign）对结论文件签名，随文件上传；门禁用服务器 allowed_signers 登记表验签并取 id。这样任何人（含协调者）都可原样中转文件，改一字节验签失败；也消除了"上传钥匙 ≠ 作者"的矛盾。这是第二期更根本的做法，应取代第 5 步的"钥匙指纹绑定上传通道"。
  3. 门禁直接读审查者本人放进 inbox 的文件（审查者经仅限 inbox 的受限钥匙上传），协调者无权上传 inbox。
- 当前方案内部矛盾：第 3 步让协调者上传，第 5 步又用上传所用的钥匙指纹决定 reviewer id——协调者上传时指纹是协调者的，绑定要么失败要么只能证明"协调者上传了"。判定：**阻断（第 38 行与第 47–50 行）**，须二选一：审查者自己上传，或文件内验签。

## 3. 两期划分与回退

- 第一期划分：基本合理（python stdin 三处整改、操作规范、文件格式），但项 3 的"转换成旧 JSON 由协调者运行"应删（见 1.2、2），换成审查者自传。判定：**需改**。
- 第一期并没有新增任何技术防线，只有规范与 python 整改。这应在方案开头明说，避免读者以为第一期已提高安全性。
- 第二期顺序建议：B 实施者登记（纯服务器、fail closed）→ A inbox → C 身份绑定（含验签）→ D 权限收紧。B 单独无防御力，不宜单独宣称完成。各项风险与回退：
  - A：回退可行，通过。补充：inbox 需文件数与总量上限、文件名为内容 sha256（不可覆盖、并发写不冲突）。
  - B：fail closed 写得好，通过。补充：登记者是协调者，协调者若是对手方则 B 无用；实施者最好从提交历史/派卡记录自动派生而非手填。
  - C：风险写了，回退（保留旧 tc_review、tc_admin 恢复备份）合理。需改：加"回退演练需在不影响线上的影子账号做"，以及发放/保管见 1.3。
  - D：回退写了快照与还原，通过；"harden 里 runner 无权写 reviews 不得削弱"好。补充：D 与 A 同时做时，先回退 D 再回退 A，顺序写明。
- deploy.sh 的整改改法：`cat > /tmp/akedit.$$.py` 用可预测文件名，在多用户机器上有被抢先创建的竞态，应改 mktemp 并 chmod 600。需改（小）。注意 deploy.sh 与 authorized_keys 编辑有关，"改脚本文件"虽不动钥匙，建议在第 6 节与亮圳确认时一并说明（方案已列）。

## 4. 遗漏

1. **审查记录留档：需改。**本地 verdicts 保留，但缺服务器侧：门禁每次 run 的决定（用了哪几个候选文件、各自 sha256、哈希、通过/拒绝及原因）应追加写入只追加审计日志，并回传本机归档到 F:/dnd/docs/审查记录/。否则事后无法证明某次放行依据是什么。
2. **作废机制：部分通过。**内容变则哈希变、旧记录自动失效——写得对。缺：(a) 已批内容事后发现问题的撤销办法（只能靠 changes 一票否决，且仅限同哈希；应允许"撤销记录"按哈希封禁）；(b) 记录有效期，旧批准永久可用，可加上限；(c) 批准是否单次使用（同哈希可否反复运行）应写明选择。
3. **并发一致性：需改。**未写：同一哈希多个候选（A approve、B changes、第二个 r1）时如何配对——应规定"取全部候选，任一 changes 否决，r2 必须引用其中某个存在的 r1 sha256"；候选文件原子写入（先写临时文件再 rename），门禁读取与上传不撕裂；run 与上传并发时对同一 /work/<dir> 加锁；两次 run 同时用同一批准时的计数。
4. **审查者质量/真实阅读**：方案第 124 行排除在范围外，可接受，但可用 1.3 的"已读清单"增加伪造成本。
5. **自批的另一路径**：implementers 为空时 fail closed（B 已写），同样应适用于"服务器登记表缺失"。通过。
