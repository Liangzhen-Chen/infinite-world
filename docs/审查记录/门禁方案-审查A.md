## 1. 安全论证

### 1.1 防自批
判定：需改。
- 第二期设计的服务器侧核对（两轮、互异、不在实施者登记、changes 否决、哈希绑定）与现 gate.sh approved()（第 68–94 行）、review-put.sh 的检查（第 20–29 行）相比没有丢任何一条，并增加了 r1 的 sha256 绑定与"哈希字段必须等于 run 时重算的哈希"，方向正确。
- 但实施者登记由协调者写（项 B），协调者可少登、错登；"fail closed 目录无登记就拒绝"只防忘记，不防故意。协调者自己不在"实施者"清单里（实施者是执行者代理），所以协调者以别的 reviewer id 自批不会被登记拦住。该风险没有写进遗留风险。
- 改法：遗留风险增写"登记由协调者维护，只防审查者与执行者重合，不防协调者以第三方 id 自批；自批的真正防线只有身份绑定（1.3）与钥匙保管"；登记按（目录名 + 派卡）追加，不覆盖，新卡必须新建登记，否则旧登记会让同一目录的新实施者以审查者身份通过。

### 1.2 防代交（协调者上传审查者文件，算不算代交）
判定：第一期阻断；第二期需改。
- 第一期：不算"转送"，就是代交的技术等价物。理由：第一期没有任何签名、令牌或指纹（方案 3.1 项 2 末句自己承认"并非权限已收紧"），审查者文件与协调者自己写的文件无法区分；协调者本来就能写文件、持钥匙提交。把提交步骤从审查者移到协调者，等于把批准记录的写入完全交给实施方（见 2 的阻断项）。
- 第二期：协调者转送文件是否算代交，取决于文件里有没有协调者伪造不了的东西。方案给的是"HMAC/令牌摘要"或"钥匙指纹"两条路，都有洞：
  1. 令牌随文件上传，协调者读得到令牌，可以替该审查者另造文件，除非令牌一次性且绑定 hash+round；方案写的是"一人一令牌"，不是一次性。
  2. 钥匙指纹方案（项 C）是服务器 authorized_keys 的 command="gate.sh review-inbox <id>"，这要求审查者自己用自己的钥匙连服务器上传，协调者转送（方案第 2 节第 3 步）用的是 tc_dnd 强制命令里的 review-inbox 动词（项 A），动词无法知道 id。两种模型混在一起，第 3 步的转送与项 C 的指纹绑定互相排斥：转送模型下 id 只能靠文件内签名；钥匙指纹模型下没有转送。必须二选一。
  3. 推荐做法：文件内签名，不用服务器端账号。审查者用自己的 SSH 密钥对结论文件做 `ssh-keygen -Y sign`（命名空间固定），文件旁带 .sig；服务器 run 时用 `ssh-keygen -Y verify` 对登记表（allowed_signers：reviewer id → 公钥）核对，id 由公钥决定，不接受自报。这样协调者可以只转送，改一个字节就验签失败；转送者也不需要任何批准权，才真正做到"转送不是代交"。该做法登记的是公钥，不改 authorized_keys，但仍属于"新增登记/权限"，归第二期、须亮圳批。
  4. 即使签名成立，私钥保管仍是根本问题：审查者是协调者派出的代理，运行在同一台机器、同一个 OS 用户下，私钥若放在这台机器上，协调者读得到。签名只防"事故与自动化误操作"，不防协调者故意。方案遗留风险 2 只写了"发放步骤"，没写"私钥存放位置"。改法：遗留风险增写此项；要真正防代交，私钥须在协调者的 OS 账号之外（亮圳/李白手里、独立账号或独立机器），或明确承认第二期只达到"防误不防恶"。
- round1_sha256 只是把 r2 绑到某个具体 r1 文件，不绑身份：协调者可以同时伪造一对 r1、r2 文件并让 sha 一致，方案第 53–55 行"改一字节即失败"只对"单独改 r1"成立。改法：把该句限定为"防止事后替换 r1"，不要写成防篡改的总结。

### 1.3 防篡改
判定：通过（有限定）。哈希绑定在 run 时由服务器重算，r1 以 sha256 绑定，候选只追加，这些对"事后改内容"有效。需补：门禁核对 r2 引用的 r1 时，除 sha256 相等外，还要显式核对 r1.round==1、r1.hash==r2.hash==当前哈希、r1.verdict=="approve"（第 39–45 行没有逐条写；旧 review-put.sh 第 25–29 行有，别丢）。

## 3. python 读 stdin
判定：需改（漏两处；替代写法有 3 个缺陷）。

### 3.1 覆盖
方案列了 review-submit.sh:12-18、manifest.sh:7（含 manifest.py:121-122）、deploy.sh:15、:66、:83。逐个核对：这五处位置与调查属实。但还漏：
- stage.sh:14：`git ls-files … -z | python "$G/manifest.py" manifest . --normalize --stdin-list --out /dev/null`，与 manifest.sh:7 同类。
- stage.sh:19：`$T get … | python -c "import json,sys;d=json.load(sys.stdin);…"`，python 从 stdin 读 JSON，同属红线。
- akedit.py 第 1 行注释仍写 `python3 - <file> …`，文档性质，应随 ak() 一起改。
- 连带风险：方案项 1 要求"去掉 `--stdin-list`"，若只改 manifest.sh 而漏掉 stage.sh:14，stage.sh 会直接失效。必须把 stage.sh 列入项 1，且 manifest.py 的 `--stdin-list` 与 `--list-file`（或新方案）同时保留一个过渡期，或同批改完所有调用点。
- 其余 python 用法（deploy.sh:23、:26、:62 的 `python3 -c`、gate.sh 的 `python3 apply.py/manifest.py <path>`）不读 stdin，不违规。

### 3.2 替代写法可行性
1. manifest：`git ls-files -co --exclude-standard -z > "$T"` 再 `python manifest.py … --list-file "$T"`。可行，但有两点要写清：①本机 Windows 的 python 若是原生版，Git Bash 的 mktemp 给的 `/tmp/…` 路径它读不到，需用 `cygpath -w` 转换，或把临时文件放在固定的 F:/dnd-tmp/ 下；②必须 trap 清理。更干净的备选：manifest.py 增加 `--git` 选项，自己用 subprocess 调 `git ls-files`，不需要临时文件（服务器侧不受影响，仍走 os.walk）。无论选哪个，方案的哈希等价验证（第 5 节第 1 点）必须覆盖含空格、中文名、CRLF、-text 文件。
2. 结论 JSON：方案 mkverdict.py 以 verdict 为命令行参数，与"审查者用 Write 工具写文件"（第 2 节第 1 步、3.1 项 2）互相矛盾：到底由谁写 JSON？若 mkverdict 以 verdict 为参数，那它就是把"评语与结论"变成命令行参数的小工具，和旧 review-submit.sh 在性质上相同，没有解决"同一步生成结论并盖章"。改法：审查者直接用 Write 工具写结论 JSON（唯一动作）；转换/校验/哈希核对用另一个只读文件、不带 verdict 参数的工具。用 jq 一步完成（`jq -n --rawfile scope … --rawfile findings … --arg …`），不引入新的解释器依赖；服务器侧已有 jq，格式互相可测。
3. 本机是否允许运行 python：调查第 15 行说"约束说本机不运行 python"，方案保留 `python manifest.py`（manifest.sh）与 mkverdict.py，并在第 5 节用"本机不运行 node/python 时由执行者在云端跑"带过。需要明说红线是"python 读 stdin"还是"本机根本不运行 python"。若是后者，manifest.sh 也必须去掉对本机 python 的依赖，而不仅是去掉 stdin。
4. deploy.sh 替代写法的两个缺陷（见 3.3）。

### 3.3 deploy.sh 替代写法
方案写成两条 ssh 调用：`as $k "cat > /tmp/akedit.\$\$.py" < akedit.py`，随后 `as $k "python3 /tmp/akedit.\$\$.py $*; rm -f …"`。缺陷：
- `$$` 是远端 shell 的 PID，两次 ssh 是两个会话，PID 不同，第二条找不到文件。必须在同一次 ssh 里完成，例如 `as $k "f=\$(mktemp) && cat > \"\$f\" && python3 \"\$f\" $*; rc=\$?; rm -f \"\$f\"; exit \$rc" < "$G/akedit.py"`（stdin 给 cat，python 只收到文件路径）。
- `mktemp` 默认 0600 属 ubuntu；:66 与 :83 是 `sudo -u reviewer python3 …`，reviewer 读不了，需 `chmod 644 "$f"` 再运行，并保证用完删除。固定的 `/tmp/akedit.$$.py` 还存在可预测路径被抢占的风险，所以用 mktemp。
- 新引入违规的可能：`python3 file args` 不读 stdin，不违规；但 `cat > f < akedit.py` 属于 shell 重定向，不是 python，不违规。

### 3.4 其它
- review-submit.sh 的上传部分改为 `ssh … review < "$verdictfile"`：重定向的是 ssh，不是 python，可行。保留原脚本开头的"本地哈希 == 服务器哈希才提交"预检（第 9–11 行），方案新流程里没写这一步的归属，应写进发布/提交脚本。

## 二、新引入的问题与细化（均为第二期，非阻断）

M-1（第 160 行，F 项，小）`f=$(mktemp) && cat > "$f" && chmod 644 "$f"; python3 "$f" …` 中 chmod 后用的是分号：若 mktemp 失败，`$f` 为空仍会执行 `python3 "" …`。把分号改成 `&&`，用 `rc` 保存 python 退出码再删文件（rc 写法已有，保留即可）。另外 ARGS 是预先加引号的字符串（含 `'command=\"…\"'`），原样放进单引号包裹的远端命令会破坏引号，实现时应整串用双引号构造，并在影子账号上验证。

M-2（第 59 行，2.3 节，事实性）"符号链接哈希其链接目标"只对服务器侧成立。manifest.py:97-99 在 `--normalize`（本机）遇到符号链接直接 die('symlink not supported')，只有非 normalize（服务器）才哈希 `->目标`。改写为"本机含符号链接的树不可算哈希（报错）；服务器侧哈希链接目标；故带符号链接的树不可审"。其余 2.3 的描述（CRLF 归一、NUL 视为二进制、-text、顶层排除目录、按路径字节排序、空目录与权限位不入哈希）与 manifest.py:15-16、18-65、104-106 核对一致。

M-3（第 38、173 行）changes 结论带 expires_at 并过期不参与，会使"一票否决"在 7 天后悄悄失效，等于允许等待一周后通过。改法：expires_at 与 max_runs 只作用于 approve；changes 不过期，只能被已登记审查者/亮圳签发的 revoke 撤销。

M-4（第 53、64–65、174 行，运行可操作性）cmd 逐字绑定加 max_runs 默认 1，意味着同一内容换一个测试子集、改一个 P 值、或原命令失败后重跑，都要新的签名结论；方案一下每次要亮圳本人触碰。这不是安全缺陷，但会使第二期难以日常使用。需亮圳权衡：cmd 只绑定"动词 + 目录 + 入口脚本"，不含 P 与文件清单；max_runs 由审查者在签名时决定（方案已允许），并在第 8 节把这一权衡列给亮圳。

M-5（第 50–51 行，项 E）"只读运行快照，runner 只读"与现作业行为冲突：测试会在目录内写 .out/.tmp，stage.sh、jobs、kill、busy 等动词按 /work/<dir> 查进程与结果（gate.sh:53-64、runjob.sh 调用），结果文件为 /work/<dir>.full。方案需写清：快照的位置与命名、runner 可写的子目录（排除目录在快照内重建，即 2.3 所述）、结果与日志文件如何仍按原路径对账、快照的清理与磁盘上限。这是项 E 的设计空白，可在批准项 E 前补。

M-6（第 189 行，测试副本）"只把路径参数指向临时树"需要把 gate.sh 里写死的 W=/work、R、GD 等变成可配置。切勿以环境变量覆盖的形式放进正式 gate.sh（强制命令环境被改写即成旁路）；应在复制测试副本时用文本替换生成，正式文件保持写死。

M-7（第 144–146、34、43 行，项 A）签名需要两个文件（.json 与 .sig），文件名"取内容 sha256"只命名了一个；需写明成对存放（同一 sha 的 .json 与 .sig，或单个 envelope），以及 `review-inbox` 动词如何在一次 stdin 内收两个文件。另外项 C/E 需在 preflight 加"服务器 OpenSSH 版本满足 `-Y verify` 与（若用硬件钥匙）sk 类型验签"的检查，不满足则整个第二期不开始。
