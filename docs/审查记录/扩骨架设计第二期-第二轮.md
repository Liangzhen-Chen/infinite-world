 - N11：快照由谁生成、谁核对没写。要加检查：最新版快照等于当前派生函数加数据表的输出，否则快照会悄悄落后于代码。旧版本不改不删要有测试（哈希钉住）。
 - N12：存量重扫（用最新规则找已批准记录里的编造）用最新版事实，指纹核对用记录自己的版本，两个用途要在设计里分开写，否则会出现“记录在旧版本下通过、新规则下该报错却没人报”。
 - 记录没有 skeletonFields 的老记录（332 件）按“无派生字段”处理，现行投影已覆盖，保持。

## 其余三项
表的哈希门禁（修订七第 3 条）：L4 批准后在入库记录写内容哈希，L1 先核哈希，不符拒绝，对应我 N1，成立。补一句：recipeSteps 里 derived 步骤记录所依据的表哈希，表改动时步骤 L1 自动重跑。非阻断。
金属主材料（第 4 条）：“配方 materials 里重量份额最大的那一项；相同时取第一个金属类材料”有歧义：锻造配方的材料常含木炭小袋，若按全部材料取最大，主材料可能是燃料而不是金属。应写成“在金属类材料里取重量份额最大的一项（排除燃料和辅料）”；复合物品（钢刃木柄）用钢的密度算体积会偏小，应说明复合物品的体积不推（记未知），或按各部分分开。非阻断，需在数据卡前定稿。
新顺序（第 5 条）：与李白 11-11 的 PLAN 一致。PLAN 里“先修评分细则、删已发布样本的编造”在 RUBRIC2（t-skf）里并行推进，不在第二期设计范围内，设计里应加一句指向它，并把第一期第五节评分细则标注“被 RUBRIC2 取代”。非阻断。
额度 8% 到 13%：比上轮估算（约 6.5% 到 11%）上调并补了正文对账、L2 配方清单、版本快照和步骤全读，区间合理，62% 已用加 13% 为 75%，未过 80% 封顶。再提醒：R-B1 的修法要改 context，会多一张小代码卡，在区间内可吸收。


# 复审二：修订八（11-11）

## 结论：R-B1（原 B3）已解决，设计层面没有新的阻断
 - 第 1 条：版本投影作用于 context 里嵌入的配方骨架，且与 entry 共用一处规则。这正是我上轮实测的泄漏点（w3ContextFacts 物品分支整条嵌入配方，334 个物品条目里 185 个）。我再核了一遍 context 的其他成分：物品分支只有 origin（固定字段的 fact()）、recipe（整条，已覆盖）、book（只取 teaches 的 id 与名称）；配方分支的 materials、tools、product、byproducts、skill 都经 fact() 只取 id、name、weight、basePrice、use、shelfLifeDays，workplaces 取 id、name，没有别的嵌入骨架条目会随后加字段变化。投影规则按“嵌入的 entry 一律投影”写，也兜住以后新增的嵌入。
 - 第 2 条：硬门槛是对的写法：334 个物品记录加 185 个配方记录逐条复算 0 失效，并要求 v0 记录复算值与改动前逐字相同（防止投影写松、把变化也一并剥掉）。这两条合起来既证明不失效，也证明核对的仍是批准时的内容。
 - 第 3 条：v1 与两条已标记记录指纹逐字一致，成立。
 - 第 4 条：重扫用最新版、指纹用记录版，分开写，成立。
 - 第 5 条：主材料限定在金属类材料内，没有金属类就不推，成立。复合物品（钢刃木柄）体积偏小的问题我上轮提过，设计没有回应，仍是非阻断，建议数据卡阶段把复合物品的体积写“未知”。
 - 第 6 条：L1 只核动词、其余由 L2 配方清单和 L4 全读兜底，分工写明，成立。

## 非阻断（实施时落到代码卡的测试里）
 - skeletonFields 从字符串数组改成 {field, version} 的格式变更，要有迁移与读取兼容：manualRewrite、projectEntryForRecord 对旧格式（字符串）按 v1 读，且 0 失效验收要覆盖格式迁移前后。
 - 0 失效验收用复算指纹测，应放进腾讯云上跑的测试（本机不跑测试），并在每次改词表、改抽取器、新增版本时重跑；它同时是 N11（快照不落后于代码）的检查之一。
 - 注册表要做成“新增后加字段必须同时登记投影与验收”，避免有人加字段忘记登记，硬门槛会立刻报出，故不算缺口。
