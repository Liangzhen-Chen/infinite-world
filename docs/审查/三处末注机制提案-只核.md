## 一、`dimension_write_rejected` 接收方

逐项核：
- 同族写法一致：卷二:844–846 三码都是"规则层 `emit`、提交后由 transaction 交出、事务被拒即无信号"。本码相反，恰在被拒时出现，提案让 transaction 在事务内接收、不经 `emit`，和 kernel 组内传递一致。kernelApi 导出没加。`report`（卷二:914）、`ReplyResult` 的 `rejected` 加 `ErrorCode` 拒收代号（卷二:770、:789、:994）都核实。
- 和卷二十 §4.1.4 调度器"信号后重取计划"（卷二十:456；卷二:801"结束当前计划段"）不冲突：事务整笔回滚后同一事务里的 `layout_change` 也不存在，不会触发重取。一致。
- 复演（卷二:806）：被拒请求留在输入序列、复演同处同拒，成立。

真问题：
1. **没有覆盖整类**。运行期写入被拒不止校验器这一处：`writePath` 也会拒写（卷二:448，E-VIEW-UNDECLARED-WRITE、E-TEXT-UNGATED、E-TERM-RESIDUE），还有 `relocate` 第 7 点的校验错、卷四 B-10 的 E-BODY-PART-TARGET（卷四:460）。这些拒写之后事务怎么处理，卷二同样没写。提案只给 `dimension_write_rejected` 定"整笔回滚、`report`、回执"，等于做了一条特例。第三处"不定会怎样"里也默认 E-BODY-PART-TARGET 走这套处理，前提并不成立。应改为一条整类规则写在卷二一处：事务内任何一次写入被拒（校验器拒写与 `writePath` 拒写都算），就整笔回滚，然后 `report`，有句柄的回 `rejected`。`dimension_write_rejected` 只是这类里登记为信号的一员。
2. **"整笔回滚是卷二通例"说过头了**。卷二没有通用的事务原子性条款（全卷"原子"0 处），"任一步失败整笔回滚"只在 `relocate` 原语内（卷二:469）和卷十九规则 4（卷十九:986）出现。正文应把它写成本条新定的事务规则（单点定义），不要说成引用通例。
3. **待选甲没定续推点**。卷二十:425–426 规定钩子按绝对分钟对齐，同一刻里依次执行。如果某刻 t 有一部分钩子已提交、后面一笔被拒，甲说"世界时刻停在最后一笔提交处"，接下来有两种结局：时钟已到 t，下次推进从 t 之后取，t 这一刻剩下的钩子就被永久跳过，实际变成了乙；时钟没到 t，下次重跑 t，已提交的钩子会再生效一次。甲必须写清续推点（比如"一刻内全序作为一个单位，提交前置"，或者存一个续推游标），否则交李白选的甲还不是一个可选的方案。

待选是否确属须选：**是**。卷二第 0 条"排队，不插队"（:805）、卷二十 §4.1.3 都没写推进中途被拒以后怎么办，现有条款定不了。

## 三、C16-12 ①

逐项核：
- "不调用 `relocate`"成立：原语只对 place 表的行开放（卷二:466 第 1 点）；状态实例存在 `state.statuses[主体][]`（卷二:306），不是表行，没有 `parent` 和边，用不上 `placement`。借用"离场不存标记、不作数"的读法（卷二:468）也合理。作数谓词只在 `statusView` 求值，有 P21-1（卷二十一:313）和 :262 撑着，和 `chronic` 派生布尔（:128）同一做法，符合单点定义。
- 卷二十一:291"五个钩子"、:405、:417、:431、:467、:478、:507、:1533，卷十六:711、:844、:877、:1014，以及第五批只核的五点，全部核实。提案逐条回应了 N1 的 5 点。

真问题：
1. **名字和单点定义撞了**。卷二:465 把"行改挂"定为通用原语、唯一定义，:466 还写着"别的表、别的行要开放改挂，须改本卷并报李白"。提案在卷二十一里另立同名的"改挂"，其实只是 status.mjs 用普通 `writePath` 改写 `bodyPart` 一个字段。有两种改法，选一种：其一，改个名字，不叫"改挂"，并写明"不是卷二 §2.6 行改挂，是登记写者的普通字段改写"；其二，保留这个名字，同时把卷二:466 第 1 点列进牵连，补一句"状态实例的 `bodyPart` 改写不属本原语"。现在的牵连表里没有这一处。
2. **不变量清单列错了字段**。第 3 点要求"`status`、`severity`、`peak`、`since`、`source`、`duration` 逐位相同"，但 `duration` 是状态行字段（卷二十一:112），不是实例字段。实例字段见卷二:207 `struct:statusInstance`，再加卷二十一:229 的 `peak`。应照 `relocate` 第 5 点的写法，改成"除 `bodyPart` 外全部字段逐位相同，比对清单由 `struct:statusInstance` 机器枚举"，不要手列。
3. **卷四的牵连漏了，行号也错**。真正的定义处是卷四 B-10（:460），提案没列。B-10 末句写着"如何处置见 §8 Q-5"，要改为回指卷二十一，同类还有卷四:1102。提案标的卷四行号也不对：`broader` 在 :228（不是 :226），E-BODY-PART-TARGET 在 :319（不是 :317），Q-5 在 :1383（不是 :1368）。而且 Q-5 已经标"已结"，"Q-5 标结"一项多余。
4. **待选的前提引错了条款**。R21-1.10（:421）是驱动行的新建条件，不是"同部位同一行只能一个实例"的不变量。卷四:1102 的唯一性是对（状态行, 部位, `since`）三者全同说的。"只能一个"实际上由 R21-2.1 写入时合并（:467）和 R21-1.10"无实例才建"两条间接维持。还有第三种可能：两个实例都改挂、在同一部位共存。它下一次被 R21-2.1 写入时并入哪一个是不定的，所以同样需要新规则。正文应如实写明这个前提，并说明共存为什么不可取。

待选是否确属须选：**是**。R21-2.1 只给了严重度相加的规则，`peak`、`since`、`source` 怎么合，被并掉的实例算哪种移除，现有条款都定不了。挂起会导致变身期间伤病不叠加，合并则不可还原，这是一项设计取舍。
