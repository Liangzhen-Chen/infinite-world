## 二、S6-14 的范围：实体行、偏离行、状态键

S6-14 :337 原句：

> **状态模式检查**：遍历存档状态的模式声明（卷二 §2.7 的状态登记表），实体行、偏离行、状态键上凡是单位属于任一资源种类行 `unit` 的数值字段，除 `accounts.*`、`ledgerTotals.*`、`outflowTotals.*` 与合同、义务记录里的应付数额外，计数为 0。

配套原句：

- 卷六 S6-1 :324：「`kernel/ledger.mjs` 之外对 `accounts.*` 的写入计数为 0；数量只存在于账本，这一点用状态模式检查判定（S6-14），不靠阅读字段含义。」
- 卷六 §4.1 规则 11 :382：「实体行上不存在任何数量字段，读者一律读 `balance`。」
- 卷六 §2.1 :103：「容器、固定装置、以及只当位置用的地点不开账户（S6-14；封卷后勘误 1118k8…）」；同格「未登记为主体的 place…当持有人即 E-LEDGER-HOLDER-NOT-SUBJECT」。这一段是 S6-14 同一格后续的「持有人只能是主体」，不是本卡「状态模式检查」第一句的数量扫描；本条目 source 只引第一句，故不把它算作本卡漏项（见第七节第 5 条）。

「实体行」「偏离行」不是本卡自造的分类，卷二 §1.3 :123-126 定义为：

- 实体行 `rows.<id>`：「该类实体本身的定义（`fac_forge`、`deity_x`…）；实体行写完整值」——在 `world/ontology/dimensions/<kind>.json` 的 `rows` 节。
- 偏离行：「对某一个运行期或作者个体…相对其模板/类别的个别偏离，位于 `instanceTable`、表 `generated` 节或存档 `state.created[id].props`」。

检测器的现状：

- `state_pattern.mjs:101-123` 只读 `world/ontology/state-owners.json` 的 `pathTypes`；全文没有读 `world/ontology/dimensions/` 的代码。⇒ 实体行（M1）完全没扫。
- `state-owners.json:35` 的 `created.*.props.*` 是 `dimension`；`state_pattern.mjs:71-97` 的 `leaves` 对 `"dimension"` 不产出任何叶子，直接返回。⇒ 偏离行（M2）没扫。
- `state-owners.json:43` 的 `pendingPost.*` 是 `list<struct:pendingPost>`；`leaves` 的字符串分支不解析 `list<…>`。⇒ 状态键里的容器类型（M3）漏扫。
- 其余直接数值路径（`clock.minute`、`clock.seq` 等）与 `struct:<名>` 路径能展开，但只按当前 `pathTypes` 已写出的路径。

按卷文的正确口径（供修卡用）：

1. **实体行**：读 `world/ontology/dimensions/*.json`（除 `_units.json`、`_vocab.json` 等 `_` 开头文件），对每个 `rows.<id>` 实体行，按该表 `dimensions` 表头的 `unit` 判：凡单位在资源种类行 `unit` 集合内、且该行确有该维度的数值（含 set/map/list 里的数值叶子），报一条。命中文件应是该维度表文件，不是 `state-owners.json`；当前检测器的 `file` 固定为 `STATE_OWNERS`（:120），修卡要改命中形状。
2. **偏离行**：对 `pathTypes` 值为 `dimension` 的模式，按 `keyKinds` 取该路径可出现的实体 kind，再按这些 kind 的维度表 `dimensions` 表头判单位；`created.*.props.*` 的 `keyKinds` 是 `[["item","person","place"], "dimKey"]`（`state-owners.json:52`）。统一加载器已有这段展开逻辑（`kernel/load/state-owners.mjs:255-268`），检测器应复用它或同一口径，不要另写一套。
3. **状态键**：直接数值路径与 `struct:<名>` 展开保留；另加 `list<…>` 等容器简写解析，复用 `kernel/validate/types.mjs` 的 `listItemType`（:34）与 `parseNumberType`（:39），不要自备 `NUMERIC`/`STRUCT_REF` 正则（卷二 §2.7 :811 的类型文法只一处，别处只引用）。
4. **表缺失**：item/person/place 的维度表当前尚未建；加载器的既有口径是缺失就跳过（`state-owners.mjs:262-264`）。检测器照此跳过可以，但必须加一条合成维度表夹具，证明表在时能报；不要把「表不存在」当成「检查通过」。若主会话要求缺表即报参数错，需另定，且块 3 会因 item/person/place 表未建而红。

**「带 kg 等单位的物理量维度算不算数量」——按卷六原句，算。** 原句只写「单位属于任一资源种类行 `unit` 的数值字段」，没有给物理量、属性量、显示量任何排除。当前资源种类表的 `unit` 只有 `bps`（`world/rules/tables/economy/resources.json` 两个行都是 `bps`），所以现在 0 命中；但 `material.json` 的维度表头里有 `mealCap: g`（:2052）与 `appearanceRefs: count`（:1592）。一旦某个资源种类行用 `g` 或 `count`，按原句字面，材料行的 `mealCap`、`appearanceRefs` 都算「单位属于资源种类行 unit 的数值字段」。这可能是原句想要的效果（账本是数量的唯一出处，质量、件数都是数量），也可能过宽；卷文没有给排除条件，检测器不能自行排除。见第七节「拿不准」。

## 三、豁免：整键 vs 应付数额

S6-14 原句的豁免是「合同、义务记录里的**应付数额**」，不是「合同、义务记录」整类。卷六 §2.4 的字段定义（:200）：

> `resource`、`qty`、`done` | 资源引用、integer、integer | 应给付与已给付

`qty` 是应给付（应付数额），`done` 是已给付（已付出去的数量）。`done` 是已给付数量，按「账本是数量的唯一出处」不应在义务记录里另存；原句没有豁免它。检测器 `state_pattern.mjs:22` 把 `contracts`、`obligations` 两个顶层键整类放过，`tests/accept/bypass/state_pattern-11.txt:18` 还把 `qty` 与 `done` 一起放进不报用例，等于用测试固化了过宽豁免。

收窄办法（不按字段名、不按 id）：

- 在合同/义务记录的类型登记处（将来登记 `contracts.*`、`obligations.*` 的 `pathTypes` 时）给「应付数额」字段加机器可读标记，例如命名 struct 行的字段级别 `payable: true`，或给该字段一个独立类型节点 `payable:<unit>`；检测器只豁免带该标记的叶子。
- 没有标记的数值字段（如 `obligations.done`、合同 `terms` 里非应付的数量）照常报。这样豁免粒度落在字段语义上，不按字段名，也不为某个记录整键开口子。
- 标记的文法与登记位置要由主会话按卷二 §1.5「命名 struct 登记」/§2.7 `pathTypes` 文法定；不要在检测器里写 `qty`、`done` 这类字段名，否则违反卡头红线第 2 条。
- 测试要改成：`obligations.qty`（应付）不报；`obligations.done`（已给付）必报；合同 `terms` 里单位是资源单位、且按记录类型登记不属于应付数额的数值必报。当前 must_pass 用例（`state_pattern-11`）在修 M4 后会失败，必须随实现一起改。

## 四、违例码

`E-DIM-STRUCT-FIELD` 已在卷二 §4.3 :1528 登记，`server-plugin/kernel/error-codes.mjs` 也有。卷十二 §2.12 :547「无码状态不许出现」要求验收报告里凡条目「不过/未跑」都落到有登记的码；:549「无码检查不许出现」要求门禁里有检查类别而无登记码的补登记码。本项用的是已登记码，满足这两条，不属于无码检查。语义上它不是最贴切的（登记义是「取值域与类型」的 L1/L2 校验），但：

- 卷六错误码表与卷十二 §2.12 都没有「账本外存数量」专码；
- 运行期账本对批次属性带数量的拒收也用同一码（`server-plugin/kernel/ledger.mjs:452`、`:775`），口径一致；
- `E-LEDGER-HOLDER-NOT-SUBJECT` 只管持有人主体，套不上。

结论：可接受，不阻塞。若主会话要专码，走卷十二 §2.12 勘误补登后换 `params.code`，检测器不用改结构。
