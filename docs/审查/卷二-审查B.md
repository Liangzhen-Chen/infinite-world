# 卷二审查 B

审查对象：卷二-维度表规范与统一入口.md（968 行，已全文读完）。对照：调研 10 的子系统表与卷目、09 的系统清单，以及我对 DF、CDDA、RimWorld、EVE、CK3 的了解。没有运行任何代码。

## 总判：有条件通过

格式母本的骨架站得住。必改点共 6 条，其中 1 至 3 条不改会直接妨碍后续卷落地。

## 一、维度表与继承：长处吸取了，有一个坑没填平

吸取的长处：
- 一种文件格式服务全部实体类，加载器和校验器只有一份。
- 类别行加实例行，加 abstract，对应 CDDA 和环世界的做法。
- 取值算法只有一个，写在 §1.3 的伪代码里，所有表共用。这正是 CDDA 缺的"统一实现"。
- extends 深度限制为 4 层并检查成环。
- 缺值是未知，不在代码里补默认值。
- GENERATED 行与手写行走同一校验器，来自 DF。

仍有的问题：
1. **extends 与 precedence 的关系没写进算法。** §1.3 的 `value()` 伪代码只遍历 `precedence ∩ memberOf`，完全没有沿 extends 链取值的步骤。附录 A 的 `class_workshop_hot extends class_workshop extends class_public_building` 同时出现在 precedence 里，读者无法判断先走哪条链，也无法判断 extends 的父类算不算 precedence 的成员。必须补一句话：extends 链在同一类别行内先展开（子覆盖父），展开后再参与 precedence 比较；并给一个 3 层示例的求值轨迹。
2. **precedence 是整张表的一个全局全序。** 材料表只有 13 行时可行。扩到约 40 行、再加上物品和地点后，"某维度上 A 比 B 更具体，另一维度上相反"就表达不了。可以保持现状，但要在卷里明说这条限制。同时规定两个互不相含的类别同时命中同一维度时，按 precedence 先后取值，且该冲突由校验器报 warning。
3. **继承只能整值替换，没有 CDDA 的 extend/delete/relative 语义。** 例如子类想在 `allowedMaterials` 上加一项，只能整个集合重写。这个坑 CDDA 踩过，后来补了 relative 和 extend。建议在 set 和 map 维度上预留 `extend` 和 `remove` 两个字段。

整体评价：避开了 CDDA 的"各处各自实现"。但同一个概念有 classes、tags、components、extends、precedence 五个入口，数据作者的心智负担偏重，见第五节。

## 二、修正值体系：取舍合理，有几处不严密

"键集合开放于数据、封闭于代码、运算符和作用域封闭"是对 CK3 与 EVE 的合理折中。叠加惩罚公式及其算例（0.869、0.571 等）自洽，附录 B 的手算也对。

问题：
1. **`op` 与 `stage` 的组合在 §3.2 内部不一致。** 示例是 `stage:"mul", op:"post_percent"`，但第 420 行的组合表把 "mul→post_percent" 与 "add→add" 并列，读不出 stage 与 op 哪个决定哪个。要么删掉 post_percent（加载期本来就归一成 mul 因子，等于多余），要么明确 stage 是上位、op 是下位。
2. **目标 `capability.consciousness` 在 17 类实体里没有对应的表。** §1.11 状态容器和 §3.1 都用到了 `capability.*` 作修正键，但 `<kind>.<dimension>` 的规则要求 kind 是 17 类之一。需要补一个明确的"派生量命名空间"，或者规定它归 body_plan/status 表登记。
3. **没有说明 modifiable 只能用于 number 和 integer。** 对 map 类型维度（技能、upkeepPerDay）的修正该怎样定位（键加子键）没有写。附录 A 的 `upkeepPerDay` 是 map 且 `modifiable:true`，按现有文字无法求值。
4. **叠加惩罚只能由维度决定，不能豁免来源。** EVE 里技能和部分植入体不受惩罚。这里若某来源（如基础种族加成）不应受罚，只能靠 stackGroup 或拆维度。建议允许修正项带 `unpenalized:true`，或在 §3.4 明说不支持并给出替代办法。
5. **缺 set / override / min / max 运算。** 环世界的 setMax 与 offset、CK3 的"设为某值"在"必须是 X"的场景（石化、封印）会用到。当前只能靠 post 曲线硬凑。
6. **作用域解析的性能没有交代。** `located`、`members`、`believers`、`jurisdiction` 都要求"从来源找到受影响者"或"从受影响者找到所有来源"，对约 550 个具名 NPC 加数千次求值是否需要反向索引没有说。至少要写出采用哪个方向、缓存键是什么。

## 三、随机实例化：方向对，确定性有三个缺口

对的部分：种子键由 `template.seed, kind, rowId, dimension, instanceId` 构成，纯函数；AI 输出不进种子；惰性采样与读取顺序无关；写回走同一校验器。这是对的。

缺口：
1. **联合分布（copula）的种子键定义不清。** 每个维度一个种子键，那么相关的多个维度（人格向量）各自独立抽样，相关性就丢了。必须规定 joint 用"组 id"而不是"维度"作种子键，一次抽出整个向量后分发。
2. **跨机器、跨 Node 版本的字节一致无法保证。** B6 要求"逐字节相同"，但 lognormal、normal 依赖 `Math.log/exp/cos`，不同平台的浮点结果可能不同。需要规定：自带 PRNG（计数器式哈希→均匀数）；超越函数用固定实现；写回值按固定精度舍入。同机复现没有问题，跨机复现（腾讯云与本机）不一定。
3. **"无限世界"所需的实例 id 确定性不在本卷。** 种子键里的 `instanceId` 必须本身由坐标或父级 id 确定性导出，否则同一格子两次生成得到不同 id，种子键就失效。本卷应写一句约束并指给卷十。
4. **全量写回会让存档随探索无限增长。** B8 让惰性采样写入 `state.created`。对无限世界应只存种子键和被偏离的维度，其余每次重算；"写回"只在实例偏离了采样值（受伤、成长）时才发生。否则存档膨胀，且 stateMemo 在读取时被写入失效。
5. **入口"纯读"与 `sampleOnRead` 写回冲突。** §2.2 说入口纯读，§1.10 又让读入口触发写。建议 sampleOnRead 改为"结果纯函数计算，不写；仅在被偏离时写"，这样一并解决第 4 点。

## 四、覆盖面：17 类加 3 表不够覆盖约 330 个子系统

对照调研 10 的卷目，下列实体类在卷二没有表，也没有说明挂到哪张表上：

1. **配方 / 工艺（recipe）。** 现有 349 条配方，卷二的 `item.selfMake` 只是物品上的一个对象。配方有输入、输出、工位、工具、技能、时间、产出分布，是独立的可检索实体（卷三、卷十四、卷十九都要查它）。**必须补表。**
2. **植物 / 作物 / 资源场（卷二十五）。** `place.deposits` 与物种的 `habitats` 都只能引用它们。作物有生长期、季节、产量，不是物种也不是物品。应当补表（或明确作为 species 的子种类，并给出作物专属维度）。
3. **事件 / 局势 / 灾异模板（卷二十四、卷二十，调研 10 第 17 节）。** 事件有触发条件、权重、后果、持续阶段，是卷二十四的核心数据，却不在 17 类里。事件的结果又需要走修正与状态。**必须补表。**
4. **科技 / 知识条目与研究（卷二十二）。** 知识持有、失传、研究门控需要一张"条目"表（前置、难度、地域门控）。卷二把"知识"只当作技能（skill）的一部分，覆盖不了秘传、情报、研究。
5. **作品 / 文物 / 神器（卷十五、卷二十三）。** 实例级的作品（作者、品质、内容、历史）与文物（槽位、附魔、稀有度）在 §5.1 只有一行 `qualityTier`。至少要说明这类实例走 item 实例加哪些实例字段，以及修正项存哪里（§3.2 第四处"物品实例的附魔/品质"只提了一句）。
6. **载具（卷十七）。** 可挂 item 组件 `vehicle`，但要补组件 requires（载重、速度、零件、燃料）。现在组件清单没有 vehicle，需补。
7. **天气 / 气候状态（卷二十）。** 天气类型（权重、降水、温度修正）是一张类型表；运行态在 place 的环境状态里。卷二应声明天气类型走哪张表，或新增一类。
8. **法典 / 规范（law、norm，卷八）。** `place.lawCode` 引用它，offense 表只定罪名。法典条目（比附、罚则、适用范围）无归属。
9. **语言、历法（卷二十）。** `culture.pillars.language` 被规定引用 skill 表中的语言技能，这会把语言绑死为技能。历法按文化变化，也需要表。
10. **疾病**：已覆盖，由 status 容器承载，没有问题。
11. **法术 / 效果、任务（quest）、服务类型、能力词条（abilities）：** 前两者无表；后两者按词表处理即可，但词条上带属性（如 ability 的等级数）时，词表格式要明确可带字段。

小结：事件、配方、作物、知识条目、法典五类缺失是硬缺口。建议要么把 17 扩为 22 左右，要么在 §5 增一节"未单独成表的实体类及其归属"，逐类写清"挂在哪张表、用哪个组件"。

还有一个细节：§5.7 说首批 14 类设施，但列出了 17 个名字（house…office）。数量不符，需订正。

## 五、过度设计与难以实现的部分

1. **五级校验加 L5 报告、约 40 个错误码。** 全部实现需要大量代码。建议分期：L0 至 L3 与跨表不变量里最关键的 3 条（质量体积、ref 闭合、必填）先做，其余作为"应当"。
2. **量纲符号运算（E-DIM-UNIT-MISMATCH）。** 对 RX 公式做量纲推导是一个小型类型系统，收益有限，且 score、axis、fraction 都是无量纲，推导出来也查不出有意义的错。建议降为"单位词表存在性检查"，量纲检查留作可选。
3. **读取路径追踪（E-VIEW-UNDECLARED-READ，靠只读代理或夹具追踪）。** 实现成本高，也会拖慢运行。可保留 `declareViewInputs`，但验证用静态扫描（grep 入口函数体里的 `state.<key>`），不做运行态追踪。
4. **classes、tags、components、extends、precedence、sphere 六套分类机制并存。** 每个实体要写清自己在哪套里。建议在 §1.3 末尾加一张"何时用哪个"的判定表，并砍掉一套（组件与 byComponent 几乎等价于"类别 + required 条件"，若合并可大幅简化）。
5. **Gaussian copula 联合分布。** 只用于人格向量等少数地方。首批可只实现 independent 与 categorical，copula 留给卷二十六。
6. **§7 的断言约 40 条，口径一律"必须"。** 其中 A5/A6（清空 labels 后推进 30 天逐事件相同）、B6（逐字节相同）属于集成级验收，应标为阶段门而不是本卷收口条件，否则本卷永远收不了口。
7. **"维度表自动生成派生槽"（§3.1 第 5 点）。** 与 derived.mjs 的现有 `closed` 槽语义要对齐后才能动，建议先保留手写槽表一个阶段，生成逻辑做完再切换。

## 必改点（汇总）

1. 补 extends 与 precedence 的求值顺序（§1.3），并明示全局全序的限制；set/map 增加 extend/remove。
2. 补缺失的实体类归属：配方、作物或资源场、事件、知识或科技条目、法典；作品、载具、天气写清挂靠方式；订正设施"14 类"与列表不符。
3. 随机实例化：joint 的种子键用组 id；规定自带 PRNG 与写回精度；说明实例 id 的确定性来源（交卷十）；改惰性写回为"只存偏离值"，消除 §2.2 的自相矛盾。
4. 修正体系：统一 stage/op 的组合表；规定 modifiable 仅限 number/integer 并说明 map 子键寻址；给 `capability.*` 找到归属；补 set/override 与来源豁免叠加惩罚的办法；写出作用域解析的索引方向。
5. 砍或降级过重部分：量纲推导、运行态读取追踪、copula 首批不做；分类机制六套收敛并写判定表。
6. §7 的断言分档：A5/A6/B6 作为阶段门，不作本卷收口条件。
