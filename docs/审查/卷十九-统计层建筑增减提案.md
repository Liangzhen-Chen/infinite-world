## 结论（先读）

1. **必需。** 现行规则下，未物化站点的设施数与床位只由第 0 日清单给出（卷十 R10-7.4 :626；卷二十七 R27-2.10 :378）。统计层没有任何主体会盖房：卷六 §4.7 规则 11 的运行期投资（:626）只写给名册主体，卷十九 §4.4 的工程入口只收个人工时。而床位在人口承载力里恒参加取小（卷八 R8-16.4 :1118）。结果，离屏聚落从开局起就被开局床位封顶。按“不现实即缺规律”，这里缺的是统计层的建造规律。
2. **增：不另立判据。**
   - 应有几座、立不立项，一律沿用来源规则在个体层已有的判据，统计层只把主体换成聚合体。生产类与店铺类用卷六规则 11 的利润判据，先扩建、后新建；住处用一条两层共用的新来源（③-4）。
   - 卷十九只新增一个统计形态的建造执行器：立项、计工时、完工、扩建，全部走现有工程入口与唯一写者。
3. **减：不按人口减。** 减只来自卷十九既有的实物规则：劣化、不修、倒塌即终止。离屏时这条链缺两样，由减甲补（④-减）：
   - 未物化建筑没有行；
   - 统计层没有维护执行者。
4. **接口定为甲**：经 `requireMaterialized`，R27-2.10 原样不动。乙（另存增建清单）只登记为备选：卷二十七标定（R27-6.6）显示甲的离屏建筑数超预算时，再报李白。
5. **请李白批**：本提案整体方案，以及减甲的四项新设计（见文末）。

## ① 为何必需

1. **不定会怎样。**
   - 未物化站点的床位 = 清单经卷十九类型派生函数得出的计数（卷十 R10-3.10 :446；卷十 §5 :924）。清单在第 0 日按开局人数折户数、每户一处（卷十 R10-7.2 ④ :619），所以开局床位约等于开局人数。
   - `popCapacity = min(各 support_k, 床位数)`（卷八 R8-16.4 :1118），`headroom = popCapacity − total`（R8-16.5 :1119）。统计层的出生照常发生（R8-16.3），床位却不变，`headroom` 很快变负，于是迁出（R8-16.7 :1121）。**离屏聚落的人口被钉在开局床位附近。**
   - 单元内各站点人数按床位分摊（卷八 R8-16.1 第二款 :1112）。床位不变，分摊比例也就永远是开局的比例，离屏的城乡格局冻结。
   - 物化时建出的仍是第 0 日清单（卷十 R10-3.8 :444、R10-7.8），即使已经离屏五十年。
   - 卷十 §8 第 5 条（卷十:1066）与 C10-8（卷十:965）已登记“未给出”；卷二十七把它留给卷十九（:781）。
2. **与 R27-2.10 的关系。** R27-2.10 规定了怎么增减：先 `requireMaterialized`，再经卷十九的写者写。它没有规定谁、何时增减（末句 :378）。本提案补的正是“谁、何时”，接口甲完全在 R27-2.10 之内。
3. **为什么不按人口减。**
   - 人口下降，留下的是空房，空房失修后倒塌或被拆。卷十九已有这条链：
     - 劣化：§4.1 规则 6，:322；
     - 谁该修：§4.1 规则 8；
     - 倒塌即终止：§4.16 规则 4，:989；
     - 缩减时不拆：卷六 §4.7 规则 11“缩减”款，:629。
   - 空床使 `headroom` 转正，吸引迁入。这是空城重新住满的路径。
   - 若按人口自动减建筑，这条路就断了，还与守恒冲突。

## ③ 增减时点与判据（整类规则）

拟作卷十九 §4.4 新规则 10“统计形态的建造”，以及 §4.8 新规则“住处来源”。规则文字不出现任何设施类型、文化、地区代号。

1. **在哪一层执行。** 两层读同一份来源名单、同一判据：
   - 个体层：判据成立就立项（与卷六规则 11 运行期款相同，判据成立即立，不另交 NPC 取舍），出资方、出工方是名册主体。
   - 规则层与统计层：由新钩子 `settleStatBuild(unitId, span)` 执行，形态 `simform_stat`（卷二十七 R27-1.5 :276–277）。
2. **何时执行。** 每个整拍边界执行一次（R27-1.6 :281）。按卷十一 R11-3.14 登记 `after`，排在卷八 `settlePopulation` 与卷六统计劳动力、统计生产的同拍结算之后。
3. **立项判据。** 遍历顺序：站点按 id 升序，来源按登记序，同一来源内按（`intendedType` 代号，`ownerRef`）升序。
   - 缺口 `g = needed − 现有座数`。现有座数包括已建的（未物化时读清单的类型派生计数，已物化时数 `facilityView().type`）和本站点同意图、未完工的工程。
   - `g ≥ statBuild.minGap` 且 `admit` 为真，才立项。
   - `admit` 由来源给出：
     - 生产、店铺类：卷六规则 11 的利润判据（:626），主体换成 `ownerRef` 所指的聚合体或组织；
     - 礼拜、治理类：由卷七、卷八给出；
     - 住处：见第 4 条。
   - 不另设“付得起”。支付约束来自实际执行，与个体层同路：
     - 备料按卷六 §4.19 规则 4 从出资方账户采购，聚合账户的 `purpose_unmaterialized` 分区不可花（卷六:356）；
     - 钱或料不够就停工，不赊（§4.19 规则 6；卷十九 §4.4 规则 7）；
     - 停着的工程计入现有座数，所以不会反复立项。
   - **3a 生产来源：先扩建，后新建**（照卷六规则 11 运行期款的两种情形 :627–628，以及卷十九 §4.4 规则 8 :526，两层同式）：
     1. 工位缺口 `s = viableStations − 现有工位数`。现有工位数是该活动在站点上各设施 `stations` 之和；未物化时，按清单行 `fixtures` 的件数 × 类条目 `stationSlots` 求和（清单行 `fixtures` 即卷十 R10-7.3 写入的装置批）。`s ≤ 0` 时不做任何事。
     2. 装置类 `F` 照卷十 R10-7.2 ① 的同一取法选出（选中的 `F.stationSlots ≥ 1`）。
     3. **扩建**：在该站点上找类型相同、`ownerRef` 为份额持有人的现有设施，按设施 id 升序逐座加装 `F`。每座可加的件数 = `floor((floorAreaM2 × usableShare − 已装各件 footprintM2 之和) ÷ F.footprintM2)`，与 `ceil(s ÷ F.stationSlots)` 取小（`footprintM2 > 0`，除数恒为正）。每加一件，`s` 减去 `F.stationSlots`。扩建也要满足 `admit`，成本式取扩建情形。
        - 扩建是一项“加装”工程：装置物品经采购取得，安装照规则 8 建安装边，同一事务的砌料照 §4.1 规则 11“扩建”一行记账。
        - 不新增座数，所以不计入 `g`。
     4. **新建**：扩建之后若仍有 `s > 0`，该来源对（`intendedType`，`ownerRef`）返回 `needed = 现有座数 + 1`。“同一 `ownerRef`、同一设施类型合成一座”（R10-7.2 ①），新座的装置件数 = `ceil(s ÷ F.stationSlots)`，面积与形制照 R10-7.3。
     5. 店铺类同理：先看现有场所能否加装，余下的按家数式返回应有座数。
   - **3b 统计层 `ownerRef` 的出处**：
     - `stationPlan` 的归属推法（卷六 :624）在三种保有方式下的结果：
       - 归组织公有、归上级：`ownerRef` 是组织。组织在统计层照常存在（卷八 §5.4 :1350，组织不折叠），有出处。
       - 归户：取“技能最高、尚无同类设施的家户”。统计层单元没有家户行，卷六只写了生成期第 0 日的退回取法：按卷十 R10-7.4 同法，取该站点所在单元里人数最多的居民聚合体，并列取 id 最小。**运行期统计层没有已登记的出处。**
     - **最小取法（标明：本提案新增，须卷六写入 :624）**：把这条退回取法从“生成期第 0 日”扩到“运行期中，单元有效层不是个体层、因而没有家户行时”。取法不变，仍按 R10-7.4 同法，只扩大适用时点。个体层照旧取家户。住处来源的 `ownerRef` 见第 4 条，不经 `stationPlan`。
   - 每立一项，`g` 减一。同一拍内，后立的项读前一项入账后的状态，所以结果只取决于状态与固定次序。
4. **住处来源**（归卷十九 §4.8，两层同源）：
   - 单元缺床 = 单元常住人数（`popView`）− 单元可用床位数。缺户数 = `ceil(缺床 ÷ size)`（R8-16.10，`size ≥ 1`）。
   - 落点：在满足前状态的站点里，取“非床位各项 `support_k` 最小值 − 床位数”最大者，并列取 id 小者。
   - 返回 `needed = 该站点现有住处数 + 缺户数`。
   - `intendedType` 取住处句柄（同 R10-7.2 ④）。
   - `ownerRef` 两层同一律，取缺住处最多者：统计层取居民聚合体，个体层取无成员持有居住边的家户中人数最多者。并列取 id 小者。
   - `admit` 恒为真，支付约束同第 3 条。
5. **工时与完工。**
   - 立项调 `openBuildProject`。`chooseForm`、`buildPlan` 的输入照卷十 R10-7.3：技能读 `stratumSkill`，发起人取 `ownerRef`。
   - 工程作为雇主进入招工清单，统计层由阶层供工时（卷六 §4.11 规则 10）。`contributeBuild` 的出工主体取聚合体 id。工时达到 `laborMinutes` 时调 `completeBuild`。
   - 出资方成员归零时，照 §4.4 规则 7 停工。

## ④ 与卷十九现有统计层、实体层的接口（定为甲）

**现状。** 卷十九没有统计层规则，也没有矩阵行（卷二十七 :300 的收件名单里没有卷十九；卷十七 :835 指向卷十九，但卷十九未登记）。对未物化站点，卷十九只经卷十的类型派生函数与建行函数参与（R10-3.10 :446；卷十九 §4.4 规则 9 :527）。

**甲：经 `requireMaterialized`，统计层不存任何建筑计数。**

- 做法：
  - 立项（含扩建）的那一笔里，站点若未物化，先调 `requireMaterialized(site, 建筑与房间阶段)`，它会递归带出分片阶段。前状态要读分片行与已有建筑行，扩建要拿到现有建筑的 id，这都属于 R10-3.7 ②“要拿到其下某一行的 id”。
  - 此后与个体层同一路，卷六不改。物化出的行不回收（R10-3.11）。
- 代价：
  1. 物化的粒度是整个站点（大站点可达上万行，卷十:1074），而且不可回收。
  2. 离屏的劣化与维护要逐建筑结算，由 ④-减 给出，列为同批必改。离屏成本进入 R27-3.1 的成本式（:420）。
  3. 卷二十七登记上界一条（登记位同 R27-3.9–3.11 :443–445）：离屏已物化站点数 ≤ 统计层立项触发数 + 空置触发数 + R10-3.7 其他触发数，标定时实测（R27-6.6 :619）。
- 为什么定甲（依二版只核）：R27-2.10 原文就是“增一栋先调 `requireMaterialized`”，甲照它执行。乙要放宽这条已批规则，并要卷六另开未物化份额的来源。乙只登记为备选：标定超预算后再报李白，备选内容同第二版 ④ 乙。

### ④-减 离屏怎样减（定为减甲）

**沿用的现有规则**（建筑一旦成行就适用）：

| 规则 | 出处 |
|---|---|
| 劣化（没有闭式，须逐日算） | §4.1 规则 6 :322 |
| 修缮 | §4.1 规则 7 |
| 谁该修 | §4.1 规则 8 |
| 公共设施维护拨款 | §4.9 规则 1 :710 |
| 倒塌即终止 | §4.16 规则 4 :989 |

**现有规则撑不住的两处**：
- (a) 未物化建筑没有行，劣化起点取物化日（R10-3.8 :444）；
- (b) 统计层没有业主修缮的执行者（§4.1 规则 8 :363；卷六 §4.19 规则 8）。

**减甲做法：**

1. **空置触发物化**：同一拍里，站点可用床位 − 站点分摊人数 ≥ `statBuild.minGap × size` 时，调 `requireMaterialized(site, 建筑与房间阶段)`。此后照上表劣化、倒塌。
2. **修缮线**：`condition < repair.dueCondition`。这条线由 §4.9 规则 1 推广到全部建筑，作为两层共用的“业主该修”线；个体层把同一条线交给 NPC 作立项候选。
3. **修缮的条件**：维护责任人（规则 8）是聚合体或组织，且该建筑“在用”。
4. **“在用”的判据**（本版改；两层同式，只读 `popView` 与已登记维度，不读 `opsLevel`）：
   - 住处：站点内的住处按（`condition` 降序，id 升序）排，前 `ceil(站点分摊人数 ÷ 每处平均床位)` 处在用。
   - 生产与店铺设施：设施的工位所需服务代号（卷六 §4.11 规则 1 招工清单的服务代号）属于某一主业，且站点上该主业的分摊人数（`popView().byProfession`，卷八 R8-16.1 :1110）大于 0，该设施就是候选。同类候选按（`condition` 降序，id 升序）排，前 `ceil(该主业分摊人数 ÷ 每座平均工位数)` 座在用。主业属于哪些服务，读卷十四的职业与服务代号（卷六 :786 引卷十四 §4.1、§4.3）。
   - 礼拜、治理等公共设施：照 §4.9 规则 1，由持有组织的拨款决定修不修，不经本判据。
   - 两层用同一式：个体层的 `popView` 按实体行的常住地与 `primaryProfession` 计数（R8-16.1），所以两层算出的在用集合口径一致。
   - 不读 `opsLevel` 的理由：统计层生产走阶层聚合账户（卷六规则 12），不经设施，离屏的 `opsLevel` 恒为 0（卷十九 :949）。若读它，离屏生产设施会一律判为不在用而塌掉。
5. **使用强度**（同一真问题的另一半，随本条改）：劣化式里的 `ops.useIntensity`（:146）在统计层取不到进入人次与工位占用。统计层改为：在用设施取 `min(1, 对应人数 ÷ 在用设施的床位或工位总数)`，不在用的取 0；对应人数，住处是站点分摊人数，生产与店铺是该主业的分摊人数。个体层照旧由实测得出，层间差异由卷二十七基准核对（R27-1.5 的可观测量）衡量。
6. **修的走法**：在用的照规则 7 修。`repairFacility` 的出工主体取聚合体 id，料与工经采购与统计劳动力。

**结果**：空着的房子、没有对应从业者的作坊不修，按规则 6 与 §4.16 规则 4 塌掉，床位与设施真减；住着的、有人干活的照常修。

**代价**：
- 新增设计四项：空置触发；“在用”判据；统计层使用强度；`dueCondition` 推广到全部建筑。
- 衰退中的站点也会物化，甲的上界与离屏成本随之增加。
- 一直在用的开局建筑，仍取物化日为劣化起点，按“在用即修缮稳态”近似。
- `settleFacilities` 须声明矩阵行：个体层逐日；规则层与统计层 `simform_batch`，逐建筑逐日补结。

**为什么定减甲（依二版只核）**：另一做法（不物化、另算衰减）要为规则 6 另写一条衰减律，违反统一底层，还要放宽 R27-2.10。

## ⑤ 确定性与折叠

- 判据不掷骰。所有次序都取固定代号或 id 升序：站点、来源登记序、意图、`ownerRef`、扩建的设施 id、在用排序（`condition`，id）。
- 整拍边界执行，区间不跨拍（R27-1.6）。推进路径无关（R27-1.11 :292）；零头区间照 R27-8.6 :726 处理。

## 请李白批：整体方案与减甲新设计

请批两项。

**一、本提案整体方案**（裁定二③要求另走提案）：
- 统计层建造执行器：沿用来源判据，先扩建后新建，住处来源两层同源；
- 接口取甲，乙留作标定超预算后的备选；
- 统计层 `ownerRef` 的最小取法（3b）。

**二、减甲的新设计**，范围只限以下四项，必要理由同上：

1. **空置触发物化**：站点空床达到阈值时调 `requireMaterialized`。理由：不成行就无法劣化。
2. **“在用”判据**：住处按站点分摊人数，生产与店铺按主业分摊人数，两层同式。理由：统计层没有业主修缮的执行者，又不能让设施一律塌或一律不老。
3. **统计层使用强度**：按对应人数折算。理由：劣化式所需的进入人次与工位占用，统计层取不到。
4. **`repair.dueCondition` 推广到全部建筑**：作两层共用的修缮线。理由：私宅原本没有“该修”的数量线，统计层无从判定。

除这四项外，减甲不新增规则、不新增存储。
