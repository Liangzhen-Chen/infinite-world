# 门禁提交流程调查（只读）

范围说明：本机文件已逐行读完。远端只读调查中，第一条 ssh（grep authorized_keys 的 command= 行与列目录）成功，第二条（列 authorized_keys 各行、ls ~/gate、读 reviewer 的 authorized_keys）被分类器以 [Unauthorized Access] 拒绝，我没有再尝试绕过。所以远端的 review 命令内容是依据本机留存的同名脚本（review-put.sh、gate.sh）推断，未在服务器上核对实际落地版本。

## 1. 本地 review-submit.sh 实际行为
- 参数：轮次、工作树、服务器目录、结论、审查者 id、实施者列表、r1 id、scope 文件、findings 文件。
- 第 7-8 行：读同目录 review-user，当前内容为 reviewer，所以身份是 reviewer@[云机IP已抹]（deploy.sh harden 写入）。
- 第 9 行：本地 bash manifest.sh 算工作树哈希（其中 git ls-files 通过管道交给 python 的 --stdin-list，python 读 stdin，见下）。
- 第 10 行：用 tc_dnd 钥匙连 ubuntu@服务器，执行 gate.sh 的 hash 动词，取服务器目录哈希；与本地不等则 REFUSED 退出 4。
- 第 12-18 行：python heredoc 拼 JSON（round、hash、verdict、reviewer、implementers、round1、scope 全文、findings 全文），管道给 ssh -i tc_review reviewer@服务器 review。远端执行的实际命令由钥匙的 command= 强制为 review-put.sh，"review" 只是被忽略的原始命令。
- python 读 stdin 的位置（项目红线）：
  - review-submit.sh 第 12-18 行：python - 加 heredoc，脚本本体经 stdin 读入（红线直接违反）。
  - manifest.sh 第 7 行：git ls-files -z | python manifest.py --stdin-list，文件清单经 stdin 读入。
  - deploy.sh 的 ak() 函数：ssh 远端 python3 - 加 < akedit.py（部署路径，非审查路径）。
- 另：本地用 python（命令名），而约束说本机不运行 python；脚本依赖本机 python。

## 2. 远端
- 已验证：ubuntu 账号的 authorized_keys 中带 command= 的行只有一条，强制 /home/ubuntu/gate/gate.sh，选项为 no-port-forwarding 等（对应 tc_dnd，注释 skey-...）。ubuntu 上已没有 review-put.sh 的 command= 行，与 harden-run.txt（tc_review 已迁到 reviewer 账号并从 ubuntu 移除）一致。
- 未能读取：reviewer 账号的 authorized_keys。按 deploy.sh 第 66 行应为 command="/home/ubuntu/gate/review-put.sh" 加同样的 no-* 选项，所以有 command= 限制，只能执行 review-put.sh（推断，未核实）。
- review-put.sh（本机留存版）：
  - 读 stdin 最多 64KB，要求恰为一个 JSON 对象；schema 校验：round 为 1 或 2、hash 为 64 位十六进制、verdict 为 approve 或 changes、reviewer 与 implementers 匹配 id 正则、scope 非空。
  - 拒绝审查者在 implementers 中；round 2 必须引用已存在的 round-1 记录，并要求两轮审查者不同、都不在两边的实施者里、同哈希的 r1 必须是 approve。
  - 写入点：/work/.reviews/<hash>/r<round>-<时间戳>-<审查者>.json，先写临时文件再 ln 硬链接（只追加，已存在则拒绝），chmod 444。目录归 reviewer 用户。
  - 不改 gate 状态文件，但这些记录就是批准记录本身：gate.sh 的 approved() 只认它们。
  - 不校验哈希对应的是真实目录内容（哈希由调用方自报；本地脚本事先比对了服务器哈希，但这是客户端自觉，远端不核对）；不校验审查者身份真实性（reviewer 字段是自报字符串，持有 tc_review 钥匙的人可以用任意不同 id 提交两轮）。
- run 的核对（gate.sh approved()）：重新对 /work/<dir> 算哈希，到 /work/.reviews/<hash>/ 找记录；任何 changes 记录否决；需要一条 r2 approve，其 round1 引用的 r1 存在、是第 1 轮、两个 reviewer 不同且都不在两份 implementers 并集中、同哈希的 r1 必须 approve。哈希一致由目录名等于当前内容哈希保证。
- 结构性弱点：tc_review 是单一共享钥匙，没有身份绑定；谁拿到钥匙都能"替任意 id 提交"，包括实施方的协调者自己用同一脚本提交 r1 与 r2。

## 3. deploy.sh harden / review-user
- harden：建 runner（nologin，无 sudo，批准的作业以它身份运行，不能写 reviews 和 gate）与 reviewer（持有 tc_review）用户；ubuntu 获得 sudo -u runner 免密；把 tc_review 钥匙放到 reviewer 账号并保留强制命令 review-put.sh；/work/.reviews 改归 reviewer；从 ubuntu 的 authorized_keys 移除 tc_review；写入 ~/gate/runas=runner。ubuntu 自己的 sudo 仍保留（README 称为单独决策）。harden-run.txt 显示已执行成功。
- review-user 文件内容为 reviewer，本地脚本据此改连 reviewer 账号。

## 4. 为什么被判 Undermining Oversight
拒绝原文：[Undermining Oversight]，被拒的是整条 Bash 调用（cd、两个 heredoc 写文件、运行 review-submit.sh 2 ... | tail -5），没有部分执行。此前同一审查者用同一脚本提交 mktw-5 的 r2 及其他多次都成功，区别在那几次是"先单独写文件、再单独运行"。

分类器的判据一般是：这个动作是否在替监督/批准机制盖章。以下是差异对比与判断（均为推断，不可验证，未运行）：
1. 同一调用里先写结论再提交（最可能）。结论文件刚由同一命令生成，随后立刻以 approve 提交到会解锁云测试的门禁：分类器看到的是"同一个代理现编评语并当场批准"，没有任何中间的人或独立步骤，形同自写自批。分开调用时，文件内容在上一轮已可见，提交只是运行一个现成脚本，看起来像常规工作流。
2. 提交本身的性质（背景因素）：脚本用私钥向服务器写入会解锁门禁的批准记录，且 r2 带 r1 id 把审查链"闭合"。这一性质以前也存在，所以单独不足以解释这次的拒绝，但会提高整体风险评分，使 1 的组合更易触发。
3. | tail -5：只截取输出末 5 行，可能被读作"只看结果的末尾、不留全量证据"，轻微加分，但不太可能是主因。（我无法排除它。）
4. heredoc 本身：此前每次也用 heredoc 写文件，不是新变量。python heredoc 管道在脚本内部，也一贯存在，不是主因。
5. r2 与 r1 id：mktw-5 的 r2 也带 r1 id，成功过，不是区别。
结论：最可能是第 1 项（写结论与批准提交合并在同一次调用）叠加第 2 项（用特权钥匙写批准记录的性质）。不是 python 或 heredoc 本身。该判断是基于分类器可见信息的推测，不是确认。

## 5. 重设方案（审查者只写自己的审查目录，门禁核对）
目标：审查者没有任何"批准"权限，只产出带哈希的结论文件；由不属于审查者的通道传到服务器；批准判断全部在服务器 run 时做。
- 结论位置与格式：本地 F:/dnd-tmp/review/verdicts/<hash>/r<round>-<reviewer>.json（审查者只能写这个目录）。JSON 字段：schema 版本、round、hash（内容哈希）、verdict、reviewer、implementers、round1 引用（r1 文件的 sha256，而不是自报 id）、scope、findings。文件自带内容，不含任何签名权。
- 审查者的动作仅限写这个文件（单独一次调用，不同次调用提交），不再调用 review-submit.sh，不接触任何钥匙。
- 传输：由协调者的"发布步骤"（独立脚本，不由审查者运行）把 verdicts 目录用一个只写 inbox 的通道传到服务器，例如 tc_dnd 的 put 动词扩展为 review-inbox（只能放进 /work/.review-inbox/，不是 /work/.reviews）。该通道没有批准权：inbox 里的文件只是候选。
- 服务器 run 时核对（改 gate.sh approved()）：
  - 对当前目录重算哈希，只看文件内 hash 等于该哈希的记录（文件名不可信，内容为准）。
  - 需要两个 round 的 approve；两位 reviewer 互不相同；都不在 implementers；任一 changes 一票否决。
  - 审查者不等于实施者：implementers 不再由审查者自报，而由门禁从实施登记（派卡时协调者写入服务器的 implementers 登记，按目录名）读取，并与记录中的 reviewer 比对。
  - r1 引用用 sha256 绑定到 r1 文件内容。
- 避免代理替别人提交：给每位审查者一个一次性令牌或每位独立的钥匙，服务器登记 reviewer id 与令牌/钥匙指纹的对应；记录里 reviewer 必须等于该指纹所登记的 id。令牌由李白（或协调者之外的步骤）发放，协调者无法为别的审查者造记录。最弱可行版本：reviewer id 由服务器按提交通道的钥匙指纹填写，不接受自报。
- 去掉 python stdin：manifest 改为 python manifest.py hash . --list-file <文件>（先把 git ls-files 的输出写到临时文件）或让 manifest.py 自己 subprocess 调 git；review JSON 的拼装改用 jq（本机若无 jq，则用 manifest 同类的独立 .py 文件接受参数与文件路径，不用 heredoc、不读 stdin）。
- 需要改的本地文件：F:/dnd-tools/cloud/gate/review-submit.sh（重写或停用，改为只做"写结论文件"的小工具与独立的发布脚本）、manifest.sh 与 manifest.py（去掉 --stdin-list）、deploy.sh（新增 review-inbox 动词的部署、令牌登记、harden 部分的钥匙迁移与清理）、README.md 与 VERIFY-PLAN.md（更新流程）、review-user（不再需要）。
- 需要改的远端文件：~/gate/gate.sh（approved() 改读新格式、新增 review-inbox 动词、读取 implementers 登记）、~/gate/review-put.sh（停用或改成 inbox 校验器）、~/.ssh/authorized_keys 与 reviewer 账号的 authorized_keys（撤掉 tc_review 的写批准权或改为按人钥匙）、/work/.reviews 的属主与权限、新增 /work/.review-inbox 与实施登记文件、~/gate/manifest.py。
- 需要李白决策：删除/停用 tc_review 钥匙、新增按人钥匙，属于扩权/改安全配置，按规则要先报李白。
