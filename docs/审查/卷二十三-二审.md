## 二、新真问题

### N1 演出事件类型行与卷二十四 v2 对不上（局部）

位置：§2.5 :199–201，R23-4.1 :439。卷二十四 v2 表 C（卷二十四:180–196）、§2.6（:261–280）、R24-4.3/4.5/4.6/6.2。
1. `mode: onEvent` 错：卷二十四:570 R24-6.2 规定“某人决定办（C24-4 通用动作）”是 `mode` 为 `requested`；`onEvent` 是订阅动词引出。
2. 收场条件读不到：本稿在 `endings[].whenRX` 里读触发事件载荷 `actIndex + 1 >= actCount`，但卷二十四 §2.6 规定 `ev.<载荷字段>` 只给 `triggerRX`、`catalysts[].whenRX`、`completion[].whenRX`。可改为演出阶段的催化项 `{verb: actEnded, whenRX: ev.actIndex + 1 >= ev.actCount, points: 1}`，`advanceAt` 1，`advanceTo` 取结局 `done`（R24-4.5：转入目标是结局即收场）。
3. 节目单没有落点：`program` 是 `list<struct{actkind, piece, sides: list<list<EntityId>>}>`，放不进实例 `params`（卷二十四:237：`map<参数代号, 代号或 id 或整数>`；`paramsShape` 也不许嵌套表）；`startVerb` 由 `instanceStep` 发出（R24-4.1），载荷不取自起始请求。须在卷二十四现有形状内重定落点。一种做法是：`params` 只存整数 `actCount`，每一出的 `actkind`、`piece`、各方作为“演一出”动作的专有槽位。若作者认为必须扩卷二十四的 `params` 形状，写成对卷二十四的配合项，由主会话定。
4. 演者进不了席位：席位只能由 `roles.whoRX` 在起始时选入，或经 `seatMoves` 进出（R24-4.6）。本稿没给演者的 `whoRX`，也没登记 `seatMoves`，可是 R23-4.1 又要求“各方都在演者席位里”。须登记一条入席动词与 `seatMoves` 行。
5. `showOpened` 会发两次：它既是“开演”动作发出的催化事件，又是 `stageVerb`；按 R24-4.3，换阶段时实例会再发一次 `stageVerb`。须把动作事件与 `stageVerb` 分成两个动词。
6. 行与动词行缺必填项：
   - 事件类型行缺 `polarity`、`scopeKind`、`subjectFrom`、`allowedTargets`（onUnknown 为 error），各阶段也缺 `pace`。
   - 演出阶段 `durationDays` 为 0 且没有 `onExpire`，演者一直不来时实例永不收场。须给到期与结局（例如“散场”）。
   - 九个动词行缺表 B 的 `visibilityAllowed`（error），以及观众得知所需的 `perceivable`、`senses`（卷二十二 R22-2.2 读它们）。

### N4 C23-16 所请关系与原语表达不了（局部）

卷二 §1.12（卷二:313–315）：`relation` 行是 `{from: kind, to: kind, via}`，只能有一个起点实体类；`count` 的 `filter` 只读关系对象与主体的基值维度；封闭聚合族里没有“沿关系对某维度求和”。本稿有四处写不出：
- “宿主的装饰件”的宿主是 item 或 place，须拆成两行。
- “题材所指”的起点写成“实体或事件”。事件不是 22 类实体之一；人物题材存的是身份键，不是 EntityId（:150），按状态路径建的关系连不到个体。R23-6.5 的受益人要经 `linkKnown` 对到个体。
- R23-5.6 `workCount` 的过滤条件读 `workReach(k).places`，这是入口函数的结果，不是基值维度。
- R23-2.1 的 `coverShare` 之和、R23-7.2 的 `places` 之和、R23-6.5 的 `coverage` 之和，都是“沿关系求和”，没有原语可用。

改法：这些都写成本卷的纯函数入口（`adornCover(host)` 一类），沿已登记关系的反查索引逐个读；C23-16 ① 只请必要的反查关系，起点按实体类拆行；人物受益人走身份键索引再 `linkKnown`。删去“经 `count`”的说法。若坚持用原语，须请卷二封闭族增 `sumOf(rel, dim)` 并写必要理由。

### N5 装饰件的存放与生命周期（局部）

**附件机制核对**：卷三乙 §4.14（卷三乙:1503–1528）确实存在。宿主实例 `attachments`（写者 item-attach.mjs，卷三乙:352）、G-3 估值相加（V-4，:1617）、G-6 附件品质独立，与本卷用法相符；身体不能作宿主，符合 Q23-3。

但 G-1（占槽、预算）与 G-5（可拆）正与“不占槽、不可拆”相反。所以这是对附件机制的例外扩展，须在卷三乙写成通用规则，例如“无 `fitsSlot` 的附件为固结附件：不占槽、不可拆，以 `coverShare` 计”，按组件 `enables` 判定，不写成装饰件专条（C23-2 ② 改措辞）。

另有三处缺口：
1. **一个关系存了两处**：`hostRef`（装饰件上）与宿主的 `attachments`（或卷十九固定装置“装在哪”的持有边，卷十九:181）记的是同一个关系，又没有一致性规则。建议 `hostRef` 改为派生。
2. **宿主毁坏、转手时没有规则**：宿主毁坏时，固结装饰件应随之终止；转手时随宿主走。本卷都没写。
3. **写者写错**：§2.4（:188）、§3.2（:254）把宿主侧也写成由 dimension-writers 写，但卷三乙声明的 `attachments` 写者是 item-attach.mjs。

### N6 形式生成一点多值不合 R27-8.5（局部）

R23-3.3（:406）用一个抽取点 `site.works.formgen` 按字段的固定次序展开 `toolAbilities`、`performers`、`minutes` 等多值。卷二十七:665 R27-8.5 规定：一个抽取点一次取多个值时，须登记固定个数的位次，每个位次是一个不同的抽取点代号；只有“一串同分布的值”（如不放回抽 k 个）才由采样函数从一个键展开。须改为逐字段登记位次（如 `site.works.formgen.<字段>`）。§5.3 :705 “多值都从一个键展开”一句同改。
