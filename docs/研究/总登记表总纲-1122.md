### 2. "已接通"判据（能沿 import 从 index.mjs 到达）——站不住，必须改 ②③

判据原文是："有生产调用者，且提供方、调用者两个文件都沿静态 import 从 server-plugin/index.mjs 可达"（脚本 :463–465）。毛病有两处：

- **必须改 ②（经 register* 交入的看不见）**：settleBody 被判为"仅测试调用"。实际上 death.mjs:273 在模块加载时 `registerTerminationCleanup(S.cleanupRef, settleBody)`，交给 kernel/terminate.mjs，这是卷四 :430 写明的唯一接法。脚本跳过提供方本文件（:446 `if (f === p.file) continue`），所以看不见。凡经 `register*` 交给内核的钩子、清理函数、派生函数，都会同样误判。
- **必须改 ③（文件可达 ≠ 调用点活着）**：这条判据只看到模块一级。runDelegated 判"已接通"靠两个调用点：death.mjs:234 在 die 里，die 本身没有生产调用者（卷四 :426 写 lifeTick 调 die，但 lifeTick 未建）；death.mjs:210 在 settleBody 里，settleBody 是经 register 交入的，确实活着。本例碰巧对了，但判据本身分不出死调用点。"入口要有生产调用者"是块验收的硬条件（修理与重排 §四），判据放过死调用点，块验收就会被骗过。改为：调用点所在的函数本身已接通，或在可达模块的顶层，或经 `register*` 在这样的位置交给内核。从 index.mjs 的装配调用（state-owners `assembly.calls`）起，按调用点逐层推。
- **必须改 ④（范围只有各卷 §3.1，公共部件不在表里）**：修理文档点名的入口，有 installSaveEnv、setGame、bindCampaignSeed、perceiveEvent、tempAt、isPosValue、registerEventDerive，以及要新建的 familyEntries、rowIds、dimDef，都不在 620 项里。kernelApi 181 条里有 130 条不在。代码里有、卷文没登记的导出共 778 个（清点 §六）。李白要求"公共部件审查以这张表为准"，表里没有公共部件，就做不到这一点。第三步的种子要并入 kernelApi 全部导出、state-owners 的 view/predicates/entryCallerFiles 键，以及被别卷文件导入的导出。

### 3. "绕开处漏报多"对"按表查绕开"意味着什么——自报如实，过；结论是表只是三个输入之一

甲乙两份审查查出的绕开共 117 处（甲 36、乙 81）。清点只收到 23 条，去重后 12 个文件行，约一成。原因是多数绕开换了名字，把同一算法另写了一份：年龄换算 life.mjs 与 person.mjs、区格换算 8 处、事务裸写 5～6 份、规则表直读 28 个文件。这些都不是某个 §3.1 入口的同名重定义。由此判断：

- 按表能查的只有三类：
  - (a) 导入别卷提供方文件里未登记的导出（跨卷调用没经登记入口）；
  - (b) 同名另定义（脚本已有的"新发现"口径）；
  - (c) 读取某入口指定独读的资源。这又分两种：state 键的读者闭集已在 state-owners `stateKeys.readers`，由 path_access 守；规则表键要新增 `rules` 字段，登记谁是指定读者。
- 换名另算一份的，表查不出。这一类要靠 C0 的现有检测器（lit_scope 抓共享公式的特征常量、decl_cmp、call_edge），再加人工审查。所以"检查脚本按这张表查绕开"要写成：表给出提供方文件、指定资源和登记名单，C0 的检测器按这些参数判；不能宣称"按表查全了绕开"。
- 公共部件必须进表（见必须改 ④）。否则 (a)(b)(c) 连事务裸写、setInTx 这类最常见的绕开都对不上号。

### 4. 两个小环——都是清点口径问题，不是真依赖环；必须改 ⑤

- acceptance ↔ acceptanceOfPerson。真依赖只有 acceptanceOfPerson → acceptance：卷七 :1387 R7-23.7 写"`score = acceptance(O, B).score + m × …`"。反方向那条边，来自卷七 :407 acceptance 行说明格里的"改绑 `acceptanceOfPerson`，见下一行"，这只是交叉引用。

## 二、唯一出处

### 定在哪

**`tools/accept/entry-registry.json`**，一份数据文件；卷二 §2.7 只写规矩和位置（勘误 1124k110）。理由：

- 不放卷二正文。620 行以上的表抄进卷文，只能手工维护行号与状态；状态和行号会天天变，按"能派生的不另存"不该写进卷文。
- 不并进 state-owners.json。它是运行期装载的契约文件，加载器 kernel/load/state-owners.mjs:22 有封闭的字段表。把设计期元数据（卷、节、needs）塞进去，要改内核加载器，运行期也会读到用不上的东西。它管的是"谁可以调"（callers 闭集、acceptsState），总登记表管的是"有哪些入口、谁提供、设计上依赖谁"，两件不同的事，各在一处。
- 放 tools/accept/。消费它的是提交门禁（tools/accept/detectors）和派卡自查（tools/accept/lib/card-selfcheck.mjs），criteria.json、items.json 也都在这里。

### 形状

```json
{
 "version": 1,
 "kinds": ["read", "predicate", "write", "hook", "kernel", "part"],
 "entries": [
  {"name": "acceptanceOfPerson", "file": "culture.mjs", "vol": "卷七", "sec": "§3.1", "kind": "read",
   "needs": ["culture.mjs#acceptance"], "rules": []}
 ]
}
```

- 行键是 `file#name`，与 state-owners 同一写法，同一行键只一行。同名不同文件是两行（bearingView）。同一入口在别卷只是被引用或列举的（如卷二 §2.1 列出的各卷 view），不另立行。清点里同名跨卷的 22 项（620 − 598），第三步逐个定提供方卷。
- `file` 可以为 null，只限"卷文未写文件且代码未建"。代码一旦导出该名，就必须填上并与代码一致。null 不豁免别的检查（卡头第二节第 3 条）。

### 字段：哪些存、哪些派生

| 字段（李白所列） | 存还是派生 | 怎么来 |
|---|---|---|
| 入口名 | 存 `name` | — |
| 提供方卷:行 | 存 `vol`、`sec`；行号派生 | 在该节表格、列表里找名字，勘误插行不失效 |
| 提供方文件 | 存 `file`（设计声明）；代码文件:行派生 | 派生值与 `file` 不符即违例 |
| 设计上的调用方 | 派生 | 其他行 `needs` 的反查；卷文里 `名(` 调用形的出现只进报告，不作判据（泛词偏多） |

| 接通状态 | 派生 | 按必须改 ③ 的调用点口径 |
| 依赖 | 存 `needs`；代码依赖派生 | 代码依赖 ⊄ `needs` 即报告 |
| （新增）种类 | 存 `kind` | 封闭枚举在文件头 |
| （新增）指定资源 | 存 `rules` | 绕开 (c) 用；state 键不在这里记 |
