## 一、`holdWhile`（手持行的存续条件）要读的量

### 要什么

**（1）卷十三 §2.3 登记四个读时派生量。** 不落存储，写法同该表已有的 `person.forcePower`、`org.forceMorale`。四个量都按状态定义：一般读取时按现状算；R18-1.12 求值时，按该条规则给出的“假设状态”算（绑定方式见 §2.4 变量表，见第 (5) 点）。

| 表 | 维度 | 类型 / 单位 | 取值域 | onUnknown | 含义（唯一定义处：卷十三 R13-5.2） |
|---|---|---|---|---|---|
| person | `graspLimbs` | derived integer count | ≥ 0 | gap | 可用操持肢端数：身体图部位 p 中，`contributes[p][c] > 0` 且有效完好度 `eff(p) > 0` 的个数。c 是规则表键 `rules.combat.roles.graspCapability` 所指的能力 |
| person | `handsHeld` | derived integer count | ≥ 0 | gap | 已占手数：该主体每条现役手持边各自占手数之和 |
| item | `wieldHands` | derived integer count；`allowExplicit:true` | ≥ 1 | gap | 握持这件物要几只手，算法见第 (2) 点 |
| item | `wielders` | derived integer count | ≥ 0 | gap | 以该物为标的的现役手持边条数 |

一条手持边的**占手数**是 `⌈wieldHands ÷ wielders⌉`（向上取整），用派生公式算，不新增存储。

**（2）`wieldHands` 覆盖一切可握之物。** 撤回第一版“没有 `weaponClass` 就不能手持”的说法。依据是 R13-5.2“一手兵器一手盾”与 R13-10.6“持投射器的、持格挡物的”（卷十三 :903）。

- 派生式：`first(rules.combat.grip.handsRows)`。规则表是有序的，每行为 `{when: rx, hands: integer ≥ 1}`。
- `when` 只读物品的组件类代号集合（固定代号）与数值维度（如 `massKg`）。另有一个变量 `subject.classHands`：物品有 `weaponClass` 时，取该条目的 `weapon.hands`；没有时不适用。按卷二 §1.12 的未知传播总则，读到不适用变量的那一行按未命中处理。
- 表里一般第一行写“有武器类别时取 `classHands`”，后面各行写盾、投射器等其他可握之物的数值判据。行的内容与顺序都是数据，规则文字不点名组件。
- 派生式全部未命中时，按卷二 §1.6 `allowExplicit` 的写法：物品行显式写值并附 basis。这和 `categoryKind`、`sourceMode` 是同一种写法（卷二 :224）。
- 派生式未命中、也没有显式值的，本维度不适用，结果是这件物不能挂手持边。

**（3）卷十三 §2.5 新增规则表键。**
- `rules.combat.roles.graspCapability: ref vocab capability`，放在现有 `roles.kinds`（:338）旁边。
- `rules.combat.grip.handsRows`，即上一点的有序表。
- 规则文字里不出现能力代号或组件代号。

**（4）手持行 `holdWhile` 取值**（卷十八 §4.1.5 手持一栏）：

`holder.handsHeld <= holder.graspLimbs && subject.wielders <= subject.wieldHands`

前半句是 R13-5.2 的不等式，后半句是 R13-15.2“上手人数由 `hands` 限”的不等式。只读数值维度，不出现种类代号。

**（5）R18-1.12 求值时点与顺序。** 两条都是通用规则，覆盖所有 `holdWhile` 非空的行，规则文字不点名种类。

- **按事务成组求值**（解决合握起手）：
  - 一笔事务里写入的全部新边，在该事务提交前一并求值。求值所用的“假设状态”是本事务全部写入完成之后的状态。
  - 所以多人合握是一次成组写入：同一个握持动作的执行器，在同一笔事务里写入全部共握者的边。动作由一位发起者提交，共握者列在 `multi` 槽位里，各人的同意走卷九同意条款。
  - 举例：四人一起去握 `hands` 为 8 的撞槌，`wielders` 为 4，每人占 ⌈8÷4⌉ = 2 只手，不超过 2，写入。
  - 一个人单独去握，`wielders` 为 1，占 8 只手，大于 2，拒写。这是“一个人举不起”，符合实际。
  - 后来加入的人单独写入时，`wielders` 包含先到的人，⌈8÷5⌉ = 2，写入。
  - 这与 R18-1.5 的 `holderMax`“写入后持有者一端仍超限即拒写”（:472）是同一种写法。
- **重算时按建立先后逐条放回**：
  - 重算现役边时如果条件为假，把同一持有者在该种类下的现役边按建立先后排序（先按 `terms.since` 升序；同刻按边 id 的代号序），从空集开始逐条放回。放回后条件为真的留下，为假的按该行“离任”格处置。
  - 例一：可用肢端从 2 降到 1，手上原有一把双手兵器和一面盾。不论先拿的是哪一件，结果都是双手兵器关闭、盾留下。
  - 例二：合握撞槌的人从 4 降到 3，剩下每人要占 ⌈8÷3⌉ = 3 只手，三人的边依次关闭，撞槌落地。这一步由“写到标的即重算”接住。
- **成组写入中部分边为假**：本事务的新边中只要有一条使条件为假，本事务的全部新边一并拒写，报 E-HK-HOLD-WHILE。不只拒那一条，是因为拒掉一条会让 `wielders` 变小、其余各条的占手数变大，结果会随先拒哪一条而不同。例：四人合握撞槌，其中一人只剩一只手，整批举不起来，符合实际。
- **结果未知按假处理**，与 R18-1.12“为假即拒写”是同一个出口。

### 谁读谁写

- 四个派生量没有写者，由卷十三的读入口在读时算出（`combatReadings` 一族，卷十三 §3.1）。
- 输入来源：
  - `eff(p)` 只在 status.mjs 写入或移除挂在部位上的状态实例时改变（卷四 B-2）。换档由写实例的写者在事务里写入，并发换档事件（卷二十一 :1333）。所以条件仍由事务推动，不需要轮询。
  - 手持边只经持有写者写入。
  - `handsRows` 是规则表数据。
- 读者只有持有写者，在 R18-1.12 规定的时点求值。
- 合握的成组写入由卷九的握持动作执行器发起，经持有写者落地。
- `graspLimbs` 不读 `bodyView().dims` 的能力值，所以不碰卷四 P-5 (c) 的禁令。

### 不定会怎样

- 手持行进不了数据块，`rules.combat.roles.kinds.wielding` 指不到行，加载失败（卷十三 :338）。
- 行即使硬并进去，`holdWhile` 读不到登记变量，编译失败（卷十八 §4.1.1 :411）。
- 求值时点不按事务成组：多人器械谁都拿不起来，R13-15.2 落空。
- `wieldHands` 只读武器类别：盾和投射器挂不上手持边，R13-5.2 与 R13-10.6 落空。
- 不按建立先后放回：一只手已占时还能再拿起双手兵器；伤手后同一人的全部手持边被一起关闭。

### 同类先例

- 读时派生维度登记在卷十三 §2.3：`person.forcePower`、`org.forceMorale`。
- 句柄放规则表：`rules.combat.roles.kinds`（卷十三 :338）、`rules.combat.morale.gauge`（R13-8.1）。
- 派生式未命中时显式补值：卷二 §1.6 `allowExplicit`（:224）。有序规则表 `first(rules)`：卷二 §1.12。
- 写入后再核对：R18-1.5 `holderMax`（:472）。
- 多人槽位：卷九 §4.19.1 的 `multi` 槽位（卷二十三 :201 `sides: code multi` 照用）。
- rx 可读变量由登记方给出：卷十八 §4.1.1 :411、§2.4 变量表（:240）。

## 二、手持、在编两行的 `functional`（持有者失能时边不生效）

### 要什么

- **手持取真，在编取真。**
- 两格只凭同类先例取值，不另立整类判据，也不改 §4.1.1 的含义栏。
- 手持取真：手持边的效力（格挡、技法修正、打法候选，R13-5.4、R13-5.5）都是握持者出手才有的。这和“经营” `hk_operates`（持有者亲自使用物或场所，取真）同类。
- 在编取真：在编边的效力是这个人在兵力里算一份力，R13-8.1 的士气聚合与 R13-10.5 的兵力求和都按它计。这和“受雇” `hk_employed_by`（凭契约提供劳务，取真）同类。R13-10.2 规定三种兵都出自合同，与受雇同源。
- 在编挂在“成员” `hk_member_of`（取假）下面，这不妨碍它取真：“户主” `hk_household_head` 也挂在“成员”下，自己取真（:499）。
- 失能时边仍是现役，不关闭，只是不生效；恢复后自动重新生效。真正要放下兵器走第一处的 `holdWhile`，要离队走在编行的处置格。三件事各归各的列。

### 谁读谁写

- 写：本卷 §4.1.5 数据块。种类表没有运行期写者（§4.1.2 :464）。
- 读：读现役边的各个入口。行动能力只经卷二 §2.5 的状态谓词判断。
- 先例：监护行“`functional` 为真，加候补顺序”（:1378）；卷十三 A13-14.2“能行动”（:1091）。

### 不定会怎样

- 主列逐格必写（:494）。缺这一格，两行进不了数据块，加载失败。
- 定错的后果：
  - 手持取假：昏迷者仍按握持计格挡。
  - 在编取假：昏倒的兵仍计入兵力与士气。
  - 两者都与卷十三“能行动”的口径矛盾。

### 同类先例

- 取真的五行：`hk_household_head`、`hk_operates`、`hk_employed_by`、`hk_holds_office`、`hk_guardian_of`（卷十八 :499、:505–507、:514）。
- 取假的成员类：`hk_member_of`、`hk_business_member_of`、`hk_devotee_of`、`hk_citizen_of`（:497、:509–511）。

## 三、各动词的 `perceivable` / `senses`

### 判据（只看已登记的发出点）

本卷对每个动词，都登记了发出它的规则，即 §2.3 :183 的发出系统，加上各条规则写明的触发。判据只看这条发出规则的触发方式，不看动词名、也不看载荷字段：

- **动作发出**：发出规则的触发是一个行为人的动作，即卷九动作目录的一条动作在其裁决事务里落定（条文写成“是……的动作”，或写在某动作的裁决里）。取 `perceivable` 真、`senses` {视觉通道, 听觉通道}。
- **非动作发出**：发出规则的触发是固定刻、到期项、终止订阅、合同履行、推断，或另一笔写入的连带处置（写边时连带发出、复查时连带转中止）。取 `perceivable` 假、`senses` `[]`。
- 一个动词有多个发出点时，只要其中一个是动作发出，就取真。这样做没有副作用：R22-2.2 判定的是旁人是否“感知到该动作”，从非动作发出点发出的那几条事件，本来就没有可感知的动作，不会凭空多出亲历者。

两个“通道”指卷五 `sense` 族（前缀 `sense_`，卷五 :165）中承载光、声的两条。落正文时按卷五数据写出代号，本提案不新造代号。

### 按判据归类（每条都给出发出规则作为依据）

### 待李白选 3：成婚

  - 牵连：
    - 卷十八 R18-2.3（:646）与 §2.1 婚约合同行（登记成礼义务）；
    - 本节判据（补那一句）与归类表（成婚改为可感知类，取真、{视, 听}）；
    - 卷六 `needsPresence`（:134、:980）已有，不改。
  - 代价：
    - 判据多出一种来源，但只读已登记的布尔值，仍是整类规则；凡 `needsPresence` 为真的义务履行事件都自动适用。
    - 要补写成礼义务的条款；履行仍走卷六的现有状态机。
- **乙**：成婚改为卷九动作目录里带同意条款的一个动作，按判据直接归动作类。
  - 牵连：
    - 卷九动作目录新登一行（含同意条款）；
    - 卷十八 R18-2.3 改为“婚约到期后由当事方提交成婚动作，动作落定时写婚姻边”；

    - 卷九要多登记一个动作行。

## 五、`lieId`、`subjectRef` 的类型

### 5.1 `lieId`

**要什么**：`lieId` 的类型是 `EventId`，取值是登记这条谎言的那次说谎动作落定时的事件 id。

- 不变量：一次说谎动作只登记一条谎言（R9-13.9 每张决定卡带一条）。
- 复述旧谎：`toldTo` 增加，id 不变。
- 谎言揭穿的 `payloadShape` 为 `{lie: EventId}`。
- 事件 id 按卷二十七 R27-8.9 确定性派生。

**先后顺序**（对应只核真问题 5）：
- 新说一句谎话时，决定卡在落定**前**只带命题（`claim` 的结构化字段），外加一个“新谎”标记，不带 id。
- 动作落定的那笔事务里，lies.mjs 登记谎言，id 取本次事件的 id（R18-5.6“说谎即在谎言账登记一条”）。
- 复述旧谎时，决定卡带已有的 id。
- 所以 R9-13.9“决定卡带一条登记的谎言 id”要改成两种情形：复述旧谎带 id，新说的谎带命题。§4.11 的放行改为按命题或 id 放行。见牵连清单。

**谁读谁写**：
- 写：lies.mjs（`state.lies[EventId]`，:322）。
- 读：卷九 R9-13.9、卷二十二、立场与威望来源行。

**不定会怎样**：谎言揭穿的载荷缺写，加载失败；`state.lies` 的键没有类型，pathTypes 生成不了。

**同类先例**：卷二十二 :169 `factKey = (kind, eventId)`；卷二十四 :155 实例 id 由起始事件 id 得来；成婚的 `consentAct: EventId`（:189）。

### 5.2 `subjectRef`

**要什么**（依只核取甲；只用已有的 `EntityId`、`EventId`，不新造类型）：

- 对象一律写成两个可空字段：`subjectEntity: EntityId nullable`、`subjectEvent: EventId nullable`，二者恰好一个非空。写法照谎言账 `claim{event: EventId nullable, subject: EntityId}` 的先例（:807）。
- 群体行为载荷：`{group: EntityId, axis: ref vocab stance_axis, pressure: number, subjectEntity: EntityId nullable, subjectEvent: EventId nullable}`。`subjectEntity` 是实体类载荷字段，按表 B 映射到 related 角色，卷二十二按 `mentions` 检索能找到这件事。
- 冷却键分两个容器，免得实体 id 与事件 id 同在一个键位：
  - `state.opinion.lastFired.byEntity[groupId][EntityId][triggerRow]`
  - `state.opinion.lastFired.byEvent[groupId][EventId][triggerRow]`
  - 两个都在去留表登记，口径同原条目（:335）。
- `opinionOf(engine, state, groupId, subjectEntity, subjectEvent, axisHandle)`：两个形参恰好一个非空。
- “恰好一个非空”由构造保证：opinion.mjs 是唯一的发出者与写者，每次都从一个（群体、对象）对出发。另加一条不变量式验收断言，不新增错误码。

**谁读谁写**：
- 写：opinion.mjs。
- 读：`opinionOf`（:298）、卷二十二 `publicShare`（卷二十二 :256）、卷八民心与治理。

**不定会怎样**：群体行为的载荷不完整，加载失败；冷却键与入口形参没有类型，pathTypes 与 tsc 品牌检查都过不了。

**同类先例**：谎言账 `claim`（:807）以两个字段分写实体与事件；卷二 §1.5 规定字串形态的成员不能同在一个 `anyOf`（:182），这正是甲案不用联合类型的原因。
