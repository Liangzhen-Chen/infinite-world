## 一、`holdWhile`（手持行的存续条件）要读的量

### 要什么

**（1）卷十三 §2.3 登记四个读时派生量**（不落存储，写法同该表已有的 `person.forcePower`、`org.forceMorale`）：

| 表 | 维度 | 类型 / 单位 | 取值域 | onUnknown | 含义（唯一定义处：卷十三 R13-5.2） |
|---|---|---|---|---|---|
| person | `graspLimbs` | derived integer count | ≥ 0 | gap | 可用操持肢端数：身体图部位 p 中，`contributes[p][c] > 0` 且有效完好度 `eff(p) > 0` 的个数。c 是规则表键 `rules.combat.roles.graspCapability` 所指的能力 |
| person | `handsHeld` | derived integer count | ≥ 0 | gap | 已占手数：该主体在“求值集合”里每条手持边各自占手数的和（占手数见 item 行）。求值集合在一般读取时就是现役手持边；在 R18-1.12 求值时由该条规则给出（见下面第 3 点） |
| item | `wieldHands` | derived integer count | ≥ 1 | gap | 该物的 `weaponClass` 所指条目的 `weapon.hands`。物品没有 `weaponClass` 时，本维度不适用（`applicable:false`） |
| item | `wielders` | derived integer count | ≥ 0 | gap | 以该物为标的的手持边条数，按求值集合计 |

一条手持边的**占手数**取 `⌈wieldHands ÷ wielders⌉`（向上取整）。这样一个人独握时占满 `hands`；多人合握一件器械时，各人分摊。见下面“待李白选 1-A”。

**（2）卷十三 §2.5 新增规则表键** `rules.combat.roles.graspCapability: ref vocab capability`，放在现有的 `roles.kinds`（:338）旁边。规则文字里不出现能力代号。

**（3）手持行 `holdWhile` 取值**（卷十八 §4.1.5 手持一栏）：

`holder.handsHeld <= holder.graspLimbs && subject.wielders <= subject.wieldHands`

前半句是 R13-5.2 的不等式，后半句是 R13-15.2 “上手人数由 `hands` 限”的不等式。表达式只读数值维度，不读文字，也不出现种类代号。

**（4）R18-1.12 补两句通用规则**（不点名种类，覆盖所有 `holdWhile` 非空的行）：

- 写新边时，在“写入后”的状态上求值：求值集合包括这条新边。这和 R18-1.5 的 `holderMax`“写入后持有者一端仍超限即拒写”是同一种写法。
- 重算现役边时，如果条件为假：把同一持有者在该种类下的现役边按建立先后排序（先按 `terms.since` 升序；同一时刻按边 id 的代号序），从求值集合为空开始逐条放回。某条边放回后条件仍为真，就留下；为假的，就按该行“离任”格处置。

举两个例子。伤了一只手、可用肢端从 2 降到 1，手上原有一把双手兵器和一面单手盾：不论先拿的是哪一件，结果都是双手兵器被关闭、盾留下，这正是 R13-5.2 例子要的结果。四臂生物（:728）不需要特例。

**结果未知时**：`holdWhile` 的结果未知（例如物品没有 `weaponClass`，`wieldHands` 不适用），一律按“为假”处理，即拒写。这和 R18-1.12 的“为假即拒写”是同一个出口。

### 谁读谁写

- 四个派生量都没有写者，只在读时由卷十三的读入口算出（`combatReadings` 一族，归卷十三 §3.1）。各自的输入来源如下：
  - `eff(p)` 只经 status.mjs 写入或移除挂在部位上的状态实例而改变（卷四 B-2，:448）。
  - 状态换档由写实例的写者在事务里写入，并发换档事件（卷二十一 :1333）。
  - 手持边只经持有写者写入。
- 唯一的读者是持有写者：写入时、以及 R18-1.12 规定的事务提交前，它求 `holdWhile` 的值。
- `eff(p)` 只在状态写入的事务里变化，所以只核报告担心的“完好度随时间连续变化，要靠固定刻”这种情况不会出现。条件仍然靠事务推动，不需要轮询。
- `graspLimbs` 读的是 `bodyView().parts` 的部位贡献与有效完好度，不读 `bodyView().dims` 里的能力值，所以不碰卷四 P-5 (c) 的禁令（:370）。

### 不定会怎样

- 手持行不能进入数据块，卷十三 `rules.combat.roles.kinds.wielding` 指不到行，加载失败（卷十三 :338）。
- 即使把行强行并进去，`holdWhile` 也读不到任何已登记的变量。按卷十八 §4.1.1 :411，“变量名与取数归登记该行的卷”，结果是编译失败。
- 不补第 (4) 点：一只手已占时，再拿双手兵器也能写进去（只核报告第三节第 4 条）；伤手之后，同一个人的全部手持边会一起被关闭。

### 同类先例

- 读时派生、不落存储的维度登记在卷十三 §2.3：`person.forcePower`、`org.forceMorale`（卷十三 :236–238）。
- 句柄放规则表、规则文字不写代号：`rules.combat.roles.kinds`（卷十三 :338）、`rules.combat.morale.gauge`（R13-8.1）。
- 写入后再核对、超限即拒写：R18-1.5 的 `holderMax`（卷十八 :472）。
- rx 可读变量由登记方给出：卷十八 §4.1.1 `holdWhile` 行（:411）、§2.4 变量表（:240）。

### 待李白选 1-A：多人合握时每人占几只手

- **甲（推荐）**：占手数由派生公式 `⌈wieldHands ÷ wielders⌉` 算出，不新增存储。
  - 代价一：有人松手时，其余合握者的占手数会变大。这一步由 R18-1.12 的“写到标的即重算”接住。
  - 代价二：分摊方式由规则统一决定，玩家不能指定“我出一只手还是两只手”。
- **乙**：卷十八 §4.1.1 键表新增 termsKey `grip: integer`（本条边占持有者几只手），握持时写入。约束是：独握时等于 `hands`，合握时每人至少 1，各人之和不超过 `hands`。
  - 代价一：需要新增一个键和三条写入校验，持有写者要多接一个输入。
  - 代价二：与“派生优先”相悖。

另有一个后果（两个候选都一样）：没有 `weaponClass` 的物品不能挂手持边。所以 R13-5.2 例子里的盾，数据上必须带一个武器类别。这是数据要求，不另立规则。

## 二、手持、在编两行的 `functional`（持有者失能时边不生效）

### 要什么

- **手持 `functional` 取真，在编 `functional` 取真。**
- 整类判据（写进 §4.1.1 `functional` 的含义栏，作为解释，不新增规则）：如果这种边的效力要靠持有者本人持续行动来实现，取真；如果只是归属、名分、占有这类状态，取假。现行数据块里取真的五行都属于前一类：户主、经营、受雇、任职、监护。
- **手持取真的理由**：手持边的效力（格挡、技法修正、打法候选，见 R13-5.4、R13-5.5）都是握持者出手才有的。这和“经营” `hk_operates`（持有者亲自使用物或场所，取真）同类。
- **在编取真的理由**：在编边的效力是这个人在兵力中算一份力，R13-8.1 的士气聚合、R13-10.5 的兵力求和都按它计。这和“受雇” `hk_employed_by`（凭契约提供劳务，取真）同类。R13-10.2 规定三种兵都出自合同，与受雇同源。
- 在编的上位词“成员” `hk_member_of` 取假，这不妨碍在编取真：“户主” `hk_household_head` 也挂在“成员”下面，自己取真（:499）。
- 失能时，边仍然是现役（不关闭），只是不生效；恢复行动能力后自动重新生效。真正要“放下兵器”，走第一处的 `holdWhile`；真正要“离队”，走在编行的处置格。三件事各归各的列。

### 谁读谁写

- 写：本卷 §4.1.5 数据块，种类表没有运行期写者（§4.1.2 :464）。
- 读：读现役边的各个入口。行动能力只经卷二 §2.5 的状态谓词来判（`can` 等），不读阈值。
- 先例：监护行就是“`functional` 为真，再加候补顺序”来处理监护人失能的（:1378）。卷十三 A13-14.2“来源……能行动”（:1091）也是同一个口径。

### 不定会怎样

- 主列是逐格必写的（数据块 `columns` 中有 `functional`，:494）。缺这一格，两行就进不了数据块，卷十三两个句柄指不到行，加载失败。
- 定错了也有后果：
  - 手持取假：昏迷者手里的兵器仍按握持计格挡。
  - 在编取假：昏倒的兵仍计入兵力与士气聚合。
  - 两者都与卷十三已有的“能行动”口径相矛盾。

### 同类先例

- 取真的五行：`hk_household_head`、`hk_operates`、`hk_employed_by`、`hk_holds_office`、`hk_guardian_of`（卷十八 :499、:505–507、:514）。
- 取假的成员类：`hk_member_of`、`hk_business_member_of`、`hk_devotee_of`、`hk_citizen_of`（:497、:509–511）。
- 坦白一个出入：“看管” `hk_custody_of`、“操控” `hk_commands` 取假，与本判据不完全吻合。这两行是 §7 逐格照迁的旧值（:1377），本提案不动，留给只核者判断是否要记账。

## 三、各动词的 `perceivable` / `senses`

### 要什么

分类依据是卷十八 §2.3 :183 已登记的“发出系统与发出点”，再加上卷二十二 R22-2.2 的判定对象：被感知的是“该动作”，即当场的身体行为。分三类，同一类取同一组值：

| 类 | 判据（按发出点与载荷结构判，不看动词名） | `perceivable` | `senses` |
|---|---|---|---|
| 甲 当场行为 | 事件本身就是行为人在发生地当场做出的、有形迹的身体行为 | 真 | {视觉通道, 听觉通道} |
| 乙 随动作落定 | 事件是名分的改变，但恒在一个卷九动作的同一事务里发出，且载荷有一个非空的 `EventId` 字段指向那个动作 | 真 | {视觉通道, 听觉通道} |
| 丙 状态改变 | 关系、名分、权属、账目、认知的改变，由写者在固定刻、派生规则或别的写入里发出，没有当场形迹 | 假 | `[]` |

卷十八各动词的归类：

- **甲**：斗殴开始（R18-12.5）。它在一次互动之后当场抽中而发出，是身体冲突。
- **乙**：成婚（载荷 `consentAct: EventId` 非空，R18-2.3）。
- **丙**：其余全部。
  - 缔结关系、解除关系、离异、关系中止、关系恢复：内核关系写者在写边的事务里发；缔结、解除可以在固定刻发生（R18-5.1、R18-5.2）。
  - 分家、立嗣、遗产分配、监护变更、传承解锁：kin 发。
  - 谎言揭穿：经推断矛盾而来，R18-5.7。
  - 群体行为：固定刻的阈值触发，R18-6.2。真正的聚众场面是事件类型实例，由其定义卷负责。
  - 名士列册与除名、授予荣誉、阶层变动提议、常住变化、持有变化。
- 社交互动用的是卷九动作目录的动词，由卷九自定，不在此列。

两个“通道”指卷五 `sense` 族中承载光、声的那两条。代号以卷五数据为准，本提案不新造代号；数据行里直接写代号。

丙类的人怎样得知：
- 当事各方总是经亲历通道得知（R22-2.2 末句）；
- 旁人经转述得知（R22-2.4）；
- 或者因为感知到了承载它的那个动作事件而得知（该动作的动词行由卷九定）。

### 谁读谁写

- 写：卷十八 §2.3 动词行表（数据）。
- 读：只有卷二十二 R22-2.2 读（卷二十四表 B :169–170；C24-9）。
- 乙类的源强与判定沿用承载动作的那一次 `perceive`：卷五规则 7（一次性源由执行器给出），R22-2.2 判定的是“该动作”。不需要新增机制。

### 不定会怎样

- 表 B 这两列的 onUnknown 是 `error`，“行上必写”，缺写即加载失败。现在 §2.3 :184“按 onUnknown 取默认”的说法与表 B 不符（只核报告第三节第 2 条）。
- 如果一律取假：斗殴、婚礼没有旁观的亲历者，卷八b 的目击证据、舆论的知情率都会缺入口。
- 如果一律取真：固定刻里“好感越线成了朋友”这种事，同一地点能看见的人都会“亲眼看到”，凭空多出知情。

### 同类先例

- 卷二十三 :201：彩头结算、押注赢、押注输都是在当场较艺的事务里落定的名分或账目改变，取 `perceivable` 真、`senses` {视}，与本提案乙类同理。
- 卷二十四 :991：告示事件 `commissionPosted` 取 `perceivable` 真，属于当场行为。
- 卷二十二 R22-2.2：当事各方恒经亲历通道得知，所以丙类取假不会让当事人不知情。
- 本提案按类给值，而卷二十三是逐行定的。这是按李白 11-14“按动词类别统一给”的裁定而作的改变。判据只看发出点与载荷结构，以后别卷登记动词时可以照用。

## 五、`lieId`、`subjectRef` 的类型

### 5.1 `lieId`

**要什么**：`lieId` 的类型就是 `EventId`，取值是登记这条谎言的那次说谎动作落定时的事件 id。

- 同一句谎话后来再对别人说，`toldTo` 增加，id 不变。卷九 R9-13.9 决定卡所带的“登记的谎言 id”，指的就是这个已有的 id。
- 新说一句谎话时，lies.mjs 在该动作落定的同一事务里登记，id 取该事件的 id（R18-5.6“说谎即在谎言账登记一条”）。
- 谎言揭穿的 `payloadShape` 为 `{lie: EventId}`。
- 事件 id 按卷二十七 R27-8.9 确定性派生，所以可以复演。

**谁读谁写**：
- 写：lies.mjs（`state.lies[EventId]`，:322）。
- 读：卷九 R9-13.9、卷二十二（谎言引用 id，R18-5.7）、立场与威望来源行（引用谎言 id）。

**不定会怎样**：
- 谎言揭穿的 `payloadShape` 是 error，缺写即加载失败。
- `state.lies` 的键没有类型，pathTypes 生成不了。

**同类先例**：
- 卷二十二 :169，`factKey = (kind, eventId)` 以事件 id 作键。
- 卷二十四 :155，运行实例 id、委托 id 都从起始事件 id 得来。
- 同一张动词表里，成婚的 `consentAct: EventId`（:189）。

本项不新造类型，**不需要李白选**。

### 5.2 `subjectRef`

**要什么**：`subjectRef` 是“一个实体或一个事件”（§4.6.1 :856）。卷二 §1.5 规定，两种都是字串形态，不能放进同一个 `anyOf`，而事件 id 又没有登记前缀，用 `refs` 也区分不开。所以必须改成对象形态。

**谁读谁写**：
- 写：opinion.mjs（`state.opinion.lastFired[groupId][subjectRef][triggerRow]`，:323）。
- 读：`opinionOf` 的签名（:298）、卷二十二 `publicShare` 的签名（卷二十二 :256）、卷八民心与治理。

**不定会怎样**：
- 群体行为的 `payloadShape` 不完整，加载失败。
- 冷却键、入口形参没有类型，pathTypes 生成和 tsc 品牌检查都过不了。

**同类先例**：
- 卷二 §1.5 判别联合 `oneOf` 加 `discriminator`，例如 `struct:rxTree`。
- 别卷新增命名 struct 回填卷二 §1.5 命名表，例如 `struct:fixtureLot`（卷十，封卷后勘误）。
- 卷二十二 `factKey` 就是“事件式或命题式两种形态”的元组键，并用作状态路径的键（卷二十二 :169）。
- 谎言账的 `claim{event: EventId nullable, subject: EntityId}`（:807），是用两个分开的字段表达实体与事件。

### 待李白选 5（`subjectRef` 采用哪种形态）

- **乙（推荐）**：在卷二 §1.5 命名 struct 表登记一行 `struct:subjectRef`，定义为判别联合 `{"oneOf":[{on, entity: EntityId}, {on, event: EventId}], "discriminator":"on"}`。`on` 的两个字面值取一个新封闭枚举的两个带前缀代号，枚举由卷十八登记。
  - 好处：一个类型同时用于载荷、冷却键和两个入口的形参，卷二十二 `publicShare` 也可以直接引用。
  - 群体行为载荷写成 `{group, axis, pressure, subject: struct:subjectRef}`。对象是实体时，同时写进公共载荷字段 `payload.related`。表 B 规定 `related` 映射到 related 角色，这样卷二十二按 `mentions` 检索时能找到这件事。
  - 代价：卷二要做一笔封卷后勘误（新增命名 struct 一行，属于“登记”，不是扩充 14 种类型）。
- **甲**：不立命名 struct，在每一处都写成两个可空字段 `subjectEntity: EntityId nullable`、`subjectEvent: EventId nullable`，要求恰好一个非空，写法照谎言账 `claim` 的先例。
  - 代价一：冷却键要改成两层可空段，`opinionOf` 与 `publicShare` 的签名各要两个形参。
  - 代价二：“恰好一个非空”要另加一条加载与写入校验。
