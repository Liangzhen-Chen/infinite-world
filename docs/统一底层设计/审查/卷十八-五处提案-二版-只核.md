# 卷十八 五处提案 第二版 只核

- 被核：`审查/卷十八-五处提案.md` 第二版（提交 6ae3789b）
- 依据：`审查/卷十八-五处提案-只核.md` 真问题 1–5；`收尾待办.md` :384–388（李白 11-14 裁定：整类不特例、按类统一、读数值维度或固定代号、复用不新造、只答五处）
- 只核者：claude-opus-5-5 中档。只读；本文件是唯一写入。

## 结论：不通过

原五条里 3、4（`subjectRef`、牵连主体）改到位，1 基本到位。第三处有三处归类错误，其中成婚取不可感知不合现实，病根在成婚的发出路径没有登记“当面成礼”，不在判据。第二版因此说“已无待李白选项”不属实。

## 真问题

1. **第三处：传承解锁归错类。** 卷十八 :695 写明“传承解锁是动作”，R18-3.4 是“首领以名望解锁”。提案表里写“现行条文没有把它写成动作”，与原文不符。按提案自己的判据，应归动作类，取真。
2. **第三处：名士列册与除名漏列一个动作发出点。** R18-7.5（:920）规定“有人举荐（举荐是动作）时，写入待审的名士边”；`notable_phase` 有 pending 值（:1463），所以待审这一相位是在举荐动作的事务里写入的。提案只列了到期项、丑闻、固定刻三种触发。按提案自己的“多个发出点只要有一个是动作就取真”，这一行应取真，或者要写明为什么待审相位不发事件。
3. **第三处：成婚不可感知，结果不现实，病根是发出路径缺一条规律。**
   - 判据本身可以接受。它在设计时按发出规则分类，运行时程序只读 `perceivable`、`senses` 两个数据格，不读文字。“人看得见的是动作，看不见的是记账”作为规律也说得通。
   - 但套到成婚上，结果是婚礼现场的宾客都不会经亲历得知这桩婚事（R22-2.2 只让当事双方亲历），全村只能靠转述知道。现实中成婚通常是公开当面的事，这个结果违背北极星。
   - 病根：R18-2.3（:646）把成婚写成“婚约合同履行时”的连带写入。卷六的履行可以由 `settleObligations` 按到期调度自动完成（卷六 :979）。婚约种类行也没有登记任何需要在场的义务（卷十八查不到 `obl_` 或成婚义务，卷六 :134、:980 的 `needsPresence` 没有用上）。所以错的不是判据，而是成婚的发出路径没有登记“当面成礼”这一步。
   - 两种修法都超出五处：（甲）婚约种类行登记一条 `needsPresence` 为真的成礼义务；判据补一句“在 `needsPresence` 为真的义务履行事务里落定的，与动作同类”。这一句只读已登记的布尔值，属于整类规则。（乙）把成婚改成卷九动作目录里带同意条款的一个动作。两种都要改 R18-2.3 或卷六、卷九的登记，**须报李白选**。
4. **第一处：成组求值时，部分边为假怎样处理没写。** “一笔事务的全部新边一并求值，为假即拒写”有两种读法：一是任一条为假就整批拒写；二是只拒为假的那条。按第二种读法，拒掉一条会让 `wielders` 变小，其余各条的占手数随之变大，结果取决于先拒哪条，不确定。要补一句，例如“任一条为假，本事务全部新边一并拒写，报 E-HK-HOLD-WHILE”。四人合握时有一人只剩一只手、整批举不起来，这也符合现实。
5. **第二处：`functional` 整类判据仍要写进含义栏，与现有数据行矛盾。** 上一版只核已指出，“持续行动”判据除了看管、操控两行，还与 `hk_mentor_of`（:516，`grants: schedule`，取假）矛盾，建议删去。第二版没删，前后还不一致：§二写的是“写进 §4.1.1 含义栏”，牵连清单写的是“（可选）”。把一条有三行反例的判据写进定义栏，等于定下一条错误口径。应删去这一句，两格只凭同类先例取真（两格的结论没有问题）。

## 逐条核（对照上一版 5 条）

### 1. 合握起手：基本到位，剩真问题 4

- 合握起手已解决：一笔事务成组写入、一并求值。验算：四人握 `hands` 8，每人 ⌈8÷4⌉ = 2 ≤ 2，写入；一人单握 8 > 2，拒写，符合“一人举不起”；第五人后加入，⌈8÷5⌉ = 2，写入。
- 与 R18-1.12 原有两句不冲突：
  - “写入后求值”改成了“按本事务全部写入完成后的状态求值”，这是它的推广。
  - 逐条放回只用于重算现役边。例二（4 人降到 3 人，三人边依次关闭）是单调的：人数只减不增，每人占手数只增不减，所以只会连锁关闭，不会来回反复，结果确定。
- 手数有序表 `first(rules.combat.grip.handsRows)`、未命中时按 `allowExplicit` 显式写值并附 basis（卷二 :224 有此写法）：合规。`when` 只读组件代号集合与数值维度，规则文字不点名组件。
- 盾和投射器可以手持：撤回了第一版“没有 `weaponClass` 不能手持”的说法，与 R13-5.2（:713）的“一手兵器一手盾”、R13-10.6（:903）一致。
- 小项：
  - 卷九目前没有“握持”动作行。卷十三 :708 只写了“拿起与放下是持有边的开与关”。牵连清单写的是“握持动作带 `multi` 槽位”，应改为“新登一条握持动作行（数据）”，并写明由哪一卷登记。
  - A13-5.2 不变量式（卷十三 :734）写的是“所占 `hands` 之和”，要改成占手数之和，牵连清单没有这一项。

### 2. 感知判据：见真问题 1–3

- 判据在设计时按发出规则分类，运行时只读两个数据格：合乎“禁读自然语言”。
- 但“发出规则的触发方式”不是已登记的固定代号字段，是由人读条文判断的，所以才会出现真问题 1、2 那样的误读。
- 成婚的问题属于发出路径登记缺规律，不是判据错，理由见真问题 3。

### 3. `subjectRef`：到位

- 只用了 `EntityId`、`EventId`，没有新造类型，也没有新的封闭枚举。
- 空值写法 `nullable`，规定“恰好一个非空”，由唯一写者在构造时保证，并加一条验收断言。可空的 `EntityId` 载荷字段已有先例：R18-1.11 的 `prevHolder: EntityId nullable`（:479）。
- 冷却键拆成 `byEntity`、`byEvent` 两个容器，各自在去留表登记，没有新类型。
- 小项：`claim` 先例（:807）的 `subject` 是必填的，并不是“恰好一个非空”的写法；以 R18-1.11 作为先例更准确。

### 4. 牵连清单：主体已补齐

- 上一版缺的两项都已补上：§2.4 变量表 :240，以及 R9-13.9 的先后顺序（新谎带命题，落定时取事件 id）。卷三乙 / 卷十三的物品行显式值也已列入。
- 还缺：A13-5.2（卷十三 :734）；握持动作行的登记方。按真问题 1–3 改正第三处后，归类表与 :184 的牵连也要随之更新。

### 5. 范围与待李白项：不属实

- 新增内容都由五处推出，没有超出五处：成组求值、`handsRows`、握持动作的 `multi` 槽位、R9-13.9 分成两种情形。唯一例外是真问题 5 那句含义栏判据。
- 但“现确无待李白选项”不属实：成婚的感知要改 R18-2.3 / 婚约种类行或卷九的登记，超出五处，须报李白，在甲、乙两种修法里选一种（见真问题 3）。
