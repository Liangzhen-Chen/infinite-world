# 卷一 审查 A（独立审查员 A）

审查对象：docs/统一底层设计/卷一-总纲与分层.md（750 行，已全文读完）。依据：PLAN 11-13 02:3x / 03:5x / 04:xx 各条规矩，调研 06a、06b、07。只做静态读取，未运行任何脚本。

## 总判：有条件通过

方向、条文骨架、与 07 教训的对应都成立，基线数与代码引用基本真实。但分层有几处内部矛盾，R-2 有一处与亮圳原话冲突的豁免，几条"机器可判"实际仍是口号。下列"必改"改完才可放行波 1。

## 一、七层职责与边界

清楚的部分：每层都有职责、数据形态、读写边界、禁止事项四项；第五层只留三类接口，第七层只读投影，这两点能落地。

必改（职责重叠或空档）：
1. **L-0 与 §2.3 自相矛盾。** L-0 写"每层只读下层，不读上层"，§2.3 却写入口层"读第一层数据与第六层状态"。第六层在第二层之上。要么把运行时状态（存档）单列为一层或一个"状态存储"概念，放在第二层之下；要么改 L-0。
2. **运行时可变状态与内核事务没有层。** §2.2 说运行期无人写第一层，§2.7 说事件由内核归约时写。但状态对象（npcs.*、settlements.* 等）、内核事务（planPrimitives / commitPrimitives）、调度器都不属于七层中的任何一层。"写只有一条路"的执行者没有落点。
3. **第二层与第三层重叠。** §2.3 说入口层"不含规则"，却让 view() 返回"派生字段"、定义 canAct / capacity 等状态谓词；§2.4 又把"派生"列为第三层规则形状，且 derived() 修正槽（I27）也算规则骨架。派生值到底算在第二层还是第三层，没有判据。
4. **第一层与第四层重叠。** §2.2 说维度表在第一层统一定义，§2.5 说"每个领域有自己的维度表"。需写明：表的 schema 与校验归第一层、表的内容归领域卷，否则两处都能声称拥有。
5. **第四层几乎没有独立职责。** 它被写成"第三层规则按领域分组"，只是组织方式。请说明它与第三层的差别（领域独有的 view、领域内状态机？），否则七层实际是六层加一个目录。
6. **第六层的"叙事调度"与第三层时钟规则重叠。** §2.7 自己写"叙事调度是时钟规则的一种"，那它属于第三层，第六层只剩事件与投影。
7. **第五层"只有三类"与跨领域读并存。** §2.5 允许"读别的领域只经其 view()"，这是第四种跨领域通道（读），§2.6 没有列。另外 registerAdvanceHook（31 处）的相对次序也是跨领域依赖，三类接口没有覆盖。需明确"读"的合法通道，并说明推进次序由谁声明。
8. **输入端没有层位。** R1 理解层被写成"第七层之外的输入边"、R4 在"第一层之外的作者边"。图里没有，但 R-2 的两端论依赖它们。要在总图里画出输入边与作者边。
9. 条文编号：L-2、L-5 在 §0.4 引用、在末尾索引列出，但 §2 正文没有给出 L-n 标号；L-1、L-3、L-4、L-6 全无定义；L-7 只在 §6.2 表内一笔带过。各卷"只引用编号"的前提不成立，必须补齐。

## 二、硬规矩是否可机器判定、基线是否引自 06a/06b

基线核对：198 处 / 38 文件、294 / 89、difficulty 26、直接 import 11、server-plugin 219、tools 333、中文枚举约 1,100，均与 06a、06b 一致。引用无误。

必改：
1. **R-2 与亮圳 03:5x 第 1 条冲突。** 亮圳原话："现有所有文字匹配……一律列入写死清单，必须改掉"。R-2 判定段却允许 06b 待定 1 的 74 行（输入 / 叙述解析，位于 action-router、action-constructor 等）继续存在，只核对"输出结构化"。而 06b 表明这 74 行包含在 219 内，V-2 终值写"server-plugin 0"，与该豁免自相矛盾。默认 T0 不开 AI 时，玩家自由文字是谁解析的？若是这批正则，那就是"规则式理解层"，必须明说、单独设档、报李白确认，不能夹在判定里放过。
2. **V-2 基线口径不全。** 219 / 26 / 333 不含约 1,100 行中文枚举（06b 说"未逐条分"）和 I35"中文字面量 = 0"。V-2 标题含"中文字面量"，基线却没有这一栏。tools 的 333 也"未逐行判读"。基线必须先有逐行清单才能"只降不升"。
3. **R-2 被禁字段表是"包括但不限于"**，机器没法判。应改成"显示字清单（卷二）以外的字段不得被匹配"的白名单式。而 §4.4 的显示字清单（name、description、labels、prose、flavor、voice）与 R-2 的被禁字段、I34 清单（含 purpose、activity）三处不一致，`purpose` 在 §4.4 不在清单内。
4. **扫描算法没有给定义。** 正则扫 `item_|loc_…` 会误报合法数据引用，也抓不到"拼接生成 id"、"换成常量文件再引用"、"名字首字判断"（A-1 自己举的例子）。纯正则扫描是 A-20 型"按测试打补丁"的最容易绕过口。至少要在卷一写明扫描必须基于语法树，并且常量文件、字符串拼接、动态键算入。
5. **R-6"白名单：0、1、单位换算"含糊。** 数组下标、毫秒、分钟换算算不算？白名单推给卷二，卷一没有给出形式。
6. **R-8 判定无法机器化**（"不出现版本分叉"如何查）。R-1 判定依赖尚未存在的卷零覆盖率，现在无法判定。
7. **§6.3 基线元组与 V-3 不一致。** 元组写 (22+52+8+22)，V-3 另含 records 89 模块、npcs.* 未声明写；06a 中 npcs 55 模块 196 写点、records 311 写点没有基线数。
8. **"规则可读状态哈希"（V-4、I40、§8.3）没有定义字段集合。** 没有明文列出哪些字段进哈希，哈希相同的断言没法落地。

## 六、特例、写死、语言依赖漏网

1. **人名 / 地名生成与语言。** 卷一说命名库数据化（§5.2），但没有说生成出的名字是一个字符串（单语言）还是 labels 的键。若 `name` 在生成时按中文规则（姓、首字、"城|港"后缀）定下，en 包无法渲染，I40 的哈希一致也被破坏（名字若进状态）。需规定：生成物的名字是"名字成分代号 + 各语言拼法规则"，而不是成品字符串。
2. **`name` 与 `labels.zh/en` 的主从关系没定**：§2.2 同一实例同时有 `name`、`labels`，哪个是权威？
3. §2.8 把语言包写成 `labels.zh` / `labels.en` 字段名，三语以上要改结构；建议写成"按语言码索引"，不在条文里固化两种语言。
4. A-18（修正键开放集合）与 I18（词汇封闭）、primitives 19 个封闭，三处并存，卷一没说清楚"哪些封闭、哪些开放"的分界。
5. 不是规则漏洞但需核对：G1 写"纳入 167 + 已有 41"，合计 208，与总表 223 行差 15，卷一没交代这 15 行的去向（应在 10 号文档核对）。
