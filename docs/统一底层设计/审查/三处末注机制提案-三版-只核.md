**整刻作废与几处先例相容的核实（①）**
- **卷二十 §4.1.4、卷二:801**：格局变化信号要等事务提交后才转给调度器，调度器在 t 结束当前计划段，然后续排。整刻作废时，这份新计划和 `simProgress` 的初值也随 state 一起回退。本次推进到此结束，留在内存里的计划不再使用。下次推进开始时按"请求起点为 `before`"回调（卷二:801 的第一种时机），t 重做时同一个提案再发一次信号，在 t 再对时一次。所以结果与一气推完相同。
- **A27-1.10 / A27-1.9 / R27-1.11**：时钟停在 t 前面那个已处理完的刻，相当于在那里多切了一刀。这几条本来就要求任意切点结果都一样（卷二十七:323–324、:290），A27-1.10 的 ①②③ 不受影响。
- **卷二十 §4.1.3 第 2 条**：时钟回退到 t_prev 以后，`next = min(…)` 取到的仍是 t（理由是钩子节拍对齐绝对分钟，第 3 条），所以重做时一项不漏。
- **范围**：没有超出所请。二版给了"登记 struct"和"改存已有类型的游标"两条路。三版走的是第三条：只用 `state.clock.minute` 和整刻回退，不存游标。这是在给第一处的甲案作答，没有新增字段、类型、代号。但"刻级回退点"是一个新的内核能力，它的落点和牵连见一-T1。

## 二、真问题

### 一-T1（第一处·甲）"整刻作废"跟卷二十七的快照与输入序列对不上，牵连只写了"只核对、预计无需改字"
1. **快照和封段可能落在一刻中间**。卷二十七 R27-4.5（:485）规定"每 `snapshotEveryEvents` 条事件做一次快照"、"每 `segmentEvents` 条封成一段"，按事件条数来，不看刻的边界。所以一刻之内、某笔事务提交之后，就可能拍下快照或封好一段；等后面的项被拒、整刻作废时，那份快照里已经有了被作废的结果。甲案第 52 行"state 只会停在某刻已全部处理完的边界上，不会出现一刻做了一半的存档"，靠的就是"快照不会落在刻中间"，可是现有条款不保证这一点。要么在 R27-4.5 写明"快照与封段只在一刻全部处理完时做（满数后顺延到刻末）"，要么写明一刻的事件先暂存、刻末再并入日志。卷二十七这一行要从"只核对"改成"要改字"。
2. **被拒的请求怎样留在输入序列里，没有写**。R27-7.3（:638）说输入序列就是 `doc_log` 里的玩家指令与推进请求条目，`doc_log` 在 state 里。第一处 ① 是"整笔回滚、状态不变"，甲案是"state 回到 t 之前"。两种回退都没有写清楚：请求条目是在回退范围之外先记下的（比如受理请求时单独提交一笔），还是随回退一起消失。第一处第 4 点、甲案第 52 行"被拒的请求按请求编号留在输入序列里，复演时同样被拒"的正确性都靠这一点，应当在第 0 点或甲案写明条目在哪一步记下，并把卷二十七 R27-7.3 列进牵连。
3. **刻级回退点没有主人，卷二的"事务提交"含义也随之改变**。甲案第 53 行要求"kernel 能把一刻的结果作为一个单位丢弃"，但没有说由哪个文件持有回退点：`kernel/scheduler.mjs` 是 `clock.*` 的唯一写者、负责处理每一刻；`kernel/transaction.mjs` 负责事务。这一点应写明。另外，选甲以后，一刻之内已经"提交"的事务在刻末之前都还可能被作废。卷二几处"事务提交后"的动作要说明自己在被作废时怎么办：:844 的 `layout_change` 转交（见上文，随计划丢弃即可）、:805 心跳推进"事件序号区间由 kernel 记下"（要截掉被作废的那段）。这几处应补进卷二的牵连行，不能只写"不新增字段"。
