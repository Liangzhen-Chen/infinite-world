## 二、真问题

**1. `EventId` 没有合法产生者（强转豁免文件表与 §2.8 第 1 条构造函数清单均缺）。**
新条 :197 说"只由 kernel 产生同 §2.8 第 1、2 条"；§2.8 第 2 条规定 kernel 组内强转只许出现在 §2.9 第 2 条强转豁免文件表（:959–977）所列文件，且"kernel 组内其余文件要品牌值，一律调用 `kernel/handles/*` 的构造函数"（:981）。现表中没有任何一行产出 `EventId`，§2.8 第 1 条"只能由内核构造函数产生（…）"的构造函数列举也无 EventId 的构造函数。按现文，`kernel/events.mjs#emit`（:541、:855）给事件定 id 时的 `string → EventId` 强转即 E-TSC-ESCAPE-ASSERT——品牌无合法产生者，自相矛盾。改稿者已在 审查/EventId-全书用处.md 第三节自报未处理。
改法（只改列出项）：
- 强转豁免文件表加一行，按本卷既有惯例落在 `kernel/handles/*`，不落 `events.mjs`：建议并入 `kernel/handles/keys.mjs` 行（"`string` → … 、`EventId`"，不新增文件，免改 `kernel/files.json`），"强转前必须做的事"写"值是 §1.10 派生函数由 R27-8.9 五样成分算出的结果，不收外来串"；或新增 `kernel/handles/event-id.mjs` 一行（须同步 `kernel/files.json` 与 §6.11）。`kernel/events.mjs#emit` 调该构造函数取 id，自己不强转。读档时存档里的 EventId 经 `narrow`（`unknown → SchemaOut<S>`）回来，已有行覆盖，不另加。
- §2.8 第 1 条构造函数括号里补该构造函数名（如 `kernel.eventId(…)`）。
- 附录 D 本行"改了哪里"补这两处。

**2. `pathTypes` 值类型文法（§2.7 :665，唯一的封闭文法）未加 `EventId`。**
新条 :197 写"`pathTypes` 值写 `EventId`"，但 :665 的文法是封闭列举（`number:<单位> / integer:<单位> / boolean / ref:<kind> / enum:<族> / dimension / struct:<名> / sealed`），没有 `EventId`；且 `ref:<kind>` 按新条又不得承载 EventId。两处冲突，按 :665 加载器会拒 `EventId` 路径；卷二十七 :502/:506/:536/:996（R27-4.12 ② 按 pathTypes 认 EventId 路径）与卷十八 :327、:328 的映射键都依赖这一条。用处清单第一节称"本批已在卷二写明"，只写在 §1.5，定义处未改。
改法：:665 文法列举加 `/ EventId（§1.5）`；附录 D 本行补"§2.7 pathTypes 文法"。

## 三、小项（不阻断，随上两条同改即可）

- **14 种计数口径措辞**：:191 "共 14 种类型 … 全文以此为准"，新条称 EventId 是"本节封闭集合的成员"又"不计入 14 种"。取 14 不变是对的（L1 E-DIM-SCHEMA-TYPE 只认维度值类型，EventId 不能作维度类型），但两句读起来像封闭集合 15 个而计数写 14。建议 :191 改为"共 **14 种**维度值类型（…），全文以此为准；另登记代号类品牌 `EventId` 一种（下条），不作维度值类型"——锚点"共 **14 种**"保持，脚本第 3 项不受影响（须复跑确认）。
- **"数据行"一词**：:194 "状态、事件载荷与数据行里凡指向某一条事件的字段 … 类型一律写 `EventId`"。EventId 不是维度值类型，维度表数据行的字段写不了它；"数据行"宜删或改为"状态记录"。
- 用处清单把卷二十三 :150（`ref: EntityId 或 EventId 或身份键`，由同级 `kind` 判别）判"一致"偏宽：新条认可的是"带判别字段的 struct"（即 §1.5 `oneOf` 判别联合，成员各是 struct），而此处是单个字段随同级 enum 变类型，不是该写法。建议移入第二节作第 8 条，交下一批。
