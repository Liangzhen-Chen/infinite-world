## §1 领域总述

### 1.1 真实世界怎样运转

1. **世界不因没人看而停。** 远处的庄稼照样成熟，远处的人照样生老病死、欠债还钱。观察者不在场，改变的只是他知道多少，不是事情发不发生。
2. **远处的事只以总量为人所知。** 一个人对邻村知道张三李四，对邻省只知道“今年歉收、人口约几万”。总量由个体加总得到，不是另一套规律。所以粗算必须是细算的加总，两者不许各走各的规律。
3. **守恒不分远近。** 钱、粮、人不会因为离得远就凭空多出或消失。
4. **同因同果，但结果是分布。** 同样的起点、同样的偶然，结局相同；换一组偶然，结局在一个合理范围内散开。个别不合常理的结果可以有，整体分布不许偏。
5. **记录是发生过的事的账。** 一本只往后写、不涂改的流水账，加上隔一段时间盘一次的存量，就能回到任何一次盘点之后的任何时刻。

### 1.3 进程归属

本卷按卷二 §2.9 第 0 条的两进程建模写（第十六版），本卷只引用：

- **Node 服务端进程**：权威状态、推进、聚合、成本判定、存档读写、复演，全部在这里（kernel 组与规则层）。
- **浏览器扩展进程**：只有 display 组与 host 组文件（卷二 §2.7）；不持有权威数据（卷一 L-9）；不向规则层提供时钟、随机数或任何熵；跨进程只经卷二 §2.9 第 0 条的通道与回应通道传代号结构和已筛查文字，两侧的进程边界文件见第 1 条入口表与出口表。存档的导出、导入两路也只经第 0 条“存档四路”的 `save_export`、`save_import` 路由：客户端只原样收发存档字节，不解析。
- 由此得出本卷三条约束：① 扩展重载或断线后只重取投影，服务端状态与存档摘要不变；② 性能预算分两段记账，本卷只管服务端一段（§4.6）；③ 同一条玩家指令重复送达不得结算两次（§8 开放问题 1）。

### 3.2 唯一写者

- `simProgress.*` 与 `simDegrade.*`：`sim-advance.mjs`。`aggregates.*`：`aggregate.mjs`。两者都只产提案，经第〇层事务归约（卷一 L-2）。
- 存档写盘：只有卷二 §2.9 出口表登记的内核存档出口；读档：只有登记的内核读档入口。存档、读档、导出、导入四路按卷二 §2.9 第 0 条“存档四路”：写盘与导出在 `kernel/save.mjs`，读档与导入在 `kernel/load/save.mjs`，结果经回应通道回到玩家。分片规划与清单生成是这两个文件内部的步骤，不另开文件边界。
- 基准与复演工具：归 tools 与 tests 组，不在运行时，不写存档目录之外的任何权威数据。

### 3.3 退役的旧入口

`advanceLayerPlan`、`remoteScheduleBatch` 里的层判定与钉住判定（advance-layers.mjs:9–68）由 3.1 的入口取代；存储层的状态整份写盘路径由 §4.4 取代；legacy、compat、migrations 三个目录，world-upgrade、rule-state-migration 两个文件，四个领域迁移文件和读档格式迁移入口整体退役（§7）。

## §4 子系统

### 4.1 三层模拟运行矩阵

#### 4.1.1 维度

`unitAdminLevel`、`individualMaxHops`、`ruleMaxHops`、`ruleSharedAncestorLevel`、`globalUnitTier`、`cadenceMinutes`、`matrix`、`observables`、`driftTolerance`、`driftToleranceDefault`、`driftStat`、`seedSampleSize`；状态 `simProgress.<unit>.through`。

#### 4.1.2 统一入口

`simUnitOf`、`baseTierOf`、`simTierOf`、`advancePlan`；写者 `sim-advance.mjs`。

#### 4.1.3 规则

- **R27-1.1 模拟单元**：每个主体属于恰一个模拟单元（`simUnitOf`）。
  - 有地点的主体取其地点的单元。地点的单元 = 包含树上第一个行政层级等于 `unitAdminLevel` 的祖先。
  - 没有这样的祖先时（荒野、海域、秘境这类不属于该级政区的地点），不取根：从该地点向上走，停在第一个行政层级高于 `unitAdminLevel` 的祖先或根之前，取停下之前的最后一个节点作单元（它可以是地点自身）。所以互不相连的无政区区域各是各的单元，不会并成一个。
  - 没有地点的主体（组织、信仰、神祇、账户一类）归**全局单元**。全局单元不参与跳数计算，它的层固定取 `globalUnitTier`，不随观察锚变。
  - 单元邻接只读卷五 §4.14 规则 2 的 `placeView().neighbors`（两个单元相邻，当且仅当存在一条边连接两者的后代），本卷不自定义，也不再读手写的邻接清单。该判据对无政区单元同样有定义；请卷五确认同一入口对它们给出结果（§8 第 11 条）。
- **R27-1.2 观察锚**：观察锚 = 状态里登记为玩家控制的实体所在的单元集合，经该登记的定义卷提供的 view 读取。它与输入边无关：输入边整体拔除、只用菜单时（卷一 §2.10），锚照样存在；复演时也能从状态得到。锚可以有多个；状态里没有玩家控制的实体时（无人值守）锚为空集。
- **R27-1.3 层的判定分两步**：
  - **基础层**（`baseTierOf`，纯函数，只读拓扑、观察锚与规则表）：设 h = 单元到最近观察锚的跳数，不连通或没有锚记为无穷大。h ≤ `individualMaxHops` 为个体层；否则 h ≤ `ruleMaxHops`，或 `ruleSharedAncestorLevel` 非空且与某个锚在该级有共同祖先，为规则层；其余为统计层。
  - **有效层**（`simTierOf`）：同一判定，但两个半径与共同祖先条件取“表值按状态里的 `simDegrade.level` 套用降级阶梯之后”的值（R27-3.4）。锚所在单元恒为个体层，降级不得改变这一点。
  - 钉住（R27-2.4）、折叠（R27-2.5）、推进计划、层序值、他卷读层，读的都是有效层。基础层只用于解释和断言 A27-1.2。
- **R27-1.4 层不落盘**：有效层随时由 R27-1.3 从状态算出，不写进状态，也不写到任何实体身上。落盘的只有每个单元的 `through` 和全局的 `simDegrade`。因为档位在状态里，读档或复演时任何时刻的有效层都能原样重算。
  - **`through` 的初值**（封卷后勘误，李白 11-14 事件 94cd4688）：单元第一次出现在推进计划里时，由唯一写者 `sim-advance.mjs` 在同一事务里把 `simProgress.<unit>.through` 初始化为这次回调的 `before` 向上对齐到该单元所在层（这一项的 `stepMinutes`）的下一个整拍边界（R27-1.6 的边界；`before` 恰在边界上时取 `before` 本身），之后照常推进；首个整拍边界之前的那段不结算、以后也不补算（李白 11-14 选甲，守住 R27-1.6 末句：首桶与推进怎样切分无关）。这次回调就是新单元出现触发的那次对时（R27-1.10），所以 `before` 即新单元的出现时刻，初值 = 出现时刻之后的下一个整拍边界（出现时刻恰在整拍边界上时取该边界），与推进请求怎样切分无关（封卷后勘误，李白 11-14）。创世时就有的单元第一次推进的 `before` 即创世时刻，同样对齐。不另设创建时刻字段。
- **R27-1.5 运行矩阵**：每个系统对每一层声明一个形态。
  - `simform_individual`：逐实体行、按到期项结算。只在个体层合法（个体层单元的聚合成员全部实体化，R27-2.6）。
  - `simform_batch`：逐主体行、按该层节拍结算。主体可以是实体，也可以是地点、地块、设施这类非人口主体。该单元里的聚合体不实体化，按同一系统的统计形态规则结算。
  - `simform_stat`：逐聚合体或逐单元、按该层节拍结算，只读写人数、聚合账户与聚合维度。
  - `simform_derived`：该系统在该层的量是时刻的纯函数，由（种子、单元、时刻）算出，不结算、不留状态（例如卷二十的天气）。它三层相同。
  - `simform_frozen`：不随时间变，只由事件行改动；仅当该系统在该层没有登记任何时钟形状的规则时合法。
  - 校验：形态与该系统登记的规则不相容即 E-SIM-FORM-INVALID；主体类出现在聚合种类表里的系统，在规则层与统计层必须有统计形态的规则；新系统不声明矩阵行即加载失败。卷二十 §5.3 各行所用的说法与本族的对应见 §5。
- **R27-1.6 节拍桶对齐**：粗形态（批量、统计）的结算区间永不跨越绝对时间的整拍边界，桶号 = 时刻整除节拍（卷二十 §4.1 的钩子若带相位偏移，边界相应平移，仍是绝对时间的函数）。
  - 平常的一次推进只结算**完整的桶**：区间 [`through`, 下一个整拍边界) 走完才结算，`through` 只停在边界上。推进请求的终点落在桶中间时，这半个桶不结算，留给以后的推进。
  - 规则按传入的区间时长 `spanMinutes` 结算；完整的桶时长等于节拍。只有换层时才会出现不满一拍的区间（R27-1.7）。
  - 因此“在哪里停下、分几次走”不影响任何一个桶的结算内容。
- **R27-1.7 换层协议**：单元的有效层发生变化有两个来源，处理不同。
  - **观察锚变动引起**（可以发生在任何时刻 t）：① 追赶在改锚的提案之前、在同一事务内执行，读的是改锚之前的状态，“原来的形态”就是用改锚前的锚和状态里的档位算出的有效层所对应的形态；② 由粗变细：先按原来的粗形态结算完整的桶到 t 之前最后一个整拍边界，再对零头区间 [该边界, t) 按原来的粗形态结算一次，`spanMinutes` 取零头长度，然后 `through` = t，再实体化并请求站点物化（R27-2.6；封卷后勘误，卷十 C10-8）、换细形态；③ 由细变粗：单元按细形态已算到 t，`through` = t，折叠（R27-2.5），之后粗形态的第一个区间是 [t, 下一个整拍边界)，`spanMinutes` 取这段长度，此后回到完整的桶；④ 零头区间内的抽取，键里的时刻取区间起点（R27-8.6）。这样 [整拍边界, t) 和 [t, 下一个整拍边界) 各恰好结算一次，既无缺口也无重叠。没人看的那段时间按粗形态算，这是既定事实，不回头重算。
  - **档位重评引起**：只发生在评档块边界（R27-3.3）。块长是最粗一层节拍的整数倍，所以这一刻所有单元都正好在整拍边界上，没有零头；先按旧档位把各单元结算到该边界，再写新档位，再折叠或实体化。
  - 锚变动是世界里发生的事（由玩家指令或规则的提案引起），评档边界是绝对时间，两者都与“这一次推进请求从哪到哪”无关。
- **R27-1.8 钉住个体不随层变粗**：统计层或规则层单元里被钉住的个体（§4.2）仍按个体形态结算，结算时刻取自身最早到期项。
- **R27-1.9 层间一致性**：同一系统的粗形态必须是细形态的加总——守恒量逐笔守恒（经账本，卷六 §4.1）；`observables` 列出的可观测量按下面的办法比较：取 `seedSampleSize` 组世界种子，同一单元分别强制按个体层与统计层推进同样时长，各得一组样本；按 `driftStat` 指定的统计量算两组样本之差（`ds_mean_ratio`：两组均值之比减 1 的绝对值，以个体层一组的均值为分母；两组均值都为 0 时不做除法，漂移取 0；只有分母为 0 时不做除法，按超出容差判；`ds_ks`：两样本 KS 统计量），不得超过该维度的 `driftTolerance`。超出即判为“缺规律”，修在该系统的规则层，不许调容差掩盖（调容差须李白批）。
- **R27-1.10 推进计划怎样到调度器**：`advancePlan` 在规则层，调度器在内核，内核不 import 规则层，也不读规则表。通路照卷二 §2.9 第 0 条“推进计划与心跳推进”（唯一定义）：规则层经 kernelApi `registerAdvancePlan(provider)`（`kernel/advance-registry.mjs`）把 `advancePlan` 登记为推进计划 provider，`kernel/scheduler.mjs` 按卷二该条的回调时机回调它取计划；装配文件不调它。计划里每个单元带单元 id 与三个整数——层序值（`simtier` 的序值）、步长分钟、结算区间终点（字段见 §3.1；区间起点取该单元的 `through`，不在计划里）。**回调时机共四种**（封卷后勘误，李白 11-14；卷二 §2.9 第 0 条与此逐字相同）：推进请求开始时（以请求起点为 `before`）、每个评档块的边界、观察锚变动的事务结束后、新单元出现（卷二十七 R27-1.1 的格局变化）的事务结束后；后两种以该事务结束时的世界时刻为 `before`，都是世界里发生的事，与推进请求怎样切分无关。块内若有提案改变了观察锚，换层协议在该事务内完成；块内若有提案改变了拓扑、使 `simUnitOf` 多出一个新单元，也在该事务内。这两种事务由规则层发格局变化信号，调度器收到后结束当前计划段并再回调同一 provider；信号怎样交、"结束当前计划段"的定义一律照卷二 §2.9 第 0 条"格局变化信号""结束当前计划段"（唯一定义），内核自己不判层。所以新单元第一次进入推进计划的 `before` 恒为它的出现时刻。
- **R27-1.11 推进结果与推进路径无关**：从同一状态出发、其间的玩家指令相同，世界推进到同一时刻的结果只取决于状态与时刻，不取决于推进请求怎样切分、每次请求多长、请求属于哪一类、在哪一刻存过盘读过档。本卷为此立三条约束，任何后续修改不得破坏：① 档位只在绝对时间的评档块边界由状态算出并存入状态（R27-3.2、R27-3.3）；② 粗形态的结算区间只由整拍边界和换层时刻界定（R27-1.6、R27-1.7）；③ 折叠与实体化的时机只由整拍边界、换层时刻和规则的写入决定（R27-2.5、R27-2.6）。

#### 4.1.6 验收断言

- **A27-1.1（扫描式）**：S27-1 命中数为 0；规则层与内核中行政层级族条目的字面量为 0，层判定只经 `simTierOf` 与 `baseTierOf`；内核对规则层的 import 为 0。
- **A27-1.2（不变量式）**：对任意状态，`baseTierOf` 只依赖拓扑、观察锚与规则表——同一状态调用两次结果相同，改动任何非锚实体不改变任何单元的基础层。`simTierOf` 只比它多依赖 `simDegrade.level`——档位不变时，改动任何非锚实体不改变任何单元的有效层。
- **A27-1.3（验收测试，分段无关；交卷十二机器化）**：从同一存档出发、不夹玩家指令，把世界推进 N 分钟。分别取：一次推进 N 分钟；按任意切分分 k 次推进合计 N 分钟；每次换用不同的推进类别标签；中途在任意切点存盘再读档。各种走法结束时的**排除日志分区后的世界状态摘要两两相等**（定义见 R27-4.1；各走法的推进请求日志条数与类别标签本就不同，所以不比存档摘要）。测试取遍基准场景表的每一行，N 至少覆盖跨一个评档块边界、终点落在桶中间这两种情形。测试在不开文字模型的档位下跑；开着文字模型时改用卷一 V-13 的口径（事件流与 textPaths 之外的状态逐值相等）。
- **A27-1.4（不变量式，层间一致）**：R27-1.9 的基准对矩阵里每个声明了 `observables` 的系统都通过。
- **A27-1.5（扩展性式）**：新增一个系统，只加系统声明行与矩阵行，不改 `sim-tiers.mjs` 与 `sim-advance.mjs`，A27-1.2 至 A27-1.4 仍通过。
- **A27-1.6（扩展性式）**：换一张拓扑完全不同的世界（非西陲、含不连通区域与无政区地点），不改任何代码与规则表，A27-1.2、A27-1.3 通过；互不相连的两块无政区区域属于不同单元。
- **A27-1.7（不变量式，换层不缺不重）**：在任意时刻 t 让观察锚进入或离开一个单元，对该单元每个声明了粗形态的系统，结算区间首尾相接地覆盖全程——没有哪一分钟被结算两次或漏掉（按结算记录的区间核对）；由粗变细、由细变粗两个方向各测。
- **A27-1.8（验收测试，档位与请求无关；交卷十二机器化）**：`costPlan` 的签名里没有请求参数（扫描）；同一状态下发出长度不同、类别标签不同的推进请求，到达同一时刻后 `simDegrade` 两个字段相同；两次评档之间 `simDegrade` 不变。
- **A27-1.9（不变量式，新单元首桶与切分无关；封卷后勘误，李白 11-14 选甲）**：从同一存档出发、不夹玩家指令，其间有一个新单元出现（第一次出现在推进计划里），把世界推进到同一终点；分别一次推进到终点、按多种不同切分分多次推进到终点（切点含落在新单元出现时刻与其后首个整拍边界之间的情形）。各走法里该单元第一次出现时回调的 `before` 都是它的出现时刻（新单元出现即触发对时，R27-1.10），`through` 初值都相同（按 R27-1.4 对齐到同一个整拍边界）；该单元每个粗形态系统的结算记录（区间、`spanMinutes`、结算结果）逐条完全相同；首个整拍边界之前的分钟在任何走法里都没有结算记录。例：该层节拍 60 分钟、整拍边界在 0、60、120……分钟，新单元在 75 分出现，不切与切点在 90 两种走法首次回调的 `before` 都是 75，终点都是 200：两种走法初值都是 120，都只结算 [120, 180) 一桶，[180, 200) 不满一拍留待以后，结算结果完全一致；若新单元恰在 120 分出现，初值取 120 本身。
- **A27-1.10（不变量式，新单元对时与块切分无关的对照用例；封卷后勘误，李白 11-14）**：规则表取该层节拍 60 分钟、`chunkMinutes` = 240（评档块边界在 0、240……分钟），从同一存档出发、不夹玩家指令，块内有提案在第 75 分钟改变拓扑、使新单元出现，终点 200。走法：(a) 一次推进 0 → 200；(b) 0 → 70、70 → 200（切点在出现之前）；(c) 0 → 90、90 → 200（切点在出现时刻与其后首个整拍边界之间）；(d) 0 → 150、150 → 200（切点在首桶中间）。断言：① 四种走法里该单元第一次回调都发生在第 75 分钟、`before` = 75，没有哪种走法要等到块边界 240 或下一次请求开始才第一次回调；② `simProgress.<unit>.through` 初值都是 120（75 之后的下一个整拍边界），[75, 120) 在任何走法里都没有结算记录；③ 该单元每个粗形态系统的结算记录都只有 [120, 180) 一条，区间、`spanMinutes`（= 60）、结算结果逐项相同，终点时 `through` 都是 180，[180, 200) 都未结算。反例对照：若新单元出现不触发对时，(a) 中它要到 200 之后的请求才第一次进入计划（`before` ≥ 200，初值 ≥ 240），(c) 中在 90 进入（初值 120），[120, 240) 在一种走法里结算、在另一种走法里永不结算，本用例 ②③ 即失败。

### 4.2 聚合变体、等价、钉住

#### 4.2.1 维度

聚合种类表字段 `aggKind`、`subjectKind`、`keyDims`、`keyHoldings`、`pooledResources`、`shareRule`、`shareDist`；状态 `aggregates.<aggregate>.{kind, unit, key, members, nextOrdinal, aggNo}`、`aggregates.nextAggNo`；规则表 `keyIdAggBits`、`keyIdOrdinalBits`（封卷后勘误，李白 11-14 X5）。

#### 4.2.2 统一入口

`pinned`、`aggregateView`；写者 `aggregate.mjs`；三个动作 `fold`（折叠）、`materialize`（实体化）、`settleOut`（分户）都以一条事件加原语列表提交。足迹经内核的反向索引导出读取（向卷二 §2.7 kernelApi 登记，见 §5）。

#### 4.2.3 规则

- **R27-2.1 聚合变体是什么**：一个聚合体代表若干个“没有个人历史”的同类个体。它只存所在单元、分组键、成员区间和下一个序号；人数 = 成员区间长度之和，是派生量。
  - **聚合体 id**：由（聚合种类, 所在单元, 分组键取值）经卷二 §1.10 的派生函数确定性得出，在种子键登记表里登记为 `role_id` 的一行。同一组键永远得到同一个 id。
  - **聚合体一经建立不删除**：成员区间可以为空，`nextOrdinal` 保留。这样同一组键不会“删了重建”而把序号从头再发一遍，成员身份不会撞。
  - 每个聚合体有一个**自身来源键**，由聚合体 id 派生，用作在它名下出生的成员的 `origin`。
  - **聚合体整数号**（封卷后勘误，李白 11-14 X5）：聚合体建立时在同一事务里取 `aggregates.nextAggNo` 的值写入 `aggNo`，计数加一；同一事务建立多个时（如开局）按聚合体 id 的键序取号（内核按键排序遍历）。号只增不减、终身不改，聚合体又不删，所以号与聚合体一一对应、永存，只用于 R27-2.2 的本名键号。
- **R27-2.2 成员身份**：每个成员由（来源种子键, 序号）唯一标识，终身不变。个体的实例 id 由这一对按卷十的实例 id 导出规则确定性得到（卷十 R10-12.2：取来源聚合体与序号，迁移后不变；封卷后勘误，卷十 C10-8）；个体的各采样维度由卷二 §1.10 的采样函数从实例 id 算出，不落盘；出生时刻取所在成员区间的 `bornMinute`，为空时由采样得出；实体化时按分组键写入的维度（如卷二 §5.5 `culture`，聚合体成员实体化取分组键中的文化），由成员身份所属聚合体的分组键重算，现值与之相等的属基本行、不计入足迹（R27-2.3），不能由此重算的照常计入。分组键里经 `keyHoldings` 种类派生的维度（如卷二 §5.5 `faith` 经信奉边），实体化时在同一事务里按该维键值开该种持有边（键值为空则不开），边的条款（`terms`，如 `since`、`origin`）只由成员身份确定性重算；条款等于重算值的这类边与基本行同等对待、不计入足迹（R27-2.3），条款不同的边或多出来的边照常计入。所以同一个成员无论被实体化多少次，都是同一个 id、同一组属性。
  - **出生取得成员身份**：凡实体类出现在聚合种类表里的个体，不论在哪一层出生，出生时都从其分组键对应的聚合体（没有就建立）取 `nextOrdinal`，身份为（该聚合体的自身来源键, 序号），出生时刻记为 `bornMinute`。统计层的出生时刻取所在结算区间的起点。出生时的分组键：经 `concluded` 为真的 `keyHoldings` 种类派生的键维出生取空（新生儿无从同意），其余键维照母体；整类，只读卷十八 §4.1 持有种类表的 `concluded` 列，不点名种类（封卷后勘误，第0日生成内容提案定稿二 §9）。
  - **没有成员身份的个体**（世界数据里手写的、id 不由上述规则导出的）不可折叠，恒为钉住，原因代号 `pin_identity`。
  - **本名键号**（封卷后勘误，李白 11-14 X5；本条是全书本名键号取法的唯一定义处，卷四 K-1 引用）。必要理由：卷四 K-1 的本名键号须在折叠后再实体化时不变，否则别人知情里存的旧键（卷二十二 R22-1.5）再也解析不到此人；但成员身份是（来源聚合体, 序号）两个数，`nextOrdinal` 只增不减、卷十的序号也无上界，两个无界的数不能单射进有限位宽的键号（上限 `safeIntMax`），所以必须定位宽、定超界处置，不加就修不了。整类规则，对一切有成员身份的个体同样适用，不按物种、聚合种类分支。
    1. **两段**：记 P = `keyIdAggBits` + `keyIdOrdinalBits`（首值 20 + 31 = 51）。键号第 P 位是段标志：标志为 0 的是**置换段** [0, 2^P)，标志为 1 的是 **seq 段** [2^P, 2^(P+1))。两段不重叠；加载校验 P + 1 ≤ 53（E-KEYID-WIDTH），所以全部键号 ≤ 2^53 − 1 = `safeIntMax`。
    2. **置换段（本名键）**：有成员身份、且来源聚合体（自身来源键等于该成员 `origin` 的那个聚合体；它不删，R27-2.1）的 `aggNo` < 2^`keyIdAggBits`、序号 < 2^`keyIdOrdinalBits` 的个体，本名键号 = π(x)，x = `aggNo` × 2^`keyIdOrdinalBits` + 序号。π 是 P 位上的交替宽度 Feistel 置换：x 分为高 ⌊P/2⌋ 位 L 与低 P − ⌊P/2⌋ 位 R，**轮数写死为 8**，每轮 (L, R) ← (R, L XOR (F_r(R) mod 2^|L|))（|L| 为该轮前 L 的位宽，轮后两半位宽互换，偶数轮后复原），输出 L × 2^(P − ⌊P/2⌋) + R。轮函数 F_r(R) 取卷二 §1.10 同一个 sha256：对“轮钥_r、竖线、R 的十进制”拼成的串取 sha256，前 16 位十六进制（64 位）；轮钥_r 为对“世界种子、`|keyid|`、r 的十进制”拼成的串取 sha256 的十六进制，r = 0…7。每轮可逆，故 π 是双射，置换段内不撞号；轮钥由世界种子派生，键号对规则仍不透明（卷四 :816）。迁移不换来源聚合体（R27-2.7），故本名键号终身不变。
    3. **seq 段**：键号 = 2^P + `identities.seq`（卷四 §2.6 的键号计数，取后加一）。用于：没有成员身份的个体（手写个体，`pin_identity`）的本名键；本条第 4 项超界者的本名键；一切后建的键（`assumeIdentity` 建的化名、法号、潜藏键等）。`identities.seq` 达到 2^P 即拒写：上限 2^P 由本条设定（不是 R27-5.1 的 `safeIntMax`），错误码借用 E-DET-OVERFLOW。
    4. **超界**：来源聚合体的 `aggNo` ≥ 2^`keyIdAggBits`，或序号 ≥ 2^`keyIdOrdinalBits` 的成员，本名键一律取 seq 段；聚合体号超界时，以该聚合体为来源的全体成员同样处理（与各自序号无关）。这类成员在取得成员身份的同一事务里实体化并取键，此后恒为钉住，原因代号 `pin_keyspace`（R27-2.4），不折叠，所以键号不必重算。判定只读 `aggNo`、序号与规则表两个常数，确定性、复演一致。
    5. **足迹**：置换段本名键可由成员身份重算，属基本行、不计足迹；seq 段的键不能由成员身份重算，照常计足迹（R27-2.3 第 1 项）。证明脚本 脚本/X5/prove-x5-keyid.mjs，原始输出 审查/脚本输出/X5-终版-证明原始输出.txt（小位宽穷举双射；正式位宽多种子百万级样本无碰撞；两段不重叠；输出 ≤ `safeIntMax`；超界样例逐例落入 seq 段且原因为 `pin_keyspace`）。
- **R27-2.3 等价**：一个个体与聚合体中的一个成员等价，当且仅当它有成员身份且**足迹为空**。先定义**基本行**：该个体的实体行里，pathTypes（卷二 §2.7）标为“可由成员身份重算”的字段，并且现值等于按 R27-2.2 重算出的值。基本行有哪些字段只由 pathTypes 的这个标记决定，不手写清单（标记的登记见 §5）。足迹 = 下列各项的并集：
  1. 状态中以该 id 为路径段的全部路径，**基本行和聚合机制自身的路径除外**；以及任何以引用类型指向该 id 的路径（按 pathTypes 判定）。实体行里没有上述标记的字段、或有标记但现值与重算值不同的字段，都计入足迹；有标记的路径下，重算给不出的条目（多出来的）同样计入。身份键路径 `identities.<person>.*`（卷四 §2.6）带此标记：重算只给出置换段的那把本名键（键号按 R27-2.2「本名键号」，其余字段按卷四 K-1 实例化时的取值），它与现值相等即属基本行；seq 段的键（化名等后建键、手写个体与超界者的本名键）重算给不出，一律计入（封卷后勘误，李白 11-14 X5）；
  2. 以该 id 为端点的未结束持有边，种类在 `keyHoldings` 内且与分组键一致的除外；
  3. 引用该 id 的未了结义务；
  4. 到期堆中以该 id 为对象的条目；
  5. 该 id 名下余额非零的账户，资源在 `pooledResources` 内的除外。
  足迹由内核维护的反向索引得出；索引是投影，可随时丢弃重建，不落盘。
- **R27-2.4 钉住**：`pinned` 为真，当且仅当足迹非空，或没有成员身份，或成员身份超出本名键号位宽（R27-2.2「本名键号」第 4 项，原因 `pin_keyspace`；封卷后勘误，李白 11-14 X5），或该实体是玩家控制的实体，或它所在单元的有效层是个体层。`reasons` 给出命中的类别代号，只用于解释；任何代码不得按原因代号分支。**不存在逐条手写的钉住条件清单**：哪个系统在个体身上留了状态，哪个系统就自动把他钉住。
- **R27-2.5 折叠**：对 `pinned` 为假的个体执行，时机只有两种——该单元有效层节拍的整拍边界；换层协议内（R27-1.7）。两者都由状态与绝对时间决定，与推进请求怎样切分无关。
  - 未分户的个体（仍在成员区间里）：折叠 = 删除基本行，别的都不动。
  - 已分户的个体：折叠 = 把他名下 `pooledResources` 各资源的余额经账本全部转入聚合账户，把成员序号并回成员区间（`bornMinute` 相同且序号相邻的并成一段），删除基本行。
  - 个人名下的余额并入总数后，谁原来有多少就不再保留——“没有个人历史的人只以总量存在”正是折叠的含义（§1.1 第 2 条）。这是一次真实的状态变化，不是可逆的换表示。
  - 对足迹非空的个体折叠即 E-AGG-FOLD-FOOTPRINT。
- **R27-2.6 实体化与分户分开**：
  - **实体化**（`materialize`）只建立基本行，**不动账**：成员在 `pooledResources` 里的份额仍留在聚合账户。按指定的成员身份实体化；被实体化的成员仍留在成员区间里，除新增基本行与本条所列同一事务写入外不改任何状态。分组键里经 `keyHoldings` 种类派生的维度，实体化时在同一事务里按键值开该种持有边，条款只由成员身份确定性重算（R27-2.2）；条款等于重算值的这类边与基本行同等对待、不计足迹，条款不同的边或多出来的边照常计足迹。单元的有效层变为个体层时，该单元全部聚合体的全部成员实体化；离开个体层时按 R27-2.5 折叠。
  - **建基本行的入口**（封卷后勘误，卷十 C10-8）：实体化一名成员 = 以卷十 `rosterOf`（参数为该成员的来源聚合体 id 与序号）取名册条目（卷十 R10-4.8），交卷四 `instantiatePerson` 建行（卷十 R10-4.9），新行 id 即名册条目的 `instanceId`（卷十 R10-12.2）；按分组键写入的维度与持有边照本条与 R27-2.2 在同一事务写。名册条目是成员身份的纯函数，所以 R27-2.2 的“重算”就是以同一成员身份再走这一条路；本卷不另写建行代码，对任何聚合种类都是这一条路。
  - **开局法术知识授予**（封卷后勘误，卷十 C10-21）：开局时已在世的成员（所在成员区间 `bornMinute ≤ genesisMinute`）被实体化时，在同一事务里（与按 `keyHoldings` 开边同一事务）按成员身份调卷二十二 `grantLore`，持有判定照卷十 R10-4.14 ②，本卷不另写判定。这样开出的 `knows` 边**不属基本行、计入足迹**（R27-2.3 第 2 项：`knows` 不在任何聚合种类的 `keyHoldings` 内），持有该边的成员实体化后即钉住。理由照卷十 R10-4.14 ② 原文：持有者按卷二十二 R22-9.6 整人不释放、随之钉住（R27-2.4），这条边折叠时不删、不重算，所以不按“可由成员身份重算”处理；钉住个体数的上界见 R27-3.9。
  - **换层时的站点物化**（封卷后勘误，卷十 C10-8）：单元的有效层变为个体层时，在同一事务里先实体化全部成员，再对该单元每个站点按 id 升序调卷十 `requireMaterialized` 请求全部物化阶段（卷十 R10-3.7 ①）；先实体化，是因为居民安置阶段读的是已实体化的成员（卷十 R10-4.10）。观察锚变动与档位重评两种换层（R27-1.7）都走这一步。
  - **分户**（`settleOut`）：某条规则要对一个成员个人名下的 `pooledResources` 账户记账时，先把他的份额从聚合账户转到个人账户，再记这笔账。份额按 `shareRule`：`share_percapita` 为聚合账户余额整除“当前尚未分户的成员数”，余数留在聚合账户；`share_sampled` 为按 `shareDist` 抽取并钳在聚合账户余额之内，键按 R27-8.6。分户后该成员从成员区间移出，成为普通个体。
  - **规则要对聚合体里“某一个”成员写个人状态时**，取哪一个由骰值键抽取决定（R27-8.6），随后实体化该成员。
  - 分户发生在哪一刻、先后次序如何，由规则的写入在同刻全序里的位置决定，是世界里发生的事，与推进请求怎样切分无关。
- **R27-2.7 统计形态下的增减与迁移**：减员按骰值键在有序成员表上抽位置；增员按 R27-2.2 取 `nextOrdinal` 并加一；在聚合体之间迁移时成员保留原来的（来源种子键, 序号）与 `bornMinute`，只换所属聚合体。成员区间保持有序、互不重叠（否则 E-AGG-MEMBER-OVERLAP）。
- **R27-2.8 分组键只用已声明、且不随时钟变的维度**：`keyDims` 必须是该实体类已登记的枚举型或引用型维度；用未登记维度即 E-AGG-KEY-UNDECLARED。由时钟派生的维度（年龄段一类）不得作分组键，否则 E-AGG-KEY-CLOCKED——聚合体不逐个成员存状态，没法在某个成员跨过界线的那一刻把他挪到另一个聚合体。需要按年龄这类量区分时，由统计形态的规则从成员区间的 `bornMinute` 现算。所在单元是隐含键，由 `simUnitOf` 给出，存在 `aggregates.<aggregate>.unit`，不写进 `keyDims`。聚合种类表不出现任何具体实体 id。
- **R27-2.9 可折叠的前提是“随时间变的事实由时钟派生”**：凡希望其主体可折叠的系统，空闲时不得在个体身上留增量状态；年龄这类量由出生时刻与时钟派生（卷二 §1.12）。留了状态不是错误，只是该个体会被钉住。
- **R27-2.10 未物化站点的建筑在统计层不另算增减**（封卷后勘误，卷十 C10-8）：未物化站点按设施类型计的设施数与床位，只由清单经卷十九的类型派生函数给出（卷十 R10-3.10）；清单在第 0 日之后不由任何结算形态改写，本卷不给它设统计形态的增减规则，也不另存“统计层建筑数”。任一结算形态要在未物化站点之下增一栋建筑，或要拆、毁、改其下某一栋，都属“在其下建行或要拿到其下某一行的 id”，先按卷十 R10-3.7 ② 调 `requireMaterialized` 请求所需阶段，再经卷十九的写者写，与个体层同一路；物化出的建筑行不因单元离开个体层而删除（卷十 R10-3.11），此后按该系统在运行矩阵里声明的形态结算。哪个系统在统计层增减建筑、何时增减，由该系统的矩阵行与其定义卷的规则定，本卷不定（配合见 §5）。

#### 4.2.6 验收断言

- **A27-2.1（扫描式）**：S27-9 命中数为 0（`aggregate.mjs` 及其 import 闭包里没有任何实体类、物种、组织、持有种类、义务种类、状态族、记录种类、系统键的句柄字面量，钉住只由足迹推出）；S27-2 命中数为 0。
- **A27-2.2（验收测试，往返恒等；交卷十二机器化）**：① 对任一实体化事务未给他开出足迹项的聚合成员，实体化后不对他做任何写入就折叠，排除日志分区后的世界状态摘要（定义见 R27-4.1）与实体化之前相等；实体化时被授予秘传知识的成员（R27-2.6 开局法术知识授予，所开 `knows` 边计入足迹）不在此列，他实体化后即钉住、不可折叠，本条对他改为断言实体化后 `pinned` 为真；② 对任一未分户、足迹为空的个体，折叠后再按同一成员身份实体化，该摘要与折叠之前相等。往返多出的折叠、实体化两条事件只在日志分区里，不在比较范围内。已分户的个体不在本条之内——他的折叠按 R27-2.5 是真实的状态变化，由 A27-2.3 的守恒和 A27-2.4 的身份稳定约束。
- **A27-2.3（不变量式，守恒）**：任意折叠、实体化、分户、迁移前后，每种资源的全局总量不变；全局人数 = 各聚合体成员区间长度之和 + 不在任何成员区间里的个体数，只在出生与死亡事件上变化；同一成员身份不同时出现在两个成员区间里。
- **A27-2.4（不变量式，身份稳定）**：同一（来源种子键, 序号）在任意多次实体化之间，实例 id 与全部采样维度相同。
- **A27-2.5（扩展性式）**：新增一个在个体身上留状态的系统，不改 `aggregate.mjs`，带该状态的个体自动 `pinned` 为真。
- **A27-2.6（扩展性式）**：新增一种聚合种类（任意实体类、任意分组键），只加一行，A27-2.2 至 A27-2.4 通过。

### 4.3 成本模型与降级阶梯

#### 4.3.1 维度

`coef`、`coefMaterialize`、`costSubjects`、`cadenceRuleKeys`、`budgetCuPerChunk`、`chunkMinutes`、`ladder`；状态 `simDegrade.level`、`simDegrade.atChunk`；派生量 `costUnits`（不落盘）。

#### 4.3.2 统一入口

`costPlan`、`degradeLevelOf`；`sim-advance.mjs` 在评档块边界调用 `costPlan` 并写 `simDegrade`；`simTierOf` 读 `simDegrade.level` 取有效半径。

#### 4.3.3 规则

- **R27-3.1 成本是算出来的，不是量出来的**：成本按**一个评档块**计，不按一次推进请求计。给定状态与一个候选档位，预计成本 = 对每个单元、每个系统求和：主体数 × 块内拍数 × `coef[system][form]`，再加一次性的实体化成本。
  - 形态取该单元在候选档位下的有效层所对应的矩阵格；块内拍数 = `chunkMinutes` ÷ 该层节拍，是规则表常数。周期不是层节拍、而是若干规则表间隔的系统（即 `cadenceRuleKeys` 里有行的系统，如 R27-3.8），块内拍数 = `chunkMinutes` ÷ 该行所列各规则表键全部值中最短的一个，向上取整，得上界；各间隔 ≥ 1 由登记该间隔的卷的加载校验保证（封卷后勘误，卷九 §5.3 勘10、勘10 附）。
  - 主体数：个体与批量形态取该单元内 `costSubjects[system]` 所列实体类的行数，其中出现在聚合种类表里的类按“成员区间长度之和 + 不在成员区间里的个体数”计（不看当下有多少成员恰好已实体化）；统计形态取聚合体个数；派生与冻结形态为 0。
  - 一次性成本 = `coefMaterialize` × 候选档位下将处于个体层、而现在还没有基本行的成员数。
  - 全部整数运算。输入只有状态与规则表。
- **R27-3.2 降级只由世界内在的量决定**：档位的输入只有三类——单元到观察锚的距离（经有效层）、各单元里各实体类的主体数与足迹（经钉住）、规则表。下列各项一律不得进入档位判定，也不得进入任何状态：
  - 单次推进请求的长度、起止时刻、类别标签（`advclass`）；
  - 实测耗时、内存、机器负载、AI 额度、网络状况、墙钟。
  理由有两条。其一，降级会改变哪些单元按哪种形态结算，如果它取决于机器快慢，同一种子在本机与云上就会走出不同的世界（违反卷一 I50）。其二，如果它取决于请求怎样切分，“一次推进 N 天”与“分 k 次推进合计 N 天”就会得到不同的世界（违反 R27-1.11）。
- **R27-3.3 评档**：只在绝对时间的评档块边界进行（时刻是 `chunkMinutes` 的整数倍；开局时刻算第一次），由调度器在该时刻的固定阶段触发，属于时钟形状的规则。
  - 步骤：先按旧档位把各单元结算到该边界（R27-1.7）；再读此刻的状态，从 0 档起逐档套用 `ladder`，取使 R27-3.1 的预计成本不超过 `budgetCuPerChunk` 的最小档；把它写入 `simDegrade.level`，块号写入 `simDegrade.atChunk`。
  - 两次评档之间档位不变，哪怕其间主体数变了。
  - 到了最高档仍超预算，按最高档执行，并经内核报告出口记一条 E-COST-OVER-BUDGET（告警级，不改状态）。
  - 推进请求跨过边界时在边界处评档；请求恰好停在块中间时不评档。所以某一时刻的档位只取决于最近一个边界处的状态，与请求怎样切分无关（A27-1.8）。
- **R27-3.4 阶梯操作**（累加）：`deg_individual_hops` 把个体层半径减去 `amount`，下限为 0；`deg_rule_hops` 把规则层半径减去 `amount`，下限为个体层半径；`deg_drop_shared_ancestor` 停用共同祖先条件。节拍不在可降之列——改节拍就是改规律。卷二十 §4.10.4 所说“降级改的是层与精度”，在本卷的含义就是：改的是哪些单元落在哪一层，从而改了它们的结算形态；没有别的“精度”开关。
- **R27-3.5 长推进分块**：推进请求跨过评档块边界时，按块逐段推进，每到边界按 R27-3.3 评档、按 R27-1.10 重新取计划。由 R27-1.11，分块不改变结果。块与块之间让出执行权由 `kernel/scheduler.mjs` 负责（卷二 §2.9 第 0 条“推进计划与心跳推进”）。让出只影响别的请求何时被受理，不影响本次推进的结果；让出期间到达的玩家请求与心跳推进请求排同一个队，不插队，在本次推进处理完之后按请求编号逐条处理（卷二“心跳推进”第 3 点），每条都记进输入序列（R27-7.3）。
- **R27-3.6 系数是世界数据的一部分**：`coef` 由基准标定后入库（§4.6），随世界数据副本一起存进存档（§4.4）。所以重新标定只影响新开的世界，已有世界的降级行为不变。
- **R27-3.7 单向读**：卷九 §4.14 可以经 `degradeLevelOf` 读档位来调低 AI 档位；反过来，AI 档位、费用账、模型可用性不得被本节读取（卷一 I42）。
- **R27-3.8 活动推进重查的性能项**（封卷后勘误，卷九 §5.3 勘10，李白 11-13 批）：卷九的活动推进重查（卷九 R9-1.12、R9-12.7）按 X27-1 登记为一个系统，系统键 `activityRecheck`，补系统声明行、矩阵行、`coef` 行、`costSubjects` 行与基线行；只加数据行，R27-3.1 的成本式不改。
  - 主体：有当前活动的个体，外加没有活动、按 `rules.npc.idleAdvanceMinutes` 登记空闲推进点的个体层的人；`costSubjects` 取人这一实体类（按 R27-3.1 计行数，是上界）。
  - 周期：不是层节拍，而是 `rules.act.advanceMaxMinutes` 各值与 `rules.npc.idleAdvanceMinutes`；登记为 `cadenceRuleKeys` 的第一条数据行 `cadenceRuleKeys.activityRecheck = ["rules.act.advanceMaxMinutes", "rules.npc.idleAdvanceMinutes"]`（卷九 §5.3 勘10 附）；块内拍数按 R27-3.1 取其中最短的一个折算，得上界。
  - 每拍每主体的成本：每个推进点一次重查（只读数值维度与固定代号：`can()` 的两个 view、`interruptRX` 引用的 view、同意边），加账本抽查（卷九 R9-1.12“经账本离手”）：活跃需求块数 × 引用账户数 + 带工位的活跃需求块数 × 1（每个推进点对该活动的需求块求值一次，扫它所引用的账户与容器；带工位的再重求场所类前提三项——设施行终止谓词、固定装置能力、所在建筑 `type`，不读建筑份额账户；只扫有在世活动挂着的，不扫全账本）。同一性能项另计前提失效通知的重查（每条通知对所涉各人的当前活动各一次）与越界时刻的求解（每次推进至多一次二分），标定时折入 `coef`。
  - `coef[activityRecheck]` 与基线行的数：待实测（解冻后腾讯云），本卷不填数；未填前照 R27-6.6 只记录不拦，阶段收口时未填即 E-PERF-UNCALIBRATED。

#### 4.3.6 验收断言

- **A27-3.1（扫描式）**：S27-3 命中数为 0；`cost-model.mjs` 与 `sim-tiers.mjs` 的输入声明（卷二 §2.3）里没有 AI、费用账、旁路记录相关的状态键；`costPlan`、`advancePlan` 的参数表与 3.1 所列完全一致，没有请求长度、类别标签或其他表外参数。
- **A27-3.2（不变量式）**：同一状态，`costPlan` 在本机与云上、在项目支持的每个 Node 版本下返回值逐位相同。“本机”读法同 A27-5.4（封卷后勘误，同类收清）。
- **A27-3.3（不变量式）**：任意档位下，观察锚所在单元的层为个体层；任意档位下 A27-2.3 的守恒成立。
- **A27-3.4（不变量式）**：`degradeLevel` 对预算单调——预算调大，档位不升。
- **A27-3.5（扩展性式）**：新增一个系统，只加系数行即进入成本模型；缺行即加载失败，不存在“默认零成本”。

### 4.4 存档（事件日志加快照、分片）

#### 4.4.1 维度

`shards`、`snapshotEveryEvents`、`segmentEvents`、`keepSnapshots`、`logKeepSig`、`logKeepVerbRoles`（R27-4.12）。清单字段：`rulesDigest`、`dataDigest`、`snapshotIndex`、`clockMinute`、`shardDigests`、`logSegments`、`saveDigest`（存档摘要，只此一种）。存档清单给玩家显示的只有 `clockMinute` 与存档槽位编号（R27-4.10）；规则表 `saveSlotCount`、`saveImportMaxBytes`（§2.2）。

#### 4.4.2 统一入口

卷二 §2.9 第 1 条登记的内核读档入口与存档写盘出口；存档、读档、导出、导入四路的路由与结果回传按卷二 §2.9 第 0 条“存档四路”（唯一定义），本卷只引用；本卷不新增文件边界。扫描 S27-7。

#### 4.4.3 规则

- **R27-4.1 逻辑文档与物理布局分离；摘要只有一种**：存档在逻辑上是一份文档，分五个部分（族 `docpart`）——世界数据副本、状态、持有、账本、事件日志。**存档摘要**对逻辑文档计算，口径与排除表完全按卷二 §2.9 第 3 条（卷一 §8.3：只有一种哈希），本卷不另立口径，也不设第二种哈希。物理上怎样切片不影响存档摘要。
  - 规则层不得读取存档摘要或任何摘要（S27-8）。摘要只供三处使用：存档读写、门禁、测试。
  - 本卷所有“同种子复现”“分段无关”“存读恒等”一类的确定性要求都写成验收测试：两边各得一份存档，比较存档摘要，由卷十二机器化。
  - 例外只有 A27-1.3、A27-2.2、A27-8.2 三条：它们的两边按构造就有不同的事件日志（推进请求条数不同、多出折叠与实体化事件）或不同的登记表，所以比的是**排除日志分区后的世界状态摘要**——用存档摘要的同一算法、同一张排除表（排除表只引用卷一 §8.3 的单点定义，本卷不另抄），计算对象只取 `doc_state`、`doc_holdings`、`doc_ledger` 三个部分；`doc_log` 不计入，`doc_data` 不属世界状态、另由 `dataDigest` 标识。它只是存档摘要在计算对象上的限定，只供测试使用，不落清单，不是第二种哈希。
  - 开着文字模型时两边的 AI 文字可以不同，存档摘要按构造就不同；这时按卷一 §8.3、V-13 的口径比“事件流与 textPaths 之外的状态逐值相等”，或者把同一份 AI 输出回放后再比存档摘要。这是引用卷一的比较办法，不是新哈希。
- **R27-4.2 每个世界自带数据副本**：开局时把当时的维度表、规则表、词表冻结成一份副本存进存档（卷一 §8.5），其摘要为 `dataDigest`。世界此后只读自己的副本。语言包不在副本内，换语言包不改任何摘要。
  - **包集合节与追加段**（封卷后勘误，李白 11-14 裁定 Q28-1“只增不删”，卷二十八 C28-5）：副本带一个 `packSet` 节（字段含 `joinedAt`，定义与唯一写者见卷二十八 §2.7）。开局后副本原有部分不改；世界内追加（卷二十八 R28-6.6）只能给副本加只写一次的追加段，新包的 `packSet` 条目写在该追加段内，原有部分的 `packSet` 节不改。`dataDigest` 的覆盖范围 = 原有部分加全部追加段；追加提交时按新范围重算，由它合成的 `rulesDigest`（R27-4.3）随之重算，写进新清单；读档的那一次相等比较取清单里的最新值。
- **R27-4.3 规则指纹**：`rulesDigest` 由内核与规则层的源码摘要和 `dataDigest` 合成。读档时只做一次相等比较：不等即拒绝加载（E-SAVE-RULES-MISMATCH），不迁移、不尝试修补，也不改不删该存档文件。导入（`save_import`）在写进目标槽位之前做同一次比较（卷二 §2.9 第 0 条“存档四路”第 5 点）。显示层、语言包、host 的改动不进 `rulesDigest`。本条只管“比较这一步”；已有世界能不能安装或卸载扩展包、装了之后数据副本与两个摘要怎样算，由卷二十八 §4.6 定（§8 第 12 条），本卷不替它裁定。
- **R27-4.4 字段序列化声明读 pathTypes**：哪些路径存、存成什么类型，唯一依据是卷二 §2.7 的 pathTypes。任何系统不写自己的序列化函数；没有声明的路径写不进状态，自然也进不了存档。
- **R27-4.5 事件日志加快照**：日志只追加，每 `segmentEvents` 条封成一段；每 `snapshotEveryEvents` 条事件做一次快照。快照与封段只在一刻全部处理完时做；条数已到而这一刻还没处理完的，顺延到该刻末（封卷后勘误，李白 11-14 1442 裁定一①）。所以 state 只停在"某刻已全部处理完"的边界上，存档里没有做了一半的刻；推进中整刻作废（卷二十 §4.1.3 第 7 条）不会碰到已封的段与已做的快照。卷二 §2.9 第 0 条的提交后待办记录（`pendingPost.*`，属状态部分）在每笔事务提交后随即执行并删去，到刻末已为空，快照里不含未执行的记录；整刻作废时本刻写下的记录随作废段一并丢弃（同一勘误）。恢复 = 最近一个完好快照 + 按其后日志段里的玩家指令与推进请求重跑规则（R27-7.2、R27-7.3，§4.7）；日志里的原语列表只作核对，不原样施加（封卷后勘误，李白 11-14 卷二十四二审裁定丙）。读档耗时与该快照之后的模拟量成正比，由 `snapshotEveryEvents` 控制。
- **R27-4.6 分片**：`shards` 覆盖逻辑文档的全部五个部分，每行用 `part` 指明属于哪一部分；每个部分里的每条路径恰属一片（状态路径的匹配语义用卷二 §2.7；世界数据副本按表、持有与账本按其定义卷登记的路径、日志按段）。任何一部分有路径没被覆盖即 E-SAVE-SHARD-UNCOVERED，两片重叠同样报错。
  - `part_single` 整片一个文件；`part_by_unit` 按模拟单元再切。路径归哪个单元只经注入的映射取：规则层在启动时经 kernelApi `registerUnitOfPath`（卷二 §2.7）向内核登记一个"路径→模拟单元"映射函数，内核只认这个注入的接口，不 import 规则层；没登记映射、或映射对某条路径返回空，即按未覆盖处理（E-SAVE-SHARD-UNCOVERED），不猜。只用于状态路径，不用于 `doc_data`（封卷后勘误 1118b24，李白 11-18 块 2-4 三件裁定 a）。
  - `part_by_segment` 按追加的先后切段，**只能用于只追加的路径**：事件日志，pathTypes 带“只追加”标记的状态路径（该标记的登记见 §5），以及世界数据副本的追加段（R27-4.2）。对这三类以外的路径用它即加载失败。
  - 世界数据副本的追加段（R27-4.2）单开一行：`part` = `doc_data`，`part_by_segment`，每个追加段落一片，只写一次、此后不重写；副本原有部分仍是开局后只写一次的那一行，口径不变（封卷后勘误，卷二十八 C28-5）。
  - 快照不是第六个部分：一个快照就是那一刻逻辑文档除日志外四个部分的分片集合，由清单的 `snapshotIndex` 指到。
  - 同一个 Sealed 值不跨片拆开。
- **R27-4.7 写时复制**：每个分片文件按内容摘要寻址。存档时只写摘要变了的片；没变的片不重写。远处统计层单元的片很少变，所以一次存档的写入量与“变了多少”成正比，不与世界总量成正比。分片摘要只用于完整性与去重，不是存档摘要，也不构成另一种可比较的哈希。现存储层在日志段之间记的前后相接摘要链并入本条：段的完整性由清单里逐段的摘要保证，不再另维护一条链（M27-8）。
- **R27-4.8 原子提交**：先写齐新分片，最后以原子改名提交清单。清单是唯一的提交点；清单引用的片缺失或摘要不符即 E-SAVE-SHARD-DIGEST，回退到上一个完好清单并报 E-SAVE-TORN。写盘失败即 E-SAVE-WRITE-FAIL（卷二 §4.3 定义，本卷引用）。槽位里两份清单都不存在是空槽，不是残缺：明确要求载入该槽位即 E-SAVE-EMPTY，启动时自动读档视为新档、不报错（卷二 §2.9 第 0 条"存档四路"第 1、2 条与 §4.3 定义，本卷引用；封卷后勘误 1118b24）。
- **R27-4.9 保留与修剪（只管存档的日志与快照）**：保留最近 `keepSnapshots` 个快照及其后的日志段；更早的日志段不整段删除，在同一快照点按 R27-4.12 折叠（封卷后勘误，卷二十四 C24-10、Q24-2）。修剪只在快照点、只由规则表参数触发；不由磁盘余量、墙钟或手动时机触发。不被任何保留清单引用的分片文件才可回收。本条不碰状态：状态里的领域记录何时过期、最多留几条是规则语义，由记录所属的领域卷用到期项（卷二十 §4.1）表达，参数进规则表——它不得跟快照间隔挂钩，否则改一个存储参数就改了世界（M27-13）。
- **R27-4.10 存档不记墙钟**：存档清单的显示字段只有两样，世界时钟 `clockMinute` 与存档槽位编号，都是数值（卷二 §2.9 第 0 条“存档四路”第 3 点，唯一定义）。引擎不读墙钟，不记存档的真实时间，也不由装配文件传入任何显示参数；真实时间归宿主显示（文件系统的修改时间、浏览器的下载记录），不进存档、不进存档摘要。内核自己不取墙钟（S27-3）。战役标识不得用随机标识函数生成：需要确定性的由世界种子派生；区分存档文件用存档槽位编号（取值 [0, `saveSlotCount`)），不另设由装配文件传入的标识（M27-17）。
- **R27-4.11 进程归属**：存档读写只在 Node 服务端进程（`kernel/save.mjs`、`kernel/load/save.mjs`，卷二 §2.9 第 0 条“存档四路”）。导出与导入时客户端只原样收发存档字节，不解析；导入的字节与本机写出的存档受同一套校验（R27-4.3），没有第二条读档路径。扩展进程不保存任何权威数据，其本地偏好是客户端偏好，不进存档（本条），与卷一 §8.3（存档哈希的范围）的排除表无关。
- **R27-4.12 日志折叠与保留档**（封卷后勘误，李白 11-14 批，卷二十四 C24-10、Q24-2；理由：存档体量。原 R27-4.9 把早于最早保留快照的日志段整段修掉，卷二十四的日志投影随之丢失，R24-1.6 要求的“保留档以上结果不变”无从成立）：R27-4.9 修剪到的每个日志段（已不在任何保留快照之后），在同一快照点折叠成一个**折叠段**，替换原段。
  1. **留原样的事件**：下列事件连同全部字段原样留在折叠段里，id 与日志次序不变：① `eventSig` 不低于 `logKeepSig` 的；② 被此刻状态中任一类型为 `EventId` 的路径引用的（按 pathTypes 判定，含以 `EventId` 为成分的映射键）；③ 按句柄保留的：动词经 `logKeepVerbRoles`（§2.2）所登记的保留句柄引用的事件（含卷二十四 A24-7.2 的创世事件；只按句柄解析出的动词代号判定，不读文字，不看分量与引用；数据行见 §4.4.5）；④ 已留事件的 `payload.causedBy` 所列事件，递推到闭包。
  2. **合计行**：其余事件不留原样，合并成合计行：键为（计数动词、`eventCount` 的各筛选字段在该事件上的原值、日序），值为条数（`integer:count`）。每条事件对它按卷二十四 R24-2.7、R24-2.10 计入 `eventCount` 的每个动词各记一次；筛选字段由卷二十四 R24-2.7 定，原值照存（含该卷定义的空值）；日序取事件时刻的世界日序（与卷二十四 §2.4 同一日序）。合计行只含代号、id 与整数。
  3. **落片**：折叠段属 `doc_log`，按 `part_by_segment` 落片，只写一次，此后不再折叠、不再重写；原段的分片在新清单不再引用后按 R27-4.9 回收。
  4. **不改世界**：折叠只在快照点、只由规则表参数触发，不读墙钟与磁盘余量；只改 `doc_log`，不改 `doc_state`、`doc_holdings`、`doc_ledger`；规则层不读日志（卷二十四 S24-4），所以折叠不改变世界的任何后续结果。折叠只作用于不在任何保留快照之后的段，两种复演（R27-7.2）所取的段不受影响。
  5. **投影结果**：只取分量不低于 `logKeepSig` 的事件的投影（卷二十四 `chronicleAll`、`legendsView`、`epochView`、`originEvents` 在这一档以上的部分）折叠前后相同；`eventCount` 在以日为界的时间段上折叠前后相同；分量低于保留档、又不被状态引用的事件此后不能逐条检索（卷二十四 R24-1.6）。`logKeepSig` ≤ `era.boundarySig` 由加载校验保证（§2.2），所以纪元的界事件都留原样。状态里的 `EventId` 引用只能从状态或当前事务得来（规则层不读日志），被丢弃的事件此后不会再被引用，故第 1 项②在任一时刻都保证状态引用的事件在日志里。

#### 4.4.6 验收断言

- **A27-4.1（扫描式）**：S27-7 命中数为 0；规则层中“序列化”“反序列化”职责的函数为 0（按是否向存档出口传参判定）；逐条核对：pathTypes 的每一条路径模式、世界数据副本的每一张表、持有与账本登记的每一条路径、日志，都恰好落在分片表的一行里，没有遗漏也没有重叠；用了 `part_by_segment` 的每一行都是事件日志、带只追加标记的路径或世界数据副本的追加段（R27-4.2）；S27-8 命中数为 0。
- **A27-4.2（验收测试，分片无关；交卷十二机器化）**：同一逻辑文档换任意合法分片表存盘再读回，存档摘要不变。
- **A27-4.3（验收测试，存读恒等；交卷十二机器化）**：任意时刻存盘后读回，继续推进同样的指令序列，与不存盘直接推进相比，存档摘要在每个快照点相等（不开文字模型；开着时按 R27-4.1 的卷一口径比）。
- **A27-4.4（不变量式，中断安全）**：在写盘的任一步骤中断，读档得到的要么是新清单的完整状态，要么是上一个清单的完整状态。
- **A27-4.5（不变量式，语言无关）**：换语言包、换显示层版本后读同一存档，`rulesDigest` 与存档摘要不变（接卷一 I40）；同一状态在不同的真实时刻、写进不同的槽位，存档摘要相等，清单里没有墙钟字段（R27-4.10）。
- **A27-4.6（不变量式，拒绝而不破坏）**：`rulesDigest` 不符时读档失败，存档目录下所有文件的字节与修改前相同。
- **A27-4.7（扩展性式）**：新增一个系统及其状态键，只在 pathTypes 与分片表登记，不改存档读写文件，A27-4.2、A27-4.3 通过。

### 4.5 确定性数值

#### 4.5.1 维度

`mathAllow`、`safeIntMax`、`fnTables`；族 `detfn`；卷二 §1.5 各数值类型的 `precision`（引用）。

#### 4.5.2 统一入口

求值走卷二 §3.3 管线；超越函数只经内核的定点数学设施（现 det-math.mjs，归入 kernel 组，导出名向卷二 §2.7 kernelApi 登记）；集合遍历只经内核提供的按键排序遍历；扫描 S27-3、S27-4、S27-8。

#### 4.5.3 规则

- **R27-5.1 状态里的数只有两种**：整数（绝对值不超过 `safeIntMax`），或按维度 `precision` 的定点数（底层同样是不超过 `safeIntMax` 的整数）。非有限值、负零不得进入状态（E-DET-NONFINITE）。一次写入会让某个数超出 `safeIntMax` 时，该写入被拒绝并报 E-DET-OVERFLOW，不截断、不换别的表示法；状态里不存在“用字串装的大整数”（卷二 §1.5：字串不得出现在运行期可写路径）。确有超大数需求的领域，报卷二 §1.5 增类型，本卷不自立。
- **R27-5.2 运算**：规则层的数值运算只有三条路——卷二 §3.3 求值管线；内核定点数学设施；`mathAllow` 列出的整数安全成员（取整、绝对值、最大最小、符号一类）。其余数学成员在规则层出现即 E-DET-FLOAT。内核定点数学设施是全仓超越函数的**唯一实现**，按下面的定义做（卷二十 §4.1.4 所指“卷二十七 §4.5 定义”即此）：
  - 族 `detfn` 的每个函数在 `fnTables` 里有一行，写明输入标度 `inScale`、输出标度 `outScale`、定义域 [`domainMin`, `domainMax`]（按输入标度的整数）、表步长 `step`、表值 `values`。
  - 求值：输入落在两个表点之间时做线性插值，全程整数运算，除法向零截断，结果按 `outScale` 给出。输入超出定义域即报 E-DET-DOMAIN 并拒绝，不外推、不钳位。
  - `fn_exp` 不另立表：直接用卷二 §1.10 冻结的指数表及其算法，本卷的这一行只指向它。现 det-math.mjs 里自带的指数实现删除（M27-9）。
  - `fn_sqrt` 用卷二 §1.10 的整数开方（牛顿法固定步数），不查表；`fn_pow` 由 `fn_exp` 与 `fn_ln` 组合，底数须为正；`fn_sin`、`fn_cos` 的表覆盖一个整周期，输入先按周期取余；`fn_atan` 的定义域之外用恒等式折回。
  - 表值由 tools 组的生成脚本离线算出后入库并带摘要，运行时只读表、不现算；门禁重新生成并逐位比对入库文件。表是世界数据副本的一部分（R27-4.2）。
  - 各行的标度、步长取值在首次标定时填入并写依据；指数表的归属以卷二为准（§8 第 14 条）。
- **R27-5.3 顺序**：凡结果依赖遍历顺序的地方，顺序必须由 id 的码点序或数值键决定。排序必须给出全序比较函数，比较键只能是 id 或数值（卷一 I40）；不得使用依赖区域设置的比较；不得依赖对象键的插入顺序来自何处。违例 E-DET-ORDER。
- **R27-5.4 同步**：规则层与内核的结算是同步的；结果不得依赖异步回调的完成先后。计时器与墙钟不在可用全局之内（卷二 §2.9 第 1 条）。
- **R27-5.5 时钟**：规则只认分钟时钟（卷二十 §4.1）。墙钟不进状态、不进键、不进任何判定。
- **R27-5.6 同刻全序**：同一分钟内的结算次序由调度器的全序键唯一决定（卷二十 §4.1、卷二 §2.7 的阶段与排序键），与注册顺序、文件加载顺序无关。
- **R27-5.7 跨环境**：同一输入在本机与云、在项目支持的每个 Node 版本下结果逐位相同。凡做不到这一点的语言特性，一律列入禁用并由 S27-4 扫描。“本机”读法同 A27-5.4：按卷十二 R12-9.8 读作该卷登记的玩家平台测试台，未启用期间按该条报未运行（封卷后勘误，同类收清）。
- **R27-5.8 存档摘要的实现与断言**：摘要排除表由卷二 §2.9 第 3 条的规则生成；本卷负责把生成器接进门禁并断言入库文件与生成结果一致（E-DIGEST-EXCLUDE-DRIFT，卷二 §4.3）。摘要函数只在存档读写文件、门禁与测试里可用；规则层引用它即 E-DIGEST-READ（S27-8）。

基准执行器在 tools 组，不在运行时；结果写基线文件，由门禁读取。规则层与内核不得读基线文件。

#### 4.6.3 规则

- **R27-6.1 两类指标分开拦，类别是数据**：每个指标的类别写在规则表 `metricClass` 里，门禁只读这张表，代码与正文里不出现“哪个指标属于哪一类”的清单。
  - **计数类**（`mc_count`）：与机器无关、逐位可复现，进核心门禁，每次合入都拦。首批：成本单位、事件数、存档字节数。
  - **计时类**（`mc_timing`）：只在云上的参考环境跑，每场景跑 `runs` 次取中位数，在阶段收口与大改动时拦。首批：回合耗时、推进一日耗时、存盘与读档耗时、堆内存。
  - 新增指标 = 加一个词表条目、在 `metricClass` 里加一行、加一个采集点；门禁判定代码不改（A27-6.4）。
- **R27-6.2 三道判据**：绝对预算（`budgets`）；相对基线的回退上限（`regressRatio`）；规模判据——同一场景把 `sizeClass` 翻倍，计数类指标的增幅不得超过 `scaleRatioMax`，用来在合入时就拦住平方级以上的写法。
- **R27-6.3 基线**：基线文件入库，按（场景, 系统键）分行记录计数类指标，按场景记录计时类指标。文件名 `tools/accept/perf-baseline.json`；写者登记在卷十二 §2.11（封卷后勘误，卷十二 C12-8）。
  - 计数类：对已有的（场景, 系统键）行，基线只降不升。
  - 新增内容怎样进基线：新增系统、新增场景、重新标定系数都会让计数上升。升幅只有同时满足下面两条才被接受——① 升高的行全部属于本次合入新登记的系统键或新增的场景行，或者本次合入改动了 `coef` 且附有 R27-6.6 的标定依据；② 新增部分通过 R27-6.2 的规模判据。已有系统的行在同一次合入里仍然只降不升。
  - 基线文件不能单独改：门禁核对基线文件的每一处升高都能对上同一次合入里的一条新增登记或标定依据，对不上即 E-PERF-BASELINE-UNJUSTIFIED。把已有行的基线调高须李白批，并在该行写明批准依据。
  - 计时类基线在通过后更新为新中位数。
- **R27-6.4 场景是数据，覆盖要求是对标签的计数**：一个基准场景 = 一行（世界种子、规模、推进时长、推进类别标签、覆盖标签 `tags`、参与的系统键 `systems`）。场景表必须满足：带 `st_other_region` 的行至少 1 行；带 `st_nonhuman_major` 的至少 1 行；带 `st_supernatural_major` 的至少 1 行；同时带 `st_no_anchor` 与 `st_long_advance` 的至少 1 行。门禁按标签计数判定，不读场景的说明文字。标签是否属实由采集数据核对：例如带 `st_no_anchor` 的场景全程观察锚为空集，带 `st_nonhuman_major` 的场景成本分解里非人类主体类占多数。
- **R27-6.5 层间一致性基准**（`pm_tier_drift`）：R27-1.9 的比较在这里执行，统计量取 `driftStat`，样本组数取 `seedSampleSize`，容差取 `driftTolerance`。
- **R27-6.6 标定**：`coef` 由基准对每个（系统, 形态）单独测得每主体每拍的耗时中位数，取整入库；`coefMaterialize` 同法测得。同时核对预计成本与实测计时的秩相关系数，低于 `costCorrMin` 即要求重新标定。带“待标定”的字段在第一次标定后填入，并写明标定环境与日期（basis）。**截止条件**：阶段收口门禁检查全部待标定字段，任何一个未填或没有依据即 E-PERF-UNCALIBRATED，收口不过；在那之前门禁对未填项只记录不拦。**长跑离屏实测**（封卷后勘误，李白 11-14 卷十九统计层提案三版裁定）：标定须含一项长跑离屏实测——世界离屏推进多年后，实测离屏的已物化站点数（对照 R27-3.12 的上界）与每拍 `settleStatBuild`、`settleFacilities` 的耗时。任一项超预算（R27-6.2 的绝对预算）即停，报李白再议卷十九的乙（另存增建清单）；不得自行放宽预算、上界或改用乙。
- **R27-6.7 分段记账**（待卷二收口后对齐）：`pm_turn_ms` 只量服务端从收到指令到产出投影这一段；传输与扩展渲染另由显示层卷记账。
- **R27-6.8 守恒是性能门的前置条件**：基准场景结束时调用卷六 §4.22 的源汇报告，任何一种资源不平即该次基准作废，不记成绩。

### 4.7 复演与规则只一版

#### 4.7.1 维度

族 `replaymode`；清单字段 `rulesDigest`（§4.4）。

#### 4.7.2 统一入口

`replay_apply` 在读档入口内部；`replay_verify` 在 tests 与 tools 组。扫描 S27-5。

#### 4.7.3 规则

- **R27-7.1 规则只有一版**（卷一 R-8）：代码里不存在“按存档版本走不同分支”的任何写法。事件、义务、记录上不带复演版本标记；整份存档只有一个 `rulesDigest`。现有代码里的运行期版本标记、投递版本标记、各领域的更新版本标记及其相等比较分支全部删除，只留现行那一支（M27-15）；卷一 R-8 判定与 V-17 里给存储与迁移留的例外随之取消（§8 第 15 条）。
- **R27-7.2 两种复演**（封卷后勘误，李白 11-14 卷二十四二审裁定丙）：两种复演做的是同一件事——从快照出发，只取日志里的玩家指令与推进请求（R27-7.3 ①②），重新跑规则；文字路径照 R27-7.3 末项取存档里已有的 Sealed，不调模型。`replay_apply` 在读档入口内部，用于读档恢复：恢复出的状态就是重跑的结果；日志里记录的原语列表只作核对（重跑产生的每条事件连同其原语列表与日志里同序号的那条比对）、`why` 与审计，不原样施加。推进钩子经 `writePath` 的直写、终止与复生等内核协议的写入、声明写者在事务内的反应写入，都不在原语列表里，一律由重跑得到，不另入日志。`replay_verify` 在 tests 与 tools 组，用于验证确定性：要求重新产生的事件流与日志逐字节相同。两者的正确性都建立在同版确定性上（卷一 §8.1，R27-7.1、§4.8）。任一事件不同即 E-REPLAY-DIVERGE，报告第一处分歧的事件序号与原语序号。
  - **追加段的挂载**（封卷后勘误，李白 11-14 裁定 Q28-1，卷二十八 C28-5、R28-6.9）：两种复演走到“世界追加了一个包”事件时才挂上该追加段（R27-4.2），在此之前该段不可见；挂上时以事件载荷里的追加段摘要比对所挂之段，不符即 E-REPLAY-DIVERGE。该摘要只供复演比较，任何规则不得读它判断逻辑（S27-8）。
- **R27-7.3 外来输入全部入输入序列**：能影响规则状态的外来输入只有两种，都按 kernel 发的请求编号记进**输入序列**——① 玩家指令（封闭代号集合内的动作代号加参数）；② 推进请求。输入序列是卷二 §2.9 第 0 条“心跳推进”第 4 点的称呼，存放与复演归本卷：它就是事件日志（`doc_log`）里的玩家指令与推进请求条目，R27-4.5、R27-7.2 重跑所取的正是它。**条目先单独提交**（封卷后勘误，李白 11-14 1442 裁定一②）：请求受理时，先单独提交一笔，把这条请求条目记入 `doc_log`，再开始处理。这一笔在整刻回退范围之外：推进中整刻作废（卷二十 §4.1.3 第 7 条）与处理事务的整笔回滚都只回退处理事务，不抹条目这一笔，所以被拒的请求按请求编号留在输入序列里，复演时在同一处同样被拒。
  - 推进请求有两种来源，条目是同一种（卷二“推进计划与心跳推进”、“心跳推进”第 2、4 点）：玩家点“等待”“推进”时，推进分钟数是 `menu` 请求数值参数里的增量；心跳推进请求的分钟数不由客户端给，固定取 `rules.host.heartbeatStepMinutes`（§2.2）。目标时刻 = 处理该请求时的 `state.clock.minute` 加这个增量。计时器只负责投递一条请求，内核与规则层不拿墙钟换算时长；墙钟能影响的只有序列里心跳请求有几条、排在哪里。复演按序列重放，不开定时器；`replay_verify` 只认输入序列。
  - 界面命令不记进输入序列（卷二十九 R29-3.10、C29-6，李白 11-14 裁定 Q29-9）；上行头部的显示字段不作复演的输入。
  - 推进类别标签（`advclass`）可以随请求记在日志里供统计，但它不影响结果（R27-3.2），复演不依赖它。
  - **AI 的任何输出都不得写进 textPaths 之外的状态**（卷一 I42）。模型产出的结构化内容（人口档案一类）同样在禁止之列：需要这类内容时由规则层按种子键采样生成；模型只能写文字路径，经 aiGate 以 Sealed 入库。现有把模型生成的档案当作已接受内容写入状态的路径退役（M27-16）。
  - `replay_verify` 遇到文字路径时从存档取已有的 Sealed，不重新调用模型（录制回放归卷九 §4.18）。
- **R27-7.4 不迁移**：不存在迁移表、兼容层、旧引擎、读档时的格式转换入口。`rulesDigest` 不符的存档不能加载（R27-4.3）。“不动原存档”的含义仅是不改、不删存档文件。
- **R27-7.5 本卷只管读档时的一次比较**：读档入口对 `rulesDigest` 做一次相等比较，不等即拒绝，不迁移；导入走同一比较（R27-4.3）。已有世界能不能安装、卸载扩展包，装包后数据副本与摘要怎样算、算不算新世界，都由卷二十八 §4.6 定（§8 第 12 条，涉及产品取舍处请李白定），本卷不裁定。
- **R27-7.6 开局缺省**：新世界的缺省值全部来自卷十 §4.12；不存在“为旧存档补缺省”的路径。
- **R27-7.7 复演是日常门禁**：每个基准场景（§4.6）结束后都对其日志做一次 `replay_verify`。

### 4.8 种子键与骰值键（确定性约束与验收）

种子键的格式、派生函数、PRNG 算法一律见卷二 §1.10，五段原则见卷一 §8.2。本节规定：骰值键五段各取什么成分（R27-8.5，主会话 11-13 裁定）、必须满足的约束、怎么验。

#### 4.8.1 维度

族 `seedrole`；现有种子键登记表的各列（文件、种类、表达式、次数、前缀、角色）——表的格式归卷二 §1.10，本节只读。

#### 4.8.2 统一入口

抽取只经卷二 §1.10 的采样函数与内核的骰值键包装；种子键类型只由内核构造（卷二 §2.9 第 2 条）；扫描 S27-6。

#### 4.8.3 规则

- **R27-8.1 全登记**：规则层与内核的每一个随机抽取点、每一个由种子派生 id 的点，都在登记表里有一行；源码与登记表双向比对，任一侧多出即 E-SEED-KEY（沿用现有机制）。
- **R27-8.2 键的成分只能是代号、id、整数**：种子键与骰值键的任何成分不得来自文字、AI 输出、墙钟、内存地址、遍历次序、调用计数、存档序号或入堆序号。类型上由“种子键只由内核按文法构造”保证；另由 `replay_verify` 动态核对。违例 E-SEED-COMPONENT。
- **R27-8.3 分流（流独立）**：随机数按键即取即算，不存在跨调用共享的随机数流或游标。键里又没有任何计数（R27-8.5），因此新增、删除、重排任何一个抽取点，不改变其他抽取点得到的值。出现带游标的随机数对象即 E-SEED-STREAM。
- **R27-8.4 域分隔**：不同用途的抽取点，流代号或抽取点代号至少有一个不同；登记表中角色为 `role_seed` 的行，（流代号, 抽取点代号）两两不同，且前缀不得为空。静态查登记表：有重复或空前缀即 E-SEED-COLLISION。动态在 `replay_verify` 中查重：同一个键在两个不同的事务里被求值即 E-SEED-COLLISION——这说明有两个不同的场合没有被五段区分开，要改的是该抽取点对“对象”或“时刻”的取法，不是往键里加计数。
- **R27-8.5 骰值键的组成（全书唯一写法）**：每一次抽取的键恰为五段——

  `(worldSeed, streamCode, subjectId, worldTime, drawSiteCode)`

  - `worldSeed`：世界种子（卷一 §8.2 的“战役种子”）。
  - `streamCode`：流代号，即登记表里该用途的前缀代号（卷一 §8.2 的“规则 id”）。固定代号。
  - `subjectId`：这次抽取针对的对象的 id——实体、聚合体、模拟单元、地点，或一条确定性派生的事件、到期项的 id（R27-8.9）。
  - **复合对象段**（封卷后勘误，李白 11-14；答卷二十六 Q12，本条是骰值键对象段写法的唯一定义处）：`subjectId` 可以是上款所列的一个 id 后接一到两个限定成分，各成分之间用内核分隔符 `|` 连接，写作“id | 限定成分”或“id | 限定成分 | 限定成分”；各卷登记表写“主体 id 后接……”的，都按此读。限定成分只能是登记代号、实体 id 或数据行内的固定序号（R27-8.2），不得是计数（本条“禁止”项）。卷二 §1.10 规定种子键各部件不含 `|`，所以复合对象段与它的成分组一一对应，也不会与任何单个 id 相同，不同成分组不会撞键。R27-8.9“两个 id 合成的父段”是同一写法在 `instanceIdOf` 父段上的用法。
  - `worldTime`：世界时钟的分钟数。整拍结算取结算区间的起点；按日、按季的抽取取该日、该季的起始分钟。
  - **生成期的第三、四段**（封卷后勘误，李白 11-14；本条是生成期复合对象段空成分填法的唯一定义处，卷七 R7-16.7、卷八 R8-16.2 照此读）：生成期没有结算区间，`worldTime` 取 `state.genesis.genesisMinute`，照卷十 R10-12.3 ①（时刻段恒取 `genesisMinute`；该字段见卷十 §2.5（运行态路径）`state.genesis` 行），本卷不另定。`subjectId` 为复合对象段而某个限定成分取值为空时，该位置填卷二 §2.9 第 0 条"内核信号代号"小族登记的空代号 `nil_seedpart`，不省略该位置。
  - `drawSiteCode`：抽取点代号（卷一 §8.2 的“序号”，但它**不是计数**）。每个抽取点在登记表里有固定代号；一个抽取点一次要取多个值时，登记固定个数的位次，每个位次是一个不同的抽取点代号（卷二十的 `drawSlots` 即这种写法）。
  - **禁止**：全局计数器、存档单调序号、入堆序号、调用次数、循环下标，以及其他任何表示“第几次”的量，都不得进入键。循环里对不同对象各抽一次时，区分靠 `subjectId`；需要从一个键得到一串值（例如不放回地抽 k 个）时，由卷二 §1.10 的采样函数从这一个键展开，不另造键。
  - 因为在给定的（流、对象、时刻）之下，用到哪个抽取点代号是代码位置决定的固定值，所以新增一个抽取点只多出一个新键，不会改变任何既有抽取点的键与取值（A27-8.2）。
  - PRNG 算法、由键到随机数的派生函数归卷二 §1.10；本条只定键由哪五段组成。**卷二十 §4.1.3 第 6 条“动作与反应用存档单调序号”的写法须改为本键**：动作与反应的抽取同样取固定的抽取点代号；同一刻对同一主体的多次反应，以触发它的事件 id 作 `subjectId` 来区分。卷二十全序键里的 `enqueuedSeq` 只用于排序，不得进入任何骰值键，也不得成为事件 id 的派生成分（§5、§8 第 13 条）。
- **R27-8.6 聚合与换层的抽取**：统计形态的抽取，`subjectId` 取聚合体 id（逐单元的取单元 id），`worldTime` 取结算区间的起点——完整的桶取桶的起始分钟，换层产生的零头区间取该区间的起点（R27-1.7）。同一单元的各个结算区间起点互不相同，所以键不撞。从聚合体里抽“某一个成员”、分户时抽份额，`subjectId` 取聚合体 id（抽份额取成员的实例 id），`worldTime` 取当时的分钟，抽取点代号取发起这次写入的规则的登记代号。由此分段无关（A27-1.3）与身份稳定（A27-2.4）才成立。
- **R27-8.7 熵的去处**：`role_entropy`（非确定来源）只允许出现在 aiGate 与 host 组，且其值不得流入规则层与内核。规则层与内核中该角色的行数为 0。运行时不量延迟；延迟只在测试台外部量（卷九 R9-18.5）。
- **R27-8.8 分布质量**：对卷二 §1.10 的每种首批分布，离线抽取 `distSampleSize` 个样本，按 `distTest` 指定的方法做拟合度检验，显著性水平 `distAlpha`，被拒绝即不过；另取若干对只差一段的键，核对两条输出序列的相关系数绝对值不超过 `keyCorrMax`。换种子的分布比较（A27-8.4）用 `seedSampleSize` 组种子，统计量与容差同 R27-1.9。规律是分布：验的是整体，不是单次。
- **R27-8.9 事件 id 与实体 id 确定性派生**：规则层与内核产生的事件 id、实体 id、到期项 id 一律经卷二 §1.10 的派生函数由（世界种子、产生它的规则或指令的代号、主体 id、世界时刻、固定的位次代号）得出，不得含随机标识、墙钟、计数。原因有两条：这些 id 会作为骰值键的 `subjectId`；`replay_verify` 要求事件流逐字节复现。现有带随机值的事件 id 改为派生（M27-12）。同一刻同一主体在同一规则下产生多条事件时，用什么成分区分由卷二十与卷二给出细则（§8 第 13 条），原则同上：不得用计数。
  - **两个 id 合成的父段**（封卷后勘误，李白 11-14；本条是全书复合父段写法的唯一定义处，卷十 R10-12.1 的 `instanceIdOf` 照此读）：`instanceIdOf` 的父段（即上式的“主体 id”）可以是两个 id 用内核分隔符 `|` 连接，顺序为“群体 id | 对象 id”。卷二 §1.10 规定种子键各部件不含 `|`，所以这样拼出的父段与（群体, 对象）一一对应，也不会与任何单个 id 相同，A10-12.2 的“不同父段导出不同 id”照常成立。同一写法用于骰值键对象段，见 R27-8.5“复合对象段”（答卷二十六 Q12）。

#### 4.8.6 验收断言

- **A27-8.1（扫描式）**：S27-6、S27-10 命中数为 0；登记表与源码双向比对无差；登记表里种子角色的行前缀非空且（流代号, 抽取点代号）两两不同；规则层与内核中 `role_entropy` 行数为 0；骰值键包装的参数表恰为五段，调用处没有计数器、存档序号、入堆序号流入。
- **A27-8.2（验收测试，插入无关；交卷十二机器化）**：在任意位置新增一个抽取点后重跑，除该点自身引起的后果外，其余抽取点的取值与新增前逐个相同。用只读取不使用的探针点验证：加探针前后事件流逐字节相同、排除日志分区后的世界状态摘要（定义见 R27-4.1）相等；探针在种子键登记表里多出的一行落在 `doc_data`，不在比较范围内。探针分别加在环境与时钟规则、动作、反应三类位置上，三类都要过。
- **A27-8.3（不变量式，无碰撞）**：任意基准场景的 `replay_verify` 中，没有哪个键在两个不同的事务里被求值；不同（流代号, 对象, 时刻, 抽取点代号）产生的键两两不同。
- **A27-8.4（验收测试，同种子同输出；交卷十二机器化）**：同一世界种子两次生成并推进，事件流逐字节相同、存档摘要相等（卷一 I50；不开文字模型）；换 `seedSampleSize` 组种子后，`observables` 的分布按 R27-8.8 的方法比较落在容差内。
- **A27-8.5（扩展性式）**：新增一个带随机性的系统，只登记行并调用统一包装，A27-8.2 至 A27-8.4 不改测试代码即覆盖到它。
